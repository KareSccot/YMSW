# 30 - 故障排查


## 流水线启动失败

**错误现象**：流水线未触发，或触发后立即失败。

**适用环境**：所有使用 Common CI/CD 模板的项目。

**诊断步骤**：
1. 检查 `.gitlab-ci.yml` 文件是否存在 → 确认在项目根目录
2. 检查 `.gitlab-ci.yml` 语法 → GitLab CI Lint 工具验证
3. 检查 `include` 路径是否正确 → 确认本地路径引用格式为 `local: path/to/file.yml`
4. 查看流水线日志 → 点击失败 job，查看具体错误信息
5. 检查 GitLab Runner 是否可用 → 查看 Settings → CI/CD → Runners

**解决步骤**：
1. 若 `.gitlab-ci.yml` 缺失 → 从模板项目复制并修改
2. 若语法错误 → 使用 GitLab CI Lint 修复
3. 若 `include` 路径错误 → 修正为正确的相对路径
4. 若 Runner 不可用 → 等待 Runner 恢复或联系 DevOps 团队

**如果无效怎么办**：
- 将错误日志截图，联系 DevOps 团队 `#devops-support`
- 提供项目路径和流水线 ID，便于快速定位

## 构建阶段失败

**错误现象**：流水线在 build 阶段失败，无法完成编译打包。

**适用环境**：Gradle / Maven / pnpm 构建项目。

**诊断步骤**：
1. 查看构建日志 → 滚动到日志末尾，查找错误关键字
2. 检查构建工具版本 → 确认项目使用的 JDK/Gradle/Maven/Node.js 版本与模板一致
3. 检查依赖是否正确 → 确认 `BUILD_FOLDER` 和 `ARTIFACT_FOLDER` 变量设置正确
4. 检查 `${BUILD_TOOL}` 变量 → 确认设置为 `gradle` / `mvn` / `pnpm` 之一

**解决步骤**：
1. 编译错误 → 修复代码编译问题，重新提交
2. 变量配置错误 → 修改 GitLab CI/CD Variables 中的值
   ```yaml
   variables:
     BUILD_TOOL: "gradle"   # 改为正确的工具
     BUILD_FOLDER: "./src"  # 改为实际路径
   ```
3. 版本不兼容 → 调整项目使用的构建工具版本
4. 依赖下载失败 → 确认网络连通性，检查镜像配置

**如果无效怎么办**：
- 提供完整构建日志给 DevOps 团队
- 确认本地能否正常构建（`./gradlew build` 或 `mvn package`）

## 部署阶段失败

**错误现象**：流水线在 deploy 阶段失败，应用无法部署到目标环境。

**适用环境**：K8s（ArgoCD）部署 / VM（Docker Compose）部署。

**诊断步骤**：
1. 查看部署日志 → 展开 deploy job 的日志，查找错误信息
2. 检查部署环境变量 → 确认目标环境的 SSH/Variables 配置正确
3. 检查镜像是否存在 → 确认容器镜像已成功推送
4. ArgoCD 部署：查看 ArgoCD UI 了解同步状态和错误
5. VM 部署：检查 SSH 连接是否能到达目标服务器

**解决步骤**：
1. 镜像未推送 → 先修复容器构建阶段
2. 环境变量缺失 → 在 GitLab CI/CD Variables 中补全缺失变量
3. SSH 连接失败 → 检查目标服务器防火墙和 SSH 密钥配置
4. ArgoCD 同步失败 → 在 ArgoCD UI 中手动同步或回滚

**如果无效怎么办**：
- 联系 DevOps 团队，提供流水线链接和部署日志
- 紧急情况需回滚 → 联系 DevOps 团队立即处理

## 安全扫描问题

**错误现象**：SAST / SCA / Docker 安全扫描失败或超时。

**适用环境**：启用安全扫描的 CI/CD 项目。

**诊断步骤**：
1. 检查安全扫描日志 → 查看具体哪个扫描工具报错
2. SAST 扫描失败 → 检查 `SAST_PROJECT_ID` 和 `SAST_APP_ID` 是否配置
3. SCA 扫描失败 → 检查 `SCA_PROJECT_TOKEN` 是否配置
4. Docker 扫描失败 → 确认容器镜像已成功构建
5. 查看扫描超时设置 → 默认超时 3600 秒，可调整

**解决步骤**：
1. 安全扫描工具配置缺失 → 联系安全团队获取配置信息
2. 扫描超时 → 调整 `SECURITY_SAST_SCAN_TIMEOUT` 变量
3. 误报问题 → 在安全团队审核时说明
4. 安全扫描允许失败（`allow_failure: true`），不会阻塞流水线

**如果无效怎么办**：
- 联系安全团队 `#security-support`
- 提供扫描报告 ID 和流水线链接

## 团队层流水线配置问题

**错误现象**：团队自定义工作流（Team-CICD）引用后，流水线无法正常触发或行为不符合预期。

**适用环境**：所有使用 `team-cicd` 仓库自定义工作流的团队项目。

**诊断步骤**：
1. 检查 `include` 引用路径 → 确认 `project`、`ref`、`file` 三个参数是否正确
   - `project: 'devops/cicd-template'` 是否正确
   - `ref: Master` 分支是否存在（或 `feat/build_prod_image` 等分支）
   - `file` 路径是否以 `/` 开头（如 `'/workflows/app-workflow.yml'`）
2. 检查团队工作流文件是否存在 → 确认团队目录和文件名正确
3. 检查变量覆盖层级 → 区分顶层 `variables:` 和 job 内 `variables:` 的区别
4. 检查 Runner 标签 → 确认 `default.tags` 中的标签在 GitLab Runner 中注册
5. 检查 `rules` 覆盖行为 → 确认团队工作流中的 `rules` 正确覆盖了 Common 模板的默认规则

**解决步骤**：
1. `include` 引用错误 → 修正为正确的三段式引用格式：
   ```yaml
   include:
     - project: 'devops/cicd-template'
       ref: Master
       file: '/workflows/app-workflow.yml'
   ```
2. 变量覆盖不生效 → 确保变量放在正确的层级：
   - 全局变量放在顶层 `variables:`
   - job 特定变量放在 `build-app: variables:` 下
   - 注意 YAML 缩进（2 空格，非 Tab）
3. Runner 标签不匹配 → 在 GitLab → Settings → CI/CD → Runners 查看可用标签，调整 `default.tags`
4. 团队工作流引用失败 → 确认应用项目的 `.gitlab-ci.yml` 中 `include` 的 `project` 指向团队仓库：
   ```yaml
   include:
     - project: '<team>/team-cicd'
       ref: Master
       file: '<team>/backend-workflow.yml'
   ```
5. 分支策略冲突 → 检查团队工作流中的 `rules` 是否使用了 `!reference [.conditions_for_*]` 并正确引用

**如果无效怎么办**：
- 提供完整的 `.gitlab-ci.yml` 和团队工作流文件内容给 DevOps 团队
- 在 GitLab CI Lint 工具中验证 YAML 语法
- 开启 `BEFORE_DEBUGGING_TIME` 变量（如 `"10s"`）在构建前获取调试信息
