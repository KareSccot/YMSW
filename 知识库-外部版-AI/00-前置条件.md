# 00 - 前置条件


## 接入 CI/CD 前置条件

**触发条件**：新项目需要接入 CI/CD 流水线，或团队首次使用 GitLab CI。

**输入信息**：
- 项目 GitLab 地址（由项目负责人提供）
- 团队名（Team name）
- 部署类型：VM（虚拟机）或 K8s（ArgoCD）
- 构建工具类型：Gradle / Maven / pnpm / Docker

**步骤清单**：
1. 确认项目已托管在 GitLab 实例上
2. 确定项目对应的 Team 和部署环境（dev / uat / prod）
3. 选择构建工具类型并配置构建参数
4. 在项目根目录创建 `.gitlab-ci.yml` 文件
5. 引用 Common 层 CI/CD 模板
6. 提交代码并推送至远程仓库，触发流水线

**输出结果**：项目成功接入 CI/CD，首次流水线自动触发。

**预估耗时**：10-15 分钟（首次配置）；后续每次提交自动触发。

**升级路径**：
- 接入问题 → 联系 DevOps 团队，Slack 渠道：`#devops-support`
- 项目权限问题 → 联系项目负责人或团队 Tech Lead
- 部署环境配置 → 联系对应环境负责人（dev/uat/prod）
- 无人响应 → 升级至 DevOps 主管

## 项目 GitLab CI 配置要求

**触发条件**：准备在项目中启用 GitLab CI/CD 流水线。

**输入信息**：
- `.gitlab-ci.yml` 配置文件
- 构建工具环境变量（如 `BUILD_TOOL`、`BUILD_IMAGE`）
- 部署所需变量（不包含敏感凭证）

**步骤清单**：
1. 在项目根目录创建 `.gitlab-ci.yml`
2. 使用 `include` 关键字引用 Common 层工作流模板：
   ```yaml
   include:
     - local: workflows/app-workflow.yml
   ```
3. 根据构建工具设置变量：
   - `BUILD_TOOL`: `gradle` / `mvn` / `pnpm`
   - `BUILD_FOLDER`: 源码目录路径
   - `ARTIFACT_FOLDER`: 制品输出目录
4. 提交并推送代码

**输出结果**：流水线自动触发，包含 build → test → quality → deploy 各阶段。

**预估耗时**：5-10 分钟。

**升级路径**：
- 模板引用失败 → 确认 `.gitlab-ci.yml` 在项目根目录
- 构建报错 → 检查 `BUILD_TOOL` 变量是否正确设置
- 上述无法解决 → 截图错误信息，联系 DevOps 团队 `#devops-support`

## GitLab 项目管理入门

**触发条件**：需要在 GitLab 上创建新项目或管理已有项目。

**输入信息**：
- 项目名称（name）
- 所属组 ID（namespace_id，可选）
- 管理员权限的 GitLab Token

**步骤清单**：
1. 通过 GitLab Web UI 创建项目：
   - 进入 GitLab 实例 → Projects → New Project
   - 填写项目名称和可见性（外部项目建议设为 private）
   - 选择所属组（Group）
2. 或通过 API 自动化创建（由 DevOps 团队操作）：
   - 调用项目管理 API 创建项目
   - 设置项目可见性为 private
3. 项目创建后，在 Settings → CI/CD → Variables 中配置环境变量

**输出结果**：项目创建完成，可配置 CI/CD 流水线。

**预估耗时**：2-5 分钟（UI 创建）；即时（API 创建）。

**升级路径**：
- 无法创建项目 → 检查 GitLab 权限，联系项目管理员
- 需要批量创建 → 联系 DevOps 团队协助
- 权限问题 → 联系团队 Tech Lead 或 GitLab 管理员

## Team-CICD 团队层接入

**触发条件**：团队需要在 Common CI/CD 模板之上添加团队通用的构建配置，避免每个应用项目重复编写。

**输入信息**：
- `team-cicd` 仓库地址（团队级 CI/CD 配置仓库）
- 团队名（如 `smart-esg`、`atlas-team`、`ariba`、`axiom` 等）
- 项目类型（Java Gradle / Java Maven / Python / Go / 前端）
- 部署方式（K8s ArgoCD / VM Docker Compose）

**步骤清单**：
1. **克隆/创建 team-cicd 仓库**：参考 `devops/cicd-template` 的团队层结构
2. **创建团队目录**：在仓库根目录下创建团队目录（如 `smart-esg/`、`atlas-team/`）
3. **编写团队工作流文件**：创建 `backend-workflow.yml` 或 `frontend-workflow.yml`，引用 Common 模板并覆盖团队默认变量：
   ```yaml
   include:
     - project: 'devops/cicd-template'
       ref: Master
       file: '/workflows/app-workflow.yml'

   variables:
     DEPLOY_CONTAINER: "false"  # 使用 ArgoCD 部署，非容器化

   build-app:
     variables:
       BUILD_FOLDER: "."
       ARTIFACT_FOLDER: ./build/libs

   default:
     tags:
       - tencent
       - <team-tag>
       - shared
       - platform
   ```
4. **应用项目引用团队工作流**：在应用项目的 `.gitlab-ci.yml` 中引用团队仓库：
   ```yaml
   include:
     - project: '<team>/team-cicd'
       ref: Master
       file: '<team>/backend-workflow.yml'
   ```
5. **配置团队特定变量**：在 GitLab CI/CD Variables 中设置团队级变量（如 `IMAGE_NAME`、`SERVICE_PORT`）
6. **提交并推送**：触发流水线验证团队层配置生效

**输出结果**：团队层 CI/CD 配置就绪，应用项目可引用团队工作流。

**预估耗时**：20-40 分钟（首次创建团队层配置）。

**升级路径**：
- 引用路径错误 → 确认 `project` 和 `file` 路径正确，`ref` 分支存在
- 变量覆盖失败 → 检查团队工作流中 `variables` 层级是否正确
- Runner 标签不匹配 → 确认 `tags` 中的标签在 GitLab Runner 上存在
- 无法解决 → 联系 DevOps 团队 `#devops-support`
