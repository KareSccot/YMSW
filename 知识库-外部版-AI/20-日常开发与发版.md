# 20 - 日常开发与发版


## 日常开发流水线流程

**触发条件**：开发者在功能分支或修复分支上提交代码。

**输入信息**：
- 代码变更（push 到远程仓库）
- 分支名（feature / fix / dev 分支）

**步骤清单**：
1. 在本地功能分支开发完成后，提交并推送至远程仓库
2. 流水线自动触发，执行以下阶段：
   - **build**: 构建项目（编译、打包）
   - **quality**: 代码质量扫描（SonarQube）和安全扫描（SAST / SCA / Docker Scan）
   - **deploy-dev**: 手动部署到 dev 环境（需手动触发）
3. 查看流水线状态：
   - GitLab → CI/CD → Pipelines → 选择对应流水线
   - 各阶段显示绿色（成功）或红色（失败）
4. 准备合并到主分支时，创建 Merge Request
5. MR 触发 Merge Request Pipeline：
   - 再次执行构建和安全扫描
   - MR 合并前需通过所有检查

**注意事项**：
- 流水线规则自动判断：push 到分支触发 dev/fix 规则，MR 事件触发 MR 规则
- 安全扫描允许失败（`allow_failure: true`），不会阻塞流水线
- dev 环境部署需手动点击确认

**输出结果**：功能分支构建验证通过，可合并到主分支。

**预估耗时**：5-15 分钟（取决于项目大小）。

**升级路径**：
- 流水线未触发 → 检查 `.gitlab-ci.yml` 是否存在且语法正确
- 构建失败 → 查看构建日志，确认编译错误
- 安全扫描问题 → 联系安全团队 `#security-support`

## 发版流程（Release）

**触发条件**：功能开发完成，需要发版到生产环境。

**输入信息**：
- 已合并到主分支的代码
- 发版负责人（Release Manager）
- 审批人（Approver）

**步骤清单**：
1. **前置准备**：确保所有功能分支已合并到主分支，dev 环境验证通过
2. **创建 Tag**：在 GitLab 中创建版本 Tag（如 `v1.2.0`）
   - 推送 Tag 后自动触发 Release Pipeline
3. **发版流程**：
   - 自动创建 Release（记录发版人和版本信息）
   - 进入 **approval** 阶段：
     - **Release Approval**：发版审批（必须由非发版人的第二人审批）
     - **AppSec Approval**：安全审批（由安全团队审核）
   - 审批通过后手动部署到 **uat** 环境
   - UAT 验证通过后手动部署到 **prod** 环境
4. **发版完成**：finalize-release 阶段完成，发版结束

**注意事项**：
- Release Approval 不能由发版人自己审批，需要第二人
- 生产部署前必须通过所有审批
- `allow_failure: false` 的审批阶段必须通过，否则流水线阻塞

**输出结果**：新版本发布到生产环境。

**预估耗时**：30-60 分钟（取决于审批速度和 UAT 验证）。

**升级路径**：
- 审批卡住 → 联系对应的 Release Approver 或 AppSec 团队
- 找不到审批人 → 联系团队 Tech Lead 协调
- 部署失败 → 联系 DevOps 团队回滚
- 紧急发版 → 联系 DevOps 主管协调加速审批

## UAT 环境部署与验证

**触发条件**：代码已通过审批，需要部署到 UAT 环境进行用户验收测试。

**输入信息**：
- 已审批的 Release Pipeline
- 部署环境（uat）
- 容器镜像版本

**步骤清单**：
1. 确认 Release Pipeline 已通过审批阶段
2. 在 Pipeline 页面找到 deploy-uat 阶段
3. 点击手动触发（manual）部署到 UAT 环境
4. 等待部署完成（ArgoCD 同步或 Docker Compose 启动）
5. 在 UAT 环境进行功能验证：
   - 访问 UAT 环境 URL 测试功能
   - 确认业务功能正常
6. 验证通过后，准备生产部署

**注意事项**：
- UAT 部署仅在主分支（master/main）上触发
- UAT 环境部署是手动触发的
- UAT 验证未通过不能部署到生产环境

**输出结果**：应用成功部署到 UAT 环境，验证通过。

**预估耗时**：5-10 分钟。

**升级路径**：
- UAT 环境无法访问 → 检查网络配置，联系 DevOps 团队
- 功能异常 → 确认代码是否已正确部署，检查日志
- 需要回滚 UAT → 重新部署上一个版本

## 管理 GitLab 流水线

**触发条件**：需要手动触发流水线、查看流水线状态或调试流水线问题。

**输入信息**：
- 项目 ID 或路径
- 目标分支（ref）
- 可选：流水线变量

**步骤清单**：
1. **查看流水线状态**：
   - 进入 GitLab → CI/CD → Pipelines
   - 查看流水线列表，各阶段状态一目了然
2. **手动触发流水线**：
   - 进入 GitLab → CI/CD → Pipelines → Run Pipeline
   - 选择分支，填写变量（可选），点击 Run
3. **查看流水线详情**：
   - 点击任意流水线 ID
   - 查看各阶段日志，定位失败步骤
4. **取消/重试**：
   - 取消正在运行的流水线：点击 Cancel
   - 重试失败的流水线：点击 Retry
5. **查看流水线变量**：
   - 进入 Settings → CI/CD → Variables
   - 查看和管理环境变量

**输出结果**：流水线触发或状态查看完成。

**预估耗时**：1-2 分钟。

**升级路径**：
- 流水线卡住 → 检查是否有 pending 的 job，确认 runner 可用
- 变量配置错误 → 在 Settings → CI/CD → Variables 中修改
- Runner 不可用 → 联系 DevOps 团队

## 常见 CI/CD 问题

**典型问法**：我的流水线怎么没触发？怎么看发版进度？部署到哪了？

**标准答案**：
- **流水线未触发**：检查 `.gitlab-ci.yml` 文件是否在项目根目录，语法是否正确。确认分支名是否匹配 pipeline 触发规则（push 到分支或 MR 事件）。
- **查看发版进度**：在 GitLab → CI/CD → Pipelines 页面查看流水线状态。各阶段颜色编码：绿色=成功，红色=失败，蓝色=运行中，灰色=跳过/未执行。
- **部署状态**：在对应 Pipeline 的 deploy 阶段查看日志，或通过 ArgoCD UI 查看应用同步状态。
- **构建失败**：点击失败的 job，查看详细日志，通常日志末尾会包含错误原因。
- **审批等待**：Release 需要第二人审批，AppSec 需要安全团队审批。联系对应人员尽快处理。

**补充链接**：
- GitLab CI/CD 文档：GitLab 官方文档
- 流水线状态查看：GitLab → CI/CD → Pipelines

**升级路径**：
- 流水线配置问题 → 联系 DevOps 团队 `#devops-support`
- 审批卡住 → 直接联系审批人（Release Approver / AppSec 团队）
- 紧急问题 → 联系 DevOps 主管

## 如何管理 GitLab 项目文件

**典型问法**：怎么通过 API 管理 GitLab 项目中的文件？如何批量更新部署配置？

**标准答案**：
- **文件管理 API**：GitLab 提供 Repository Files API 管理项目文件。支持创建、读取、更新、删除和列出文件。
- **ArgoCD 版本更新**：部署到 K8s 的项目，流水线会自动调用版本管理服务更新 GitOps 仓库中的镜像版本。外部用户无需手动操作 API。
- **批量更新**：如需批量更新多个部署文件的版本号，可通过版本管理服务的批量更新功能。
- **文件操作**：所有文件操作记录在 Git 提交历史中，可追溯。

**补充链接**：
- GitLab Repository Files API 文档
- 文件管理操作：GitLab Web UI → Repository → Files

**升级路径**：
- 需要批量文件操作 → 联系 DevOps 团队协助
- 文件权限问题 → 确认项目权限设置

## 团队特定部署策略

**触发条件**：团队需要使用自定义部署策略，如禁用 dev 环境部署、使用特定分支触发 UAT 部署、自定义审批规则。

**输入信息**：
- 团队工作流文件（如 `smart-esg/backend-workflow.yml`）
- 目标分支策略（如 `UAT` 分支、`main` 分支集中管理）
- 部署环境控制（启用/禁用 dev / uat / prod 环境）

**步骤清单**：

### 1. 禁用 dev 环境部署
部分团队不需要 dev 环境，可在团队工作流中禁用：
```yaml
deploy-dev:
  rules:
    - when: never
```

### 2. 自定义 UAT 部署触发条件
使用 `UAT` 分支触发 UAT 部署（而非默认的 `master` 分支）：
```yaml
deploy-uat:
  rules:
    - if: $CI_COMMIT_BRANCH == "UAT"
    - when: never

deploy-container-uat:
  rules:
    - when: never
```

### 3. main 分支集中管理策略
使用 `main` 分支作为默认分支，UAT 自动部署、ThreatModeling 集中管理：
```yaml
deploy-container-uat:
  rules:
    - if: $BUILD_CONTAINER != "true"
      when: never
    - if: $CI_COMMIT_BRANCH == "main"
      when: on_success
    - if: $CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"
      when: on_success
    - when: never

ThreatModeling:
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: on_success
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: on_success
    - when: never
```

### 4. 安全扫描环境控制
部分团队限制安全扫描仅在特定分支执行（如 `UAT` 分支）：
```yaml
DockerScan:
  rules:
    - if: $CI_COMMIT_BRANCH == "UAT"
    - when: never

SCA:
  rules:
    - if: $CI_COMMIT_BRANCH == "UAT"
    - when: never

ThreatModeling:
  rules:
    - if: $CI_COMMIT_BRANCH == "UAT"
    - when: never

GenSecurityReport:
  rules:
    - if: $CI_COMMIT_BRANCH == "UAT"
    - when: never
```

### 5. 团队 Runner 标签配置
团队通过 `default.tags` 指定 Runner 选择策略：
```yaml
default:
  tags:
    - tencent          # 腾讯云 Runner
    - <team-tag>       # 团队专用标签（如 mno、atlas）
    - shared           # 共享 Runner（后备）
    - platform         # 平台 Runner（后备）
```

**输出结果**：团队级部署策略配置完成，各环境部署行为符合团队规范。

**预估耗时**：10-20 分钟（根据策略复杂度）。

**升级路径**：
- 部署规则未生效 → 检查 `rules` 优先级和 `when` 条件
- Runner 标签不匹配 → 确认 `tags` 在 GitLab Runner 管理中已注册
- 环境部署被错误禁用 → 检查 `deploy-dev` / `deploy-uat` 的 `rules` 配置
- 分支策略冲突 → 确认 `conditions_for_branch_push` 和 `conditions_for_merge_requests` 引用正确
- 无法解决 → 联系 DevOps 团队 `#devops-support`
