# 10 - 新手接入指南


## 新手接入 CI/CD 流水线

**触发条件**：开发者首次接入团队的 CI/CD 流水线。

**输入信息**：
- 项目 GitLab 地址
- 部署环境（dev / uat / prod）
- 构建工具类型（Gradle / Maven / pnpm / Docker）

**步骤清单**：
1. **确认项目已托管**：项目已在 GitLab 实例上创建，开发者拥有至少 Developer 角色
2. **选择工作流**：根据项目类型选择工作流模板
   - 应用程序项目 → `app-workflow.yml`
   - IaC（基础设施即代码）项目 → `iac-workflow.yml`
3. **配置构建参数**：在项目 CI/CD Variables 中设置：
   - `BUILD_TOOL`: 构建工具（gradle / mvn / pnpm）
   - `BUILD_FOLDER`: 源码目录（如 `./backend`）
   - `ARTIFACT_FOLDER`: 制品输出目录（如 `./backend/build/libs`）
   - `SERVICE_REPOSITORY`: 镜像仓库命名空间
   - `BUILD_CONTAINER`: 是否构建容器镜像（`true` / `false`）
   - `TEAM`: 所属团队名
4. **创建 `.gitlab-ci.yml`**：在项目根目录编写：
   ```yaml
   include:
     - local: workflows/app-workflow.yml
   ```
5. **提交代码**：推送至远程仓库，流水线自动触发
6. **查看流水线状态**：在 GitLab → CI/CD → Pipelines 页面查看

**输出结果**：CI/CD 流水线成功运行，项目完成构建。

**预估耗时**：15-30 分钟（首次接入）。

**升级路径**：
- 流水线未触发 → 检查 `.gitlab-ci.yml` 文件位置和语法
- 变量缺失 → 在 GitLab UI 中配置 CI/CD Variables
- 构建失败 → 检查构建工具版本和参数
- 无法解决 → 联系 DevOps 团队 `#devops-support`

## 配置构建工具（Gradle / Maven / pnpm）

**触发条件**：项目使用特定构建工具，需要配置 CI/CD 构建阶段。

**输入信息**：
- 构建工具名称（gradle / mvn / pnpm）
- 构建目录路径（`BUILD_FOLDER`）
- 制品输出路径（`ARTIFACT_FOLDER`）

**步骤清单**：

### Gradle 构建
```yaml
variables:
  BUILD_TOOL: "gradle"
  BUILD_FOLDER: "change_me"      # 修改为实际路径
  ARTIFACT_FOLDER: "change_me"   # 修改为实际路径（如 build/libs）
  GRADLE_BUILD_OPTS: "clean build"
```
- 构建环境：JDK 21 + Gradle
- 输出制品：`${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`

### Maven 构建
```yaml
variables:
  BUILD_TOOL: "mvn"
  BUILD_FOLDER: "change_me"      # 修改为实际路径
  ARTIFACT_FOLDER: "change_me"   # 修改为实际路径
  BUILD_ENV: "dev"               # Maven Profile
  MVN_OPTS: "-P${BUILD_ENV} -Dmaven.test.skip=true"
```
- 构建环境：JDK 21 + Maven
- 输出制品：`${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`

### pnpm 构建
```yaml
variables:
  BUILD_TOOL: "pnpm"
  BUILD_FOLDER: "change_me"      # 修改为实际路径
  ARTIFACT_FOLDER: "change_me"   # 修改为实际路径
```
- 构建环境：Node.js 18 + npm 9.8.1
- 输出制品：`${BUILD_FOLDER}/${ARTIFACT_FOLDER}/`

**输出结果**：构建阶段完成，制品产出。

**预估耗时**：3-10 分钟（取决于项目大小）。

**升级路径**：
- 构建超时 → 检查项目是否有大型依赖需要优化
- 构建工具版本不兼容 → 确认项目使用的 JDK/Gradle/Maven/Node 版本
- 解决不了 → 联系 DevOps 团队，提供构建日志

## 构建 Docker 容器镜像

**触发条件**：项目需要构建 Docker 镜像并推送到镜像仓库。

**输入信息**：
- Dockerfile 路径（默认 `./Dockerfile`）
- 镜像仓库命名空间（`SERVICE_REPOSITORY`）
- 服务名（`SERVICE_NAME`，默认使用项目名）
- 构建参数（`DOCKER_BUILD_ARGS`，可选）

**步骤清单**：
1. 在项目根目录准备 Dockerfile
2. 设置 CI/CD Variables：
   ```yaml
   variables:
     BUILD_CONTAINER: "true"
     SERVICE_REPOSITORY: "<team-namespace>"
     DOCKER_BUILD_PATH: "."
     DOCKERFILE_NAME: "./Dockerfile"
   ```
3. 提交代码，流水线自动触发容器构建
4. 镜像标签格式：`<registry>/<namespace>/<service-name>:<branch>-<pipeline-id>`
5. 镜像构建完成后自动推送到镜像仓库

**注意事项**：
- 如果项目不需要构建容器，设置 `BUILD_CONTAINER: "false"` 或留空
- `SERVICE_REPOSITORY` 必须设置，否则镜像推送失败
- 镜像仓库凭证由平台自动注入，无需手动配置

**输出结果**：Docker 镜像构建并推送至镜像仓库。

**预估耗时**：2-5 分钟（取决于镜像大小和网络）。

**升级路径**：
- 镜像构建失败 → 检查 Dockerfile 语法和依赖
- 镜像推送失败 → 确认 `SERVICE_REPOSITORY` 是否配置正确
- 需要修改镜像仓库配置 → 联系 DevOps 团队

## 部署应用到 K8s（ArgoCD）

**触发条件**：容器镜像构建完成，需要部署到 K8s 环境。

**输入信息**：
- 部署环境（dev / uat / prod）
- 所在区域（`REGION`，默认 `sh`）
- 所属团队（`TEAM`）
- GitOps 仓库中的部署配置文件路径

**步骤清单**：
1. 确保流水线已完成容器镜像构建
2. 在 GitLab UI 中手动触发部署：
   - 进入 Pipeline → 对应流水线
   - 点击对应环境的 deploy 按钮（dev / uat / prod）
   - 需要手动确认（manual trigger）
3. 部署流程自动执行：
   - 调用版本管理服务更新 GitOps 仓库中的镜像版本
   - ArgoCD 检测到变更后自动同步到目标环境
4. 验证部署状态：
   - 在 ArgoCD UI 查看应用状态
   - 或在 GitLab Pipeline 页面查看部署阶段日志

**注意事项**：
- 生产环境（prod）部署需要审批（approval）
- 部署是手动触发的（`when: manual`），不会自动执行
- 部署失败时不会自动回滚，需手动处理

**输出结果**：应用部署到目标 K8s 环境。

**预估耗时**：1-3 分钟（ArgoCD 同步）。

**升级路径**：
- 部署失败 → 检查 ArgoCD UI 查看具体错误
- 需要回滚 → 联系 DevOps 团队协助
- 环境配置问题 → 联系对应环境负责人

## 部署应用到 VM（Docker Compose）

**触发条件**：项目使用 VM 部署方式，需要将容器部署到虚拟机。

**输入信息**：
- SSH 连接信息（目标地址、端口、用户）
- 部署路径
- SSL 证书和密钥（可选）
- Docker Compose 配置文件

**步骤清单**：
1. 在项目根目录准备 `docker-compose.yml`
2. 在 GitLab CI/CD Variables 中配置环境变量：
   - `<ENV>_SSH_TARGET`: 目标服务器地址
   - `<ENV>_SSH_USER`: SSH 用户名
   - `<ENV>_SSH_PORT`: SSH 端口
   - `<ENV>_DEPLOY_PATH`: 部署路径
   - `<ENV>_SSL_CERT`: SSL 证书（可选）
   - `<ENV>_SSL_KEY`: SSL 密钥（可选）
3. 提交代码，在 Pipeline 页面手动触发对应环境的部署
4. 部署流程自动执行：
   - 上传 Docker Compose 文件和 SSL 证书到目标服务器
   - 登录镜像仓库拉取最新镜像
   - 停止旧容器，启动新容器
5. 使用 `docker compose ps` 验证容器运行状态

**注意事项**：
- 敏感信息（SSH Key、证书）通过 GitLab CI/CD Variables 注入，不写入代码
- 自定义变量必须以 `CUSTOM_` 前缀才能在远程脚本中使用
- 部署后临时文件自动清理

**输出结果**：应用部署到 VM 环境并正常运行。

**预估耗时**：2-5 分钟。

**升级路径**：
- SSH 连接失败 → 检查目标服务器 IP 和 SSH 密钥是否配置正确
- 容器启动失败 → 查看服务器端 Docker 日志
- 需要增加服务器 → 联系 DevOps 团队

## 配置团队自定义工作流（Team-CICD）

**触发条件**：团队需要在 Common CI/CD 模板基础上添加团队级自定义配置，如团队专用 Runner 标签、自定义 Docker 构建参数、特定部署策略。

**输入信息**：
- 团队名（如 `smart-esg`、`ariba`、`atlas-team`、`axiom`）
- 项目类型（Java / Python / Go / 前端）
- 部署方式（K8s ArgoCD / VM Docker Compose）
- 团队 Runner 标签（如 `tencent`、`mno`、`atlas`、`shared`、`platform`）

**步骤清单**：

### 1. 创建团队工作流文件
在 `team-cicd` 仓库的团队目录下创建 `backend-workflow.yml`，引用 Common 模板并覆盖团队默认变量：

```yaml
include:
  - project: 'devops/cicd-template'
    ref: Master
    file: '/workflows/app-workflow.yml'

variables:
  DEPLOY_CONTAINER: "false"   # 使用 ArgoCD 部署，非容器化

build-app:
  variables:
    BUILD_FOLDER: "."
    ARTIFACT_FOLDER: ./build/libs

build-container:
  variables:
    DOCKER_BUILD_PATH: '.'
    BUILD_FOLDER: "."
    ARTIFACT_FOLDER: ./build/libs
    SERVICE_PORT: 8080
    PACKAGE_NAME: ${IMAGE_NAME}
    DOCKER_BUILD_ARGS: "--build-arg BUILD_FOLDER=${BUILD_FOLDER} --build-arg ARTIFACT_FOLDER=${ARTIFACT_FOLDER} --build-arg PACKAGE_NAME=${PACKAGE_NAME} --build-arg SERVICE_PORT=${SERVICE_PORT}"

default:
  tags:
    - tencent
    - <team-tag>
    - shared
    - platform
```

### 2. 配置团队级变量

| 变量名 | 说明 | 示例值 |
|--------|------|--------|
| `DEPLOY_CONTAINER` | 是否使用容器部署（`true`/`false`） | `"false"` |
| `IMAGE_NAME` | 镜像名称（需在应用项目 GitLab CI Variables 中设置） | `"my-service"` |
| `SERVICE_PORT` | 服务端口 | `8080` |
| `PACKAGE_NAME` | 制品包名（默认 `${IMAGE_NAME}`） | `${IMAGE_NAME}` |
| `DOCKER_BUILD_ARGS` | Docker 构建参数 | `--build-arg ...` |
| `BEFORE_DEBUGGING_TIME` | 构建前调试等待时间 | `"10s"` |

### 3. 应用项目引用团队工作流
在应用项目的 `.gitlab-ci.yml` 中引用团队仓库：
```yaml
include:
  - project: '<team>/team-cicd'
    ref: Master
    file: '<team>/backend-workflow.yml'
```

### 4. 团队层的三层架构
```
Common 层: devops/cicd-template          ← 通用工作流模板
   ↓ 引用
Team 层:  <team>/team-cicd               ← 团队级配置（本步骤）
   ↓ 引用
App 层:  <team>/<app-repo>               ← 应用项目（仅需 .gitlab-ci.yml 引用）
```

### 5. 使用团队自定义镜像
部分团队指定自定义构建镜像（如 JDK 21 + Maven 3.9.6 组合镜像）：
```yaml
build-app:
  image: cld93-ld-tcr-premium-sh-001.tencentcloudcr.com/devops/jdk21.0.11_10-jdk-ubi9-minimal_mvn3.9.6:latest
```

**输出结果**：团队级 CI/CD 工作流配置完成，可被团队内所有应用项目复用。

**预估耗时**：15-30 分钟（初始配置）。

**升级路径**：
- 工作流引用失败 → 检查 `project` 路径和 `ref` 分支是否存在
- 变量覆盖不符合预期 → 检查 YAML 层级（`variables` 在 `build-app:` 下 vs 顶层）
- Runner 标签不匹配 → 确认 `tags` 中的标签已注册到 GitLab Runner
- 自定义镜像拉取失败 → 确认镜像仓库鉴权配置
- 无法解决 → 联系 DevOps 团队 `#devops-support`
