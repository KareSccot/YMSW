# 运维发版操作指南

## 目标

读完这篇，作为运维，你能通过 gitlab-management API 触发/查看流水线、发版时更新 ArgoCD 镜像版本（含批量），并知道审批门禁在哪里、不能碰什么。

## 流程要素

- **触发条件**：业务仓库已完成主干合并与 UAT 验证，准备发版（打 tag 进入 release 流水线），或需排障查看流水线状态。
- **输入信息**：`project_id`（GitLab project ID 或 path）、ArgoCD 部署文件路径 `app-values/<env>/<team>/<service>/<env>-<region>.yaml`、待发布的 `new_version`（格式 `<ref_slug>-<pipeline_id>`，如 `main-134361`）、`GITLAB_TOKEN`。
- **输出结果**：app-values 中的 `image.tag` 更新并提交回 GitOps 仓库（ArgoCD 据此滚动部署），或流水线状态查询结果。
- **预估耗时**：镜像版本更新约数秒级；ArgoCD 滚动部署约 3-10 分钟（取决于镜像大小与目标规模）。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于走 ArgoCD（K8s）部署路径的发版。若业务走 VM Docker Compose 路径（`deploy-container-prod`），不走 argocd API，改在业务仓库触发 tag pipeline 由 deploy Job SSH 部署（见 `docker-deploy.yml` 与「场景 06」）。

## 你管什么

- **查流水线**：查业务仓库的 pipeline 状态（排障用）。
- **改镜像版本**：发版时更新 ArgoCD app-values 里的 `image.tag`（单个或批量）。
- **守审批门禁**：确认 `approval` stage 在 `deploy-prod` 之前、审批 Job 齐全。

## 前置条件

- gitlab-management 服务可用（地址 `<gitlab-mgmt>`），已配 `GITLAB_TOKEN`。
- 已知目标业务仓库的 `project_id`（GitLab project ID 或 path）。
- 已知 ArgoCD 部署文件路径（`app-values/<env>/<team>/<service>/<env>-<region>.yaml`）。
- ⚠️ 服务无鉴权 + CORS 全开，须内网部署。

## 操作步骤

### 1. 查看业务仓库流水线（排障）

```bash
# 列某项目的流水线（可按 status 过滤）
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=failed"

# 查单条流水线详情
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/<pipeline_id>"
```

- pipelines 路由端点与请求/响应模型完整签名见「40-API参考/01-pipelines接口」。
- 响应 `PipelineResponse`：`{id, project_id, status, ref, sha, web_url}`。

> 注：触发流水线（`POST`）一般由业务线开发者做（见「业务线开发者」），运维主要用 GET 查状态排障。

### 2. 发版：更新 ArgoCD 镜像版本（单个）

发版时改 app-values 里的 `image.tag`：

```bash
curl -X POST "http://<gitlab-mgmt>/api/argocd/<project_id>/update-version" \
  -H "Content-Type: application/json" \
  -d '{
    "file_path": "app-values/prod/data-platform/my-service/prod-sh.yaml",
    "new_version": "main-134361"
  }'
```

- 请求模型 `UpdateVersionRequest`：`file_path`（必填）、`new_version`（必填）、`branch`（默认 `master`）、`commit_message`（默认 `Update image version`）。
- 完整请求体/响应字段（含 `last_commit_id`、`old_version` 等）见「40-API参考/03-argocd接口」。
- 服务端逻辑：取文件 → base64 解码 → `yaml.safe_load` → 改 `image.tag` → `yaml.dump` → 用 HTTP PUT（带 `last_commit_id` 乐观锁）回 GitLab。
- ⚠️ 要求文件含 `image.tag` 字段，否则抛 `image.tag field not found`。

### 3. 批量更新多个部署文件（多环境同时发版）

```bash
curl -X POST "http://<gitlab-mgmt>/api/argocd/<project_id>/batch-update" \
  -H "Content-Type: application/json" \
  -d '{
    "updates": [
      {"file_path": "app-values/uat/data-platform/my-service/uat-sh.yaml", "new_version": "main-134361"},
      {"file_path": "app-values/prod/data-platform/my-service/prod-sh.yaml", "new_version": "main-134361"}
    ]
  }'
```

- 请求模型 `BatchUpdateRequest`：`updates`（数组，每项 `file_path` + `new_version`）、`branch`、`commit_message`。
- 逐个调 `update_image_version`，返回汇总 `{total, successful, failed, results}`。
- 批量示例的完整请求体与 Python 调用见「40-API参考/03-argocd接口」。

### 4. 查看审批人配置（发版前确认）

审批人通过 GitLab CI/CD Variables 配置（需 Maintainer 权限查看）：
- `RELEASE_MANAGER`：发版审批人邮箱（单人），`approval` Job 校验触发人 ≠ 此人。
- `APPSECURITY_APPROVERS`：安全审批人邮箱列表（逗号分隔，如 `a@xxx.com,b@xxx.com`），`appsec_approval` Job 校验触发人在列表内。

在 GitLab → Project → Settings → CI/CD → Variables 中查看。发版前确认审批人在线、能及时点 manual approve。审批人变量的配置步骤见「安全团队 AppSec」步骤1。

### 5. 确认审批门禁未被动

发版前检查目标仓库 `workflows/app-workflow.yml` 的 `stages:` 列表：
- `approval` 须排在 `deploy-prod` 之前（见「CICD 总体架构」）。
- `approval` / `appsec_approval` 两个 Job 须存在且 `when: manual`。

## 常见排障

| 错误现象 | 适用环境 | 原因 | 解决步骤 | 无效怎么办 |
|---|---|---|---|---|
| Pipeline 卡在 approval stage | 全环境 | 审批人未点击 manual job | 在 CI/CD → Variables 查看 `RELEASE_MANAGER` / `APPSECURITY_APPROVERS` 邮箱值，通过公司 IM 按邮箱搜索并 @ 通知该审批人点 manual job | 升级到 GitLab Issue @平台管理员，附 pipeline_id 与日志 |
| approval Job 不出现 | 发版流程 | 条件域不对（extends 非发布规则） | 检查 Job 的 rules/extends 是否用了 `.release_rules` | 提交 MR 修正条件域，由团队 Lead 审批 |
| appsec_approval 报 "User $GITLAB_USER_EMAIL is NOT an approver" | 发版流程 | 触发人邮箱不在 `APPSECURITY_APPROVERS` 列表中 | 在 GitLab → Project → Settings → CI/CD → Variables 编辑 `APPSECURITY_APPROVERS`（逗号追加新邮箱后保存）；或由当前已在列表中的审批人触发本次发版 | 让【运维发版人】在发版通知中抄送审批人邮箱，或升级 @安全团队 AppSec |
| approval 报"RELEASE_MANAGER should not run" | 发版流程 | 发版人就是 Release Manager（职责分离校验） | 换非 Release Manager 的人触发，或由 Release Manager 以外的角色点审批 | 由团队 Lead 临时指定本次发版触发人 |
| 镜像版本 update 报"file not found" | ArgoCD 路径 | app-values 文件路径不对 | 检查 `app-values/<env>/<team>/<service>/<env>-<region>.yaml` 路径格式 | 核对 GitOps 仓库实际目录结构 |
| update 报"image.tag field not found" | ArgoCD 路径 | 部署文件无 `image.tag` 字段 | 核对该 app-values 文件结构，补 `image.tag` | 联系【平台管理员】确认该服务的 app-values 模板 |

## 注意事项

- **审批门禁靠 stages 顺序**：发版前确认 `approval` 在 `deploy-prod` 之前。若发现被后移或删除，等于门禁被绕过，须拦截并走安全层 Pro 复查。门禁完整机制与违规行为清单见「场景 05 审批门禁与注意事项」。
- **`last_commit_id` 乐观锁**：update-version 用 `last_commit_id` 防并发覆盖。若同时多人改同一文件，后写的会失败——这是设计行为，重取最新 commit_id 再试。
- **镜像版本来源**：`new_version` 格式为 `<ref_slug>-<pipeline_id>`（如 `main-134361`，见 `argo-rolling.yml` 的 `DEPLOYMENT_VERSION`）。须与主干已构建并过 UAT 的镜像对齐，避免发未经验证的镜像（Build Once Promote Many 原则）。
- **服务无鉴权**：发版操作写权限高，务必确保 gitlab-management 只运维可访问。
