# 产品经理操作指南

## 目标

读完这篇，作为产品经理/业务方，你能：说清发版流程全景（打 tag → 审批 → 部署，各阶段耗时）、查发版卡在谁的审批上、确认部署是否成功、验证环境可访问。**不需要写 YAML 或调 API**，全程只读视角。

## 流程要素

- **触发条件**：业务方想知道某次发版的上线时间、当前卡在哪一步、上线后如何验证。
- **输入信息**：要发版的业务仓库/项目名（可向运维或团队 Lead 索要 GitLab 链接）、GitLab 只读权限。
- **输出结果**：发版进度结论（卡在审批/部署中/已上线）、环境可访问性验证结果。
- **预估耗时**：approval stage 等审批约 1-4 小时（取决于审批人响应）；deploy-prod 部署约 3-15 分钟（取决于镜像大小与部署路径）。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于发版流程的只读进度查询与验收，面向不碰 CI 配置的业务方。不适用 CI 配置变更与流水线编排（那归「业务线开发者」与「Repo 层」）。

## 你的角色定位

你是业务方视角（如 HR 部门的薛老师、廖老师）。你不碰 CI 配置、不写 YAML，但需要知道：版本什么时候能上线、现在卡在哪一步、上线后怎么验证。这份指南给你只读的流程理解与进度查询方法。

## 发版流程全景（你需要理解的）

一次发版从代码到上线，大致经过：

```text
① 代码合主干（开发者完成 MR Review）
   ↓
② 主干流水线：UAT 部署 + 集成测试（开发/测试验证 UAT 环境）
   ↓
③ 打 tag（运维或开发者操作，触发发版流水线）
   ↓
④ 发版流水线：approval stage（等待审批）
   ├── approval         发版 Approve（Release Manager 之外的人点）
   └── appsec_approval  安全层 Approve（安全团队点）
   ↓
⑤ deploy-prod stage：生产部署（ArgoCD 或 VM Docker Compose）
   ↓
⑥ 上线，生命周期管理/Release
```

**你需要知道的时间锚点**：
- ③ 打 tag 前：UAT 必须已验证通过。
- ④ approval stage：**最常卡的环节**——等审批人点 manual job。卡住说明审批人没点。
- ⑤ deploy-prod：部署中，通常几分钟到十几分钟（看镜像大小和部署路径）。

## 前置条件

- 你知道要发版的业务仓库和项目（可向运维或团队 Lead 索要 GitLab 链接）。
- 你有 GitLab 只读权限（能看流水线页面）。
- 不需要 gitlab-management 的 token（PM 一般不调 API，直接看 GitLab 页面；下方 API 查询是给需要程序化查询的 PM 备用）。

## 操作步骤

### 1. 查看发版 Pipeline 状态

**方式 A：GitLab 页面（推荐）**

进 GitLab → 项目 → Build → Pipelines，找到 tag 对应的那条 pipeline，看状态：
- `running`：还在跑（看具体卡在哪个 stage）
- `blocked / manual`：**卡在 approval stage，等审批**——这是你要催的环节
- `passed` → 进入 `deploy-prod`：部署中或部署完成
- `failed`：某步失败，看是构建/扫描/部署哪一段

**方式 B：API 查询（程序化，备用）**

```bash
# 查最近流水线（按 status 过滤，running/blocked/failed/success）
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=blocked"

# 查某条流水线详情
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/<pipeline_id>"
```

响应 `PipelineResponse` 含 `status` 和 `web_url`，点 `web_url` 进页面看详情。

### 2. 查看审批进度（卡在谁那里）

如果 pipeline 状态是 `blocked` 或卡在 `approval` stage：

- GitLab 页面上 `approval` stage 下有两个 manual job：`approval`（发版 Approve）、`appsec_approval`（安全层 Approve）。
- 哪个还是 `manual`（未点）= 哪个审批人还没点。
  - `approval` 未点 → 催 **Release Manager**（发版审批人，单人）。
  - `appsec_approval` 未点 → 催 **安全团队 AppSec**（审批人列表，在 CI/CD → Variables 查看 `APPSECURITY_APPROVERS` 需 Maintainer 权限，或让【运维发版人】在发版通知中抄送审批人邮箱）。
- 注意职责分离：`approval` Job 会校验"发版人 ≠ Release Manager"——Release Manager 不能审批自己发起的发版。

> 你催的依据是"manual job 还没点"。具体审批人邮箱运维可查（`RELEASE_MANAGER` / `APPSECURITY_APPROVERS` 变量）。

### 3. 确认部署成功

`approval` stage 全过后，流水线进入 `deploy-prod` stage：

- `deploy-prod` / `deploy-container-prod` 变 `running` → 部署中。
- 变 `passed` → 部署成功，可去验证环境。
- 变 `failed` → 部署失败，让运维查 Job 日志（见 「运维发版排障」的"常见排障"节）。

### 4. 验证环境可访问

部署成功后，根据环境访问业务系统验证（环境访问地址在 CI/CD → Variables 的 `PROD_URL` 或对应环境变量中查看，或向【运维发版人】即发版通知 IM 群中本次 tag 触发人索要）：
- 确认页面/接口能正常访问。
- 确认版本号是本次发版的版本（可让运维告知 `new_version`，格式如 `main-134361`）。
- 若发现功能异常，走回滚流程：
  1. **立即通知运维**，说明问题和版本号。
  2. 运维回滚到上一个稳定版本（ArgoCD 回滚通常几分钟；VM Docker Compose 回滚需重新部署旧镜像，稍慢）。
  3. 回滚期间你协调业务方暂时使用旧版本功能或公告维护。
  4. 回滚后确认旧版本正常可用。
  5. 问题修复后走新的发版流程（不能跳过审批直接重新部署）。

  > 回滚不是"撤销发版"，而是"部署上一个稳定镜像版本"。审批门禁在回滚时可加速但不跳过。详见 「运维发版」。

## 注意事项

- **审批是最常卡的环节**：发版延迟多半因为审批人没及时点 manual job。提前协调审批人在线时间。
- **UAT 必须先过**：发版前 UAT 必须验证通过，否则不该打 tag 发版。你确认发版前可问开发"UAT 过了没"。
- **不发未验证镜像**：生产部署用的镜像是主干/UAT 验证过的那个（Build Once Promote Many），不会重新构建。若运维说要发一个没过 UAT 的版本，这是违规，你可质疑。
- **PM 不碰配置**：你不该改 `.gitlab-ci.yml`、不该有写权限。发现流程问题，反馈给运维或团队 Lead，不要自己改。
- **门禁被绕过要警觉**：若发现 `approval` stage 被跳过、或 `appsec_approval` 不见了，说明审批被绕过——这是合规问题，应报告安全团队（见 「安全团队 AppSec」）。
