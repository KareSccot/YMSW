# 业务线开发者操作指南

## 目标

读完这篇，作为业务线开发者，你能：把自己的业务仓库接入 CI、改 `.gitlab-ci.yml` 配置、触发分支/MR 流水线、查看结果，并知道哪些不能碰。

## 你做什么

- **接 CI**：给业务仓库写 `.gitlab-ci.yml`，include Common 层。
- **改配置**：改 `.gitlab-ci.yml`（通过 API 或直接编辑）。
- **触发流水线**：推分支 / MR / 手动触发。
- **查结果**：看流水线状态、Job 日志、MR Review 结果。


## 流程要素

- **触发条件**：新业务仓库需接入 CI/CD，或已有仓库需修改 CI 配置、触发流水线时。
- **输入信息**：业务仓库 GitLab project_id、团队 namespace（`TEAM`、`SERVICE_REPOSITORY`）、构建工具类型（`BUILD_TOOL`：mvn/gradle/pnpm）、gitlab-management 服务地址。
- **输出结果**：业务仓库 `.gitlab-ci.yml` 接入 Common 层，三大流程（分支MR/主干/发版）自动可用；分支推送后流水线触发并可通过 API 查看状态。
- **预估耗时**：接入 CI 约 10-30 分钟（写 .gitlab-ci.yml + 推 MR）；流水线执行取决于构建工具和镜像大小，约 3-15 分钟。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于业务线开发者的日常 CI 操作（接入、改配置、触发、查看）。发版流水线（tag → 生产部署）不归开发者触发——由运维走审批后操作，见「运维发版」。

## 前置条件

- 平台管理员已建好你的业务仓库（见 「平台管理员」）。
- 团队 Lead 已配好团队 namespace 与 `TEAM`、`SERVICE_REPOSITORY`、`BUILD_TOOL` 等变量（见 「Team 层」）。
- 你有本仓库 Developer 权限（推分支、提 MR）。
- gitlab-management 服务可用（地址 `<gitlab-mgmt>`，用于 API 改配置/触发流水线）。
- 若要用公司内部 AI 模型辅助开发：先在 `aisix-mgmt` 注册获取 API Key。

## 操作步骤

### 1. 接入 CI（写 .gitlab-ci.yml）

在业务仓库根目录建 `.gitlab-ci.yml`，最小内容：

```yaml
include:
  - project: 'platform/cicd-template'
    ref: master
    file: 'workflows/app-workflow.yml'

variables:
  SERVICE_REPOSITORY: "data-platform"   # 团队 namespace
  TEAM: "data-platform"                  # 团队名
  BUILD_TOOL: "mvn"                      # 必填：mvn / gradle / pnpm，决定构建方式
```

- include Common 层后，三大流程（分支MR/主干/发版）自动可用，无需自己编排。
- `SERVICE_NAME` 默认取 `${CI_PROJECT_NAME}`（仓库名），不用填。
- `BUILD_TOOL` 必填，不设则 build 阶段不出现（见 「Common 层 条件 include」的"条件-include构建工具动态选择"节）。

### 2. 改 CI 配置（两种方式）

**方式 A：直接编辑**（推荐，小改）

直接改 `.gitlab-ci.yml`，提交到 feature 分支，走 MR。

**方式 B：通过 API 改**（程序化批量）

用 gitlab-management files 接口：

```bash
curl -X POST "http://<gitlab-mgmt>/api/files/<project_id>/update" \
  -H "Content-Type: application/json" \
  -d '{
    "file_path": ".gitlab-ci.yml",
    "content": "<新内容>",
    "branch": "feature/update-ci",
    "commit_message": "Update CI config"
  }'
```

- files 路由有五个端点：`get` / `update` / `create` / `delete` / `list`，都走 `POST /api/files/<project_id>/<op>`。
- `update` 用 `last_commit_id` 乐观锁防并发覆盖，改前先 `get` 拿最新 commit_id。

### 3. 触发流水线

**方式 A：自然触发**（推荐）

- 推 feature/fix 分支 → 触发**分支流水线**。
- 提 MR → 触发 **MR 流水线**。
- 合到 master → 触发**主干流水线**（UAT 部署）。
- 打 tag → 触发**发版流水线**（生产部署，含审批门禁）。

**方式 B：API 手动触发**

```bash
curl -X POST "http://<gitlab-mgmt>/api/pipelines/" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "<project_id>",
    "ref": "feature/my-branch",
    "variables": {"BUILD_CONTAINER": "true"}
  }'
```

- 请求 `RunPipelineRequest`：`project_id`、`ref` 默认 `main`、`variables` 可选。
- 响应 `PipelineResponse`：`{id, project_id, status, ref, sha, web_url}`，`web_url` 可点开看。

### 4. 查看流水线结果

```bash
# 列自己的流水线（可按 status 过滤，如 failed/success/running）
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=failed"

# 查某条流水线详情
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/<pipeline_id>"
```

- 失败时点 `web_url` 进 GitLab 看 Job 日志排障。常见失败原因与定位见 「场景 03 排障表」的"4-流水线失败排障"节。
- MR 流水线结果在 GitLab MR 页面的 Pipelines 标签看，Review/Approve 由团队 Lead 处理（见 「Team 层」）。

## 注意事项

- **只改 Repo 层**：你只改本仓库 `.gitlab-ci.yml`。Common 层（cicd-template）由平台团队维护，不要直接改。
- **别动 stages 顺序**：若自定义 Job，不要改 `stages:` 列表里 `approval` 与 `deploy-prod` 的先后——那会绕过审批门禁。作为开发者，你自定义 Job 时 `needs` 只填构建依赖（如 `build-container`），审批靠 stage 顺序不靠 needs。完整门禁机制见「场景 05」。
- **本地 lint**：推 MR 前先校验 YAML 语法与 include/extends 解析，减少往返失败。
- **发版不归你触发**：发版流水线（tag → 生产部署）由运维走审批后触发（见 「运维发版」），业务线开发者一般到 MR 合主干为止。
- **API 改配置注意乐观锁**：`update` 文件要带 `last_commit_id`，并发改同一文件后写会失败，重取再试。
