## 一、背景与改造方向

### 1.1 为什么改造

知识库现有 25 篇按"四轴"组织（00 背景 / 10 层级 / 20 角色 / 30 场景 / 40 API + README），现收到《知识库文档规范.md》，定义了四类知识（政策规则 / 操作流程 / 常见问答 / 故障排查）的必含项清单 + 四条质量铁律（唯一事实来源 / 可执行性优先 / 适用范围显式声明 / 零矛盾）。

规范面向企业 IT 通用服务台（示例为申请电脑 / 连 WiFi），而本知识库是 CI/CD 专用、读者是开发者。经研判，**不应推翻现有四轴骨架重组成规范四类，而是保留四轴、按规范的"必含项清单 + 四铁律"逐篇改造**，使现有文档达标。

> 🔍 **批注1（方向判断）**：同意"保留四轴不重组四类"的决策。规范四类（政策/流程/FAQ/排障）面向 IT 通用服务台，CI/CD 知识库读者是开发者，四轴（背景/层级/角色/场景/API）更适合工程语境。但需注意：规范的四类是**知识分类维度**，四轴是**内容组织维度**，二者不矛盾——四轴中的每篇文档仍应归入四类之一并满足该类必含项。方案在"二、规范四类必含项"中做了映射，方向正确。
>
> ✅ **作者审查意见（批注1）**：采纳。"四类是知识分类维度、四轴是内容组织维度，二者不矛盾"这个澄清比我原文更准确，吸收进 1.1 节表述。方案方向无需改动。

## 三、改造内容（三块 + 一附）

### 块一：Procedure 类补必含项（15 篇）

15 篇 Procedure 类（角色 6 + 场景 6 + 层级 3）几乎全部缺"触发条件 / 输入信息 / 输出结果 / 预估耗时"4 项。统一改造模式：每篇正文前补"流程要素"小段（或改造现有"前置条件"段），含：

- **触发条件**：什么情况走这流程（如"业务仓库需接入 CI 时""发版时"）
- **输入信息**：需提前准备什么（工号 / 项目 ID / 变量值等清单）
- **输出结果**：走完得到什么（接入成功的流水线 / 新建的 CI 配置 / 部署成功的环境）
- **预估耗时**：定性依赖说明（如"取决于镜像大小（分钟级）+ 审批人响应时间"），不写精确 SLA

**代表篇**（改造后供其他篇参照模板）：
- `20-角色操作指南/04-业务线开发者.md`
- `30-操作场景/04-发版与镜像版本更新.md`
- `30-操作场景/06-Dockerfile与docker-compose编写.md`

> 🔍 **批注4（块一缺失"适用范围显式声明"）**：方案的块一补了 Procedure 的4项必含项（触发/输入/输出/耗时），但遗漏了规范四铁律之三"适用范围显式声明"——"每条知识必须明确标注适用的环境/对象，如果仅适用某类场景，必须同时说明不适用的场景"。现有25篇虽在 frontmatter 有 `audience` 字段，但正文中多数未声明"不适用什么"。例如：场景06 Dockerfile 编写仅适用 VM 部署路径，不适配 ArgoCD/K8s 路径——这种"不适用"声明应在正文中显式写出。建议在块一改造模板中增加第5项"适用范围与不适用场景"，或单独列为"块四"全库扫描。
>
> ✅ **作者审查意见（批注4）**：**采纳，这是我对四铁律的系统性遗漏**（我只覆盖了可执行性、唯一来源两条，漏了适用范围、零矛盾两条）。
> - 采纳：块一改造模板加第5项"适用范围与不适用场景"，全库扫描。
> - **审查补充（务实边界）**：规范原文"否则代表所有人所有情况都这样，没有任何例外"——即只有确有限制时才需声明"不适用"，不必每篇硬凑不适用场景。多数 Policy/通用篇确实全适用，无需虚构不适用。只在确有路径/角色/环境限制时声明（如场景06 限 VM 路径不适用 ArgoCD、安全团队篇限发版流程不适用分支/MR）。这避免为达标而凑数。
