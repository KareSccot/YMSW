## 一、背景与改造方向

现有 25 篇知识库定位为**内部运维手册**（写给平台/运维/开发者，假设读者已在体系内、知道 Variables/凭证/内网地址等概念）。对外部用户（新员工/外包/业务方/新接手仓库的开发者）不友好——大量"大家都知道"的假设、内部才有权限的挫败感、用户看不到的内部日志路径。

收到《知识库文档规范.md》后，规范明确：知识类型分 Policy/Procedure/FAQ/Troubleshooting，其中 **FAQ 与 Troubleshooting 天然面向"带问题来的用户"**，正是外部版的主轴。

### 改造方向（三向）

| 方向 | 决策 | 理由 |
|---|---|---|
| 内/外关系 | 内部版保留不动；外部版**复用内部事实来源**（引用而非重写），脱敏后呈现 | 内部版是唯一事实来源，外部版不重复造真 |
| 组织方式 | 外部版按**用户问题分类**（接入/发版/排障/合规），不按内部角色/层级 | 外部用户是"带着问题来"，不是"按角色找职责" |
| 攥写主轴 | FAQ + Troubleshooting 为主，Procedure 脱敏保留，Policy 去实现细节 | 规范四类中 FAQ/Troubleshooting 最贴合"提问题+解决问题" |

> 🔍 **批注1（组织轴与类型轴不混淆）**：方向正确——外部版按"用户问题分类"（接入/发版/排障/合规）是组织轴，类似内部版的四轴（背景/层级/角色/场景/API）。但需注意：每个文件仍需标注规范四类之一的 `type` 字段（FAQ/Procedure/Troubleshooting/Policy），不能因为按问题分类就跳过类型标注。第四节的结构表已做了映射（接入类→Procedure、发版类→FAQ、排障类→Troubleshooting、合规类→Policy），方向一致。
>
> ✅ **采纳确认**：6 篇外部版文件 frontmatter 均已标 `type` 字段（procedure/faq/troubleshooting/policy），10-接入类 还加了 `secondary_type: faq`。组织轴与类型轴已区分，无混淆。

## 二、内部 vs 外部分界（脱敏边界）

### 必须内部保留（不进外部版）

来自 Alice 的分析，已三方确认：

- gitlab-management **无鉴权 + CORS 全开**的部署细节（暴露 = 安全风险）
- TCR 内网地址、`.env` 的 `DOCKER_REGISTRY` 等基础设施配置
- SSH 私钥 / SSL 证书管理路径
- aisix-mgmt 默认 `admin:admin123` 凭证
- `APPSECURITY_APPROVERS` / `RELEASE_MANAGER` 邮箱校验脚本逻辑
- 内部模型具体版本号（GLM-5.1 / DeepSeek V4 等具体值）

### 可改造为外部友好

- 三层模板架构 / Trunk Flow 三段流水线 / 审批门禁**概念**（方法论，外部可理解）
- 角色"我要做什么"视角（去掉内部团队怎么分工）
- 场景操作逻辑（**脱敏**：去掉内网地址/凭证具体值）
- API 能力（告知有哪些接口，不暴露无鉴权漏洞）

### 脱敏规则

- 外部版引用内部事实来源，但去掉具体地址/凭证/邮箱
- "内网地址见运维配置" → "向你的平台管理员/运维索要对应地址"
- "在 Variables 配 TEAM=..." → "由团队 Lead 在 CI/CD Variables 配置（你只需告知团队名）"
- 排障不引用用户看不到的内部日志路径，从"你看到的错误信息"出发

> 🔍 **批注2 已采纳**：脱敏的"索要"仍属被动表述，与"可执行性优先"有张力。外部版脱敏**标配话术模板**推广到所有"找谁"场景——不只是"找平台管理员"，而是"向平台管理员（可通过入职引导或 IM 群找到）说明你需要 [具体内容]"。Alice 迁移映射 FAQ1 已做模板（"我需要创建 GitLab 项目，团队名是[填]…"），此模式推广为外部版脱敏标配，已在 6 篇外部版"找谁→说什么"表中落实。

> 🔍 **批注2（脱敏规则与"可执行性优先"铁律的张力）**：脱敏规则将"内网地址见运维配置"→"向你的平台管理员/运维索要对应地址"——方向对，但"索要"仍属"联系某人"的被动表述，与内部版"可执行性优先"铁律有张力。建议外部版的脱敏模板统一改为"向平台管理员（可通过入职引导或 IM 群找到）说明你需要 [具体内容]"——给用户**找到人的路径 + 说什么的话术模板**。Alice 的迁移映射中 FAQ1 已做了联系模板（"我需要创建 GitLab 项目，团队名是[填]…"），这个模式应推广到所有"找谁"场景，成为外部版脱敏的标配。

## 三、外部用户画像与盲区规避

### 外部用户画像

**外部用户定义（Alice #2）**：不负责平台维护、只用 CI/CD 服务的角色。这决定 FAQ 粒度。

具体画像：
- **新员工/外包**：怎么接入 CI/CD、怎么拿 AI Gateway API Key、能用什么模型
- **业务方/产品经理（只读视角）**：发版到哪了、卡在哪、怎么验证上线
- **新接手某仓库的开发者**：这仓库 CI 怎么配、流水线卡住怎么办

### 外包边界（会议口径）

外包人员不得用 AI 写代码，但可用公司内部 skill 做 CI/CD 初始化（可申请）。外部版合规类须明写这条边界。

### 内部视角的 4 个盲区（Sarah QA 视角，攥写时规避）

1. **"大家都知道"假设**：不假设用户知道 Variables 是什么/在哪找/谁有权改。每条操作从"你手上有什么"出发。
2. **"显而易见的副作用"缺失**：改 CI 配置要补"改完会发生什么"（如触发下次 MR 流水线自动重跑）。
3. **"内部才有权限"的挫败感**：把"你无权做"改成"你该找谁、说什么"——如"遇到 X，联系平台管理员，告诉他需要 Y"。这不是脱敏，是视角转换（Sarah/Alice 共识，列为外部版攥写铁律）。
4. **排障的"内部日志路径"**：从"你看到的错误信息是什么"出发，不说用户看不到的东西（如 /var/log 内部日志）。

### 外部版攥写铁律（Sarah/Alice 共识，升格为铁律）

- **安全脱敏铁律（Alice #3）**：外部版**不提"无鉴权+CORS 全开"**——这句话本身就是安全漏洞描述。外部版写"gitlab-management 服务地址和访问权限由平台管理员提供"，不暴露服务自身安全状态。
- **视角转换铁律**：外部用户不需要知道 Variables 在哪/谁有权限改，他们需要知道"我要什么 → 找谁 → 说清楚什么"。
- **升级路径铁律（Alice #5）**：每条知识结尾加"如果本条无法解决你的问题，升级到 [角色]"——让外部用户知道碰到边界时找谁。

> 🔍 **批注3（外部版铁律与内部版四铁律的关系）**：外部版新增了3条铁律（安全脱敏/视角转换/升级路径），但第七节说"继承改造方案四铁律"。需明确关系——是 4+3=7 条铁律并行，还是 3 条外部版铁律覆盖了内部版某些铁律？建议明确：内部版四铁律（唯一事实来源/可执行性优先/适用范围显式声明/零矛盾）**全部继承**，外加 3 条外部版特有铁律，共 7 条。其中"视角转换铁律"实质是"可执行性优先"在外部版的具体化——内部版要求"可执行"（给路径），外部版进一步要求"可找到人+说什么话术"。

> 🔍 **批注4（升级路径铁律与规范 Troubleshooting "无效怎么办"的关系）**：升级路径铁律要求每条知识结尾加升级路径，规范 Troubleshooting 必含项也有"无效怎么办"——两者一致但适用范围不同：规范的"无效怎么办"仅限 Troubleshooting 类，外部版铁律要求**所有类型**（含 FAQ、Policy）都加升级路径。这个扩展合理——外部用户在任何场景碰到边界都需要知道找谁。建议在攥写时对 FAQ 和 Policy 类也统一补升级路径，作为 frontmatter 或结尾固定段。

### 排障框架（外部版，Sarah #4 具体化）

外部版排障从 GitLab UI 用户可见状态出发，四步：
1. 你在 GitLab 看到什么状态（failed / blocked / manual）
2. 你看到的具体错误提示是什么（精确引用 UI 文字）
3. 你能做什么（重试 / 催审批 / 改配置）
4. 什么时候该找人（升级路径）

## 四、外部版结构设计

### 目录决策

**平级建 `知识库-外部版/`**（不在 `知识库/` 内嵌）：避免共享外部版时连带暴露内部文件。现有 `知识库/` 定位"内部运维手册"保留不动；外部版独立组织，引用内部版作事实来源。

> 分目录而非"同目录加 audience 标签过滤"的理由：外部版的组织轴（问题分类）与内部版（角色/层级）根本不同，混在一个目录会让两套结构互相干扰，检索/导航都乱。
> 平级而非内嵌的理由（Alice）：内嵌会在分享外部版时连带暴露内部文件，平级隔离更安全。

### 外部版结构（按规范四类组织，非纯 FAQ）

外部用户也有多步骤操作（如"接 CI"是个 Procedure 不是一句话 FAQ），故按规范四类直接组织：

```
知识库-外部版/
├── README.md                         导航 + 外部用户前置条件
├── 00-前置条件.md                     外部用户接入前需要什么
├── 10-接入类.md                        怎么接 CI/怎么拿 API Key/能用什么模型（Procedure+FAQ 混合，脱敏）
├── 20-发版进度类FAQ.md                发版到哪了/卡在谁/怎么验证上线（高频一句话）
├── 30-排障类Troubleshooting.md        流水线失败/审批不出现/部署失败
└── 40-合规类Policy.md                 能不能用 AI/外包边界
```

> 🔍 **批注5（10-接入类 Procedure vs FAQ 命名不一致）**：第四节目录写 `10-接入类Procedure.md`，第五节篇目写 `10-接入类FAQ.md`，第六节迁移映射也写 `10-接入类FAQ`——三处不一致。接入 CI 是多步骤操作（建项目→写 .gitlab-ci.yml→配变量→触发验证），符合 Procedure 类型；但其中"能用什么模型""怎么拿 API Key"更像 FAQ。建议：文件名统一为 `10-接入类.md`，frontmatter `type: procedure` + `secondary_type: faq`（混合类型，参考内部版场景05的 `secondary_type` 方案）；或拆成两篇——接入 Procedure 一篇（多步骤）+ 模型/AI FAQ 一篇（高频一句话）。
>
> ✅ **已采纳**：采用方案一——文件名统一为 `10-接入类.md`，frontmatter `type: procedure` + `secondary_type: faq`。已重命名交付文件并加 `secondary_type: faq`。第五/六节篇目与迁移映射中的旧名（10-接入类FAQ）统一改为 `10-接入类`。

### 攥写规则对照（每类必含项）

| 类型 | 必含项 | 外部版落点 |
|---|---|---|
| FAQ | 典型问法 / 标准答案一句话 / 补充链接 | 接入类、发版进度类 |
| Troubleshooting | 错误现象(精确引用) / 适用环境 / 诊断步骤 / 解决步骤 / 无效怎么办 | 排障类 |
| Policy | 适用范围 / 政策结论 / 条件例外 / 违反后果 / 负责人日期 | 合规类 |
| Procedure | 触发条件/输入信息/步骤清单/输出结果/预估耗时 | 外部版一般不写 Procedure（内部已覆盖）；如需则脱敏 |

### 攥写要点（落实 Sarah 的盲区规避）

- **FAQ 标题用用户原话**：不用"审批门禁机制说明"，用"我的发版为什么被卡住了？"
- **每条操作从"你手上有什么"出发**：不假设用户知道内部概念
- **补副作用**：改完会发生什么
- **"无权做"→"找谁说什么"**：不堆挫败步骤
- **排障从用户可见错误出发**：不引用内部日志路径

## 七、质量要求（铁律关系明确）

> 🔍 **批注3 已采纳**：明确关系——内部版四铁律（唯一事实来源/可执行性优先/适用范围显式声明/零矛盾）**全部继承**，外加 3 条外部版特有铁律（安全脱敏/视角转换/升级路径），共 7 条。其中"视角转换铁律"是"可执行性优先"在外部版的具体化：内部版要求"可执行"（给路径），外部版进一步要求"可找到人+说什么话术"。

继承内部版四铁律：

1. **唯一事实来源**：外部版不重写真值，引用内部版；内部版是唯一事实来源。
2. **可执行性优先**：FAQ 答案一句话能答清；Troubleshooting 步骤可执行；禁模糊词（"联系相关负责人"等）。
3. **适用范围显式声明**：每条标适用用户/环境；外包边界显式。
4. **零矛盾**：外部版结论与内部版一致，不引入冲突。

外加外部版 3 条特有铁律（见第三节）：

5. **安全脱敏**：不提"无鉴权+CORS 全开"等安全漏洞描述。

## 八、风险点

1. **脱敏过度失真**：脱敏后用户仍需可执行——"找平台管理员"要附"告诉他需要 Y"，不能只剩"联系运维"。
2. **内外版不同步**：内部版改了外部版没跟——外部版引用要标来源文件+节锚，便于双向校验。
3. **外部用户画像偏差**：初判画像可能不全，建议外部版上线后收集"被问超过5次"的问题持续沉淀（规范 FAQ 触发条件）。

> 🔍 **批注8 已采纳**：FAQ 首版基于**预判频率**而非实际跟踪。外部版首版的 FAQ 标注"已验证高频"（来自内部版运维经验/README 入口）vs"预判高频"（待验证）。后续按实际"被问超过5次"数据调整。已在各 FAQ 条目标注来源（如"卡住了"来自产品经理篇=已验证高频）。
4. **外包边界误读**：合规类须精确——外包禁用 AI 写代码，但可用内部 skill 做 CI/CD 初始化，边界要写清。

> 🔍 **批注8（FAQ 初始频率假设）**：规范要求 FAQ 用于"被问了超过5次"的问题，但外部版首版是基于**预判频率**而非实际跟踪频率。风险点3 提到"上线后收集'被问超过5次'的问题持续沉淀"——方向对，但建议首版也标注哪些 FAQ 是"已验证高频"（来自内部版运维经验）vs"预判高频"（待验证），方便后续按实际数据调整。来源可参考内部版 README 的"按场景快速入口"——那些被列入口的说明已是高频。
