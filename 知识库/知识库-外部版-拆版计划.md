# 外部知识库拆版计划（AI 版 / 人类版）

> 主导：@Cindy。本文件是采纳专家批注 + 全员讨论后的定稿，供专家二审。OK 后全量推：AI 版 6 篇（按问题分类，已完成 QA 通过）、人类版 5 篇（按用户旅程，结构见 §四）。
> 配套：迁移映射（@Alice）、QA（@Sarah）。

## 一、为什么拆

现在每篇外部版同时背两个目标，互相打架：
- **喂 DEAP 知识集 / RAG**：要结构化 frontmatter、FAQ 一问一答、chunk 短而自包含、去叙事过渡
- **给人读**：要连贯叙事、导读目录、自然语气、去机械标签

结果是 frontmatter 对人是噪音、叙事过渡对 AI chunk 是干扰、"适用范围/违反后果"标签人读着生硬——即 @kare-scott 说的"读起来拗口"。

## 二、两个版本的定位

| 维度 | AI 版（`知识库-外部版-AI/`） | 人类版（`知识库-外部版-人类/`） |
|---|---|---|
| 读者 | DEAP 知识集 / RAG 检索 / agent 调用 | 人（新员工/外包/业务方/PM）从头读或跳读 |
| 结构 | 每条知识独立 chunk，自包含 | 连贯文档，章节叙事衔接 |
| frontmatter | 保留并强化（检索元数据 + agent 路由过滤） | 挪文末附录（保留溯源，不打断阅读） |
| 表达 | 短段落、明确小标题、去口语铺垫 | 自然语言段落、导读、目录树 |
| 标签 | 保留 `适用范围/政策结论/违反后果` 等结构化标签 | 改写成自然语言，去掉机械标签 |
| 代码示例 | 保留（机器友好） | 保留（人也看） |
| 导航 | 不放"你是谁看哪篇"导航表（检索不靠目录）；路由靠 frontmatter 的 audience/layer/flow 字段 | 保留"你是谁看哪篇""找谁对照表" |

> 说明：AI 版去掉导航表是对的（RAG 检索不靠目录），但 frontmatter 里的 `audience`/`layer`/`flow` 对 agent 调用仍有路由价值（按用户身份过滤 chunk）——这些字段在 AI 版保留并强化。导航表（给人读的入口）和 frontmatter 路由字段（给机器过滤的元数据）不混淆。人类版 frontmatter 不直接删——`source`/`owner`/`updated` 对人有溯源价值（知道信息哪来、谁维护、多旧），挪文末附录既不干扰阅读又保留溯源。

## 三、AI 版结构规范

每篇骨架：
```
---
audience: [...]      # 检索过滤用
layer: ...           # 检索过滤用
flow: [...]          # 检索过滤用
source: [...]        # 事实溯源
type: ...            # faq/procedure/troubleshooting/policy
owner: ...
updated: ...
---

# <标题：用户问题原话最好>

## <chunk 1：一个独立知识点>
**适用范围**：...
**结论/步骤**：...
**条件与例外**：...
**违反后果/升级路径**：...

## <chunk 2：另一个独立知识点>
...（每条 ## 独立成 chunk，不依赖上下文）
```

**chunk 必含字段按 type 区分**（不硬凑——并非每种 type 都有全部字段）：
| type | 必含字段 | 可选字段 |
|---|---|---|
| procedure | 适用范围/步骤/条件/升级路径 | 触发后行为 |
| faq | 典型问法/标准答案/升级路径 | 条件与例外 |
| troubleshooting | 错误现象/适用环境/诊断/解决/无效怎么办 | 常见坑 |
| policy | 适用范围/政策结论/条件与例外/违反后果/负责人 | — |

> procedure 不加"违反后果"，faq 的"条件与例外"不适用就省。

要点：
- 每个 `##` 是一个自包含 chunk——检索命中后不读前后文也能懂
- 去掉"你不需要管的""咱们"等叙事过渡
- FAQ 用"典型问法"做小标题（用户搜的就是这句话）
- 不放目录树/导航表（检索不靠目录）
- **chunk 粒度**：单个 chunk 建议 200-500 字；超长（如排障类 MR 冲突 5 步 git）拆 `###` 子 chunk；过短（<50 字）并入相邻 chunk——给 RAG embedding 合理上下文窗口
- **chunk 间"参见"**：参见指向**相关主题**（如 build 失败 → 参见状态解读，"看完了想深入"的跳转），**不指向前置知识**（若 chunk B 不读 chunk A 就看不懂，B 不自包含，应把 A 关键信息内联进 B）。参见是补充不是依赖。

## 四、人类版结构规范

> **@kare-scott 指引（2026-07-31）**：人类版**不用遵照知识库文档规范**（frontmatter/type/必含项那些约束是给 AI 版和内部版的），可以**多参考内部版（`知识库/`）的结构和内容**重新组织；不用口语化，但要让人轻松看明白。也就是说：人类版不受规范枷锁，目标是"人读着顺、看得懂"，结构上向内部版靠拢。

### 文档组织：按用户旅程，不按问题分类（全员讨论共识 2026-07-31）

**关键决策**：人类版的**文档划分**也参考内部版——不沿用外部版"接入/发版/排障/合规"4 篇按问题分类，而是**按用户旅程**重新组织成 5 篇。

为什么不按问题分类：AI 版和事实底稿按问题分类是对的（RAG 检索需要结构化分类），但人类版目标是给人读，人按"我在做什么"找信息，不按"这是 procedure 还是 faq"找。

为什么不按角色分（内部版 20-角色操作指南 的方式）：外部用户角色比内部少，且内容大量重叠（开发者和 PM 都要查发版进度、都要懂合规），按角色分会重复。内部版按角色分是因为各角色职责差异大，外部用户不是。

**人类版 5 篇结构（全员共识：Cindy/Alice/Sarah/Candy）**：
1. **README（导读手册）**：全局概览（这套 CI/CD 怎么运转）+ "你是谁看哪篇"导航 + 联系人总表（参考内部版 00-背景与术语的全局认知思路）
2. **新手接入指南**：前置条件 → 接 CI → 改配置 → 本地验证 → Dockerfile/compose（合并现有 00+10，新手一口气读完整条接入链路；参考内部版 30-操作场景 场景01/02/06）
3. **日常开发与发版**：提交后流水线 → 查进度 → 发版配合 → 验收 → 回滚 → MR 不能合（现有 20 的 FAQ 按使用频率重排成叙事流程，不是 Q1-Q8 机械堆砌；参考内部版 20-角色操作指南 + 30-操作场景 场景03/04/05）
4. **故障排查**：排障四步法 → 6 个排障条目（已比较场景式，改动最小）
5. **合规须知**：9 条政策按"AI 使用"和"CI/CD 安全"两大段叙述（不用 P1-P9 机械编号；参考内部版 03-合规要求）

**对映射表的影响**：KB-ID 不变（48 块仍标 ID），只改映射表"人类版章节"列的目标——如 KB-00-02 从"00-前置条件.md"变成"新手接入指南.md §前置条件"。三版同步不受影响。

**保留项**：找谁对照表是人类版最高频查阅内容，放日常开发与发版篇末尾 + README 各一份（README 那份作全局总表）。

**参考内部版的结构特点**（人类版可借鉴）：
- `## 目标`：开头一段说清"读完这篇你能干嘛"，给人建立预期（内部版每篇都有）
- `## 你做什么`：用 bullet 列出这篇涉及的动作（接 CI/改配置/触发流水线/查结果），人一眼看到全貌
- `## 前置条件`：开始前要有什么（权限/变量/联系人），避免读到一半卡住
- `## 操作步骤`：编号步骤（1. 2. 3.），叙事式写法，自然连贯
- `## 注意事项`：易踩的坑、不能碰的边界
- 全局：内部版 00 目录有"CI/CD 总体架构 + 术语表"给人全局认知——人类版 **README（导读手册）** 中放一段"这套 CI/CD 怎么运转"的全局概览，不放进每篇文件（每篇只管自己的主题）

每篇骨架（参考内部版，可自由调整）：
```
# <标题>

> 一句话导读：这篇讲什么、读完能干嘛

## 这篇讲什么 / 你能干嘛（=内部版的"目标"）
（自然语言，1-3 句）

## 你要做什么（=内部版的"你做什么"）
- 动作1
- 动作2
（bullet 列全貌）

## 开始前确认（=内部版的"前置条件"）
- 权限/变量/联系人

## 怎么做（=内部版的"操作步骤"）
### 1. ...
### 2. ...
（编号步骤，叙事式，自然连贯）

## 注意事项（=内部版的"注意事项"）

## 找谁（如本篇涉及）
（保留找谁对照表，人需要）

## 下一步
（自然语言指向相关篇）

## 附录：本篇信息
- 来源：`source`
- 维护人：`owner`
- 更新日期：`updated`
```

要点：
- **不受文档规范约束**：不要 frontmatter、不要 type、不要"适用范围/政策结论/违反后果"等机械标签——这些是 AI 版的事。人类版按内部版式自然组织
- **frontmatter 的溯源信息挪文末附录**（`## 附录：本篇信息`，列表形式列 source/owner/updated）——保留溯源但不打扰阅读
- 加导读 + 必要时目录（人读要入口）
- 章节间加过渡句——过渡句限于"上文→下文的逻辑关联"（如"接完 CI 后，你可能还想知道怎么改配置"），**功能性但不公文腔**，不加文学性铺垫
- **每个章节第一句最好是结论**（如"审批门禁不能绕过"），再展开——合规类这种政策型尤其重要，扫描阅读能抓到允许/禁止
- **语气基调：工程指南风格，不是日记**——规范书面语，让人轻松看明白，但**不口语化、不聊天化**。具体要求（@kare-scott 2026-07-31）：
  - **不要人称代词**：不出现"你""我"等——用**角色名替代**（如"开发者""产品经理""运维""外包人员"）。例：不写"你提交到 feature 分支"，写"开发者提交到 feature 分支"；不写"你要记住"，写"需注意"。
  - **不要日常聊天语言**：不写"过后就再也看不到了""别慌""一定要记住"这类——用工程陈述。例："Key 明文仅首次返回，需妥善保存，此后无法再次获取"。
  - **是工程指南不是对话**：信息完整、表述清晰、语气中性专业，读着不费劲但不唠嗑。
  - 语气标尺：**规范、专业、客观**——段落/陈述/完整句，主语用角色名，不用第二人称。
- **条目编号去英文字母前缀**（@kare-scott 要求，三版统一）：排障类 T1→1、合规类 P1→1、发版FAQ Q1→1（纯数字）。交叉引用同步改（"见排障类 T1"→"见排障类第1条"）。这条同时适用于现有版、AI 版、人类版，拆版改写时一并统一。
- **内容来源**：人类版不只从外部版事实底稿派生，也可**回引内部版的结构和叙事方式**重新组织（@Alice 映射表的 source 列会标注"内部版结构参考"）。事实仍以脱敏后的外部版为准，结构/叙事向内部版靠拢。

### AI 版小样（`10-接入类.md` 节选）

```markdown
---
audience: [新员工, 外包, 业务线开发者]
layer: Repo
flow: [分支MR]
source: [内部场景01/02, aisix-mgmt接口, 合规要求]

secondary_type: faq
owner: 团队Lead/业务线开发者

# 接入类：怎么接 CI、怎么拿 AI Gateway API Key

## 怎么把项目接入公司 CI/CD

**适用范围**：有新业务仓库、需接入公司流水线的开发者。

**步骤**：在业务仓库根目录创建 `.gitlab-ci.yml`，引用公司通用工作流：
\`\`\`yaml
include:
  - project: 'platform/cicd-template'
    ref: master
    file: 'workflows/app-workflow.yml'
variables:
  BUILD_TOOL: "mvn"    # 必填：mvn / gradle / pnpm
\`\`\`

**条件**：团队名 `TEAM` 和镜像仓库 `SERVICE_REPOSITORY` 若团队 Lead 已在团队 Variables 配好，此处不填；没配找团队 Lead（见前置条件）。

**触发后行为**：提交 feature/fix 分支 → 自动触发分支流水线 build→test→dev 部署→发起 MR。

**升级路径**：`.gitlab-ci.yml` 引用报错 → 检查 `project`/`ref`/`file` 路径 → 不行找团队 Lead。

## 接完怎么确认接成功

**判断标志**：GitLab → 项目 → Build → Pipelines 看到新流水线；整体 passed = 成功跑完 build/test/dev；build Job 出现且变绿 = `BUILD_TOOL` 配对（没出现 = 没设或值不对）。

**升级路径**：流水线变红 → 见排障类第1条（build 失败）。

## 怎么拿公司内部 AI 模型的 API Key

**适用范围**：要用公司内部 AI 模型的人员。

**步骤**：找平台管理员走 AI Gateway 入驻（提供邮箱、团队名、姓名、要用的模型），平台管理员一键入驻生成 Key。

**条件**：Key 调用的是公司内部模型（如 DeepSeek），不允许用公网 Claude/Anthropic（数据出口合规，见合规类）。

**Key 保管**：明文只在首次返回，务必保存；之后无法再看明文；丢了找平台管理员重生成。

**升级路径**：默认模型不满足 → 问平台管理员可用模型；Key 丢 → 找平台管理员重生成（旧作废）。
```

> 小样中"怎么拿 API Key"chunk 没有"违反后果"字段——印证上文：procedure 类 chunk 不需要"违反后果"，只需"升级路径"。

### 人类版小样（`10-接入类.md` 节选）

```markdown
# 项目接入公司 CI/CD 与内部 AI 模型 API Key 获取

> 本篇面向需要将新项目接入公司 CI/CD 的开发者，以及需要使用公司内部 AI 模型的人员。阅读后可完成项目流水线接入和 API Key 获取。

## 适用读者

本篇适用于持有新业务仓库（或接手未接入 CI 的仓库）的开发者，以及需要使用公司内部 AI 模型的人员。平台维护人员请参阅内部版。

## 项目接入 CI/CD

### 接入步骤

在业务仓库根目录创建 `.gitlab-ci.yml`，引用公司通用工作流（无需从零编写流水线）：

\`\`\`yaml
include:
  - project: 'platform/cicd-template'
    ref: master
    file: 'workflows/app-workflow.yml'
variables:
  BUILD_TOOL: "mvn"    # 必填：mvn / gradle / pnpm，决定构建方式
\`\`\`

`BUILD_TOOL` 需填写项目实际使用的构建工具（mvn/gradle/pnpm）。团队名（`TEAM`）和镜像仓库（`SERVICE_REPOSITORY`）若团队 Lead 已在团队 Variables 中配置，此处无需填写；未配置则联系团队 Lead 补充（前提条件见「前置条件」）。

### 触发后行为

提交至 feature/fix 分支后自动触发分支流水线：build → test → dev 部署 → 发起 MR 代码评审。无需手动触发，push 即触发。

### 接入验证

提交后进入 GitLab → 项目 → Build → Pipelines，可查看新流水线。流水线整体 passed 表示 build/test/dev 部署全部通过。重点关注 build Job 是否出现且变绿：出现表示 `BUILD_TOOL` 配置正确；未出现通常表示该变量未设置或值不正确。

流水线失败（红色）时，参见「排障类」第1条（build 失败处理）。

## 内部 AI 模型 API Key 获取

### 获取方式

需要使用公司内部 AI 模型时，联系平台管理员走 AI Gateway 入驻流程。需提供：邮箱、团队名、姓名、所需模型。平台管理员通过 AI Gateway 一键入驻生成 Key。

### 注意事项

1. **模型限制**：Key 仅可调用公司内部模型（如 DeepSeek），**禁止**配置公网 Claude 或 Anthropic API（数据出口合规要求，详见「合规类」）。
2. **Key 保管**：API Key 明文仅在入驻时返回一次，需妥善保存；后续无法再次查看明文。Key 丢失需联系平台管理员重新生成（旧 Key 作废）。

### 升级路径

- 默认模型不满足需求 → 联系平台管理员确认可用模型
- Key 丢失 → 联系平台管理员重新生成
```

## 六、对比说明（给 owner 判断）

- **AI 版**：每条 `##` 是一个自包含 chunk，带 frontmatter，去叙事——检索命中后直接可用，不"拗口"因为它不追求连贯。
- **人类版**：frontmatter 挪文末附录，导读+连贯叙事+工程陈述+"找谁"表——从头读到尾通顺。
- **内容等价**：同一事实两版都有，只是表达形态不同。
- **现有版命运**：作为"事实底稿"保留，两版从它派生。
- **双版等价性验证标准**：只核对**事实陈述**（步骤、规则、后果）一致，不要求元数据（frontmatter）和叙事层（导读/过渡句）等价——那些是各版各自的增值。**脱敏等价**也必须验证：两版暴露给用户的信息边界必须一致，不能 AI 版多暴露一个内网变量名而人类版没有（或反之）。脱敏是事实层的一部分。
