# 场景 05：审批门禁与注意事项

## 目标

集中说清本仓库审批门禁的**真实机制**（stage 偏序，非 needs）、审批层级、什么算"绕过门禁"、怎么人工核查门禁完整性。这篇是各角色篇"审批边界"的参考底座。

## 门禁的真实机制：靠 stages 顺序，不靠 needs

这是全库最关键的一条事实，反复出现在各篇——这里集中讲透：

```yaml
# cicd-template/workflows/app-workflow.yml 的 stages: 列表（门禁载体）
stages:
  - build
  - ...
  - create-release
  - approval          # ← 审批 stage，排在 deploy-prod 之前
  - deploy-prod       # ← 生产部署 stage
  - finalize-release
```

- **机制**：GitLab CI 的语义是"同一 stage 内所有 Job 完成后才进下一 stage"。`approval` stage 排在 `deploy-prod` 之前 + 两个审批 Job 都 `when: manual`，构成**时序门禁**——审批不点，流水线停在 approval，进不了 deploy-prod。
- **不是靠 needs**：`deploy-prod`（`argo-deploy.yml`）**无 needs 字段**；`deploy-container-prod`（`docker-deploy.yml`）的 needs 只有 `[build-container]`。两者的 needs **都不含审批 Job**。门禁靠 stage 顺序，不靠 needs DAG 可达性。

> 注意：这意味着用 needs DAG 可达性去判审批门禁会**漏判**——deploy-prod 压根没 needs 审批，光看 needs 看不出门禁在不在。判门禁要看 `stages:` 偏序，即 approval stage 是否排在 deploy-prod 之前。

## 审批层级（会议口径 + 代码实现）

```text
MR Approve       团队层      开发者互相审核（GitLab MR Approve 功能）
Team 层 Pro       团队层      团队自定义 approval Job（会议口径，代码无统一实现）
安全层 Pro        安全层      appsec_approval Job（比对 $APPSECURITY_APPROVERS，代码已实现）
BPM Pro          —          待定（会议口径，暂不用，代码未实现）
发版 Approve      发版层      approval Job（比对 $RELEASE_MANAGER，职责分离，代码已实现）
   ↓
deploy-prod       生产部署    ArgoCD 滚动 / VM Docker Compose
```

两个已实现的审批 Job（`stages/approval.yml`）：

| Job | 校验逻辑 | 失败信息 |
|---|---|---|---|---|
| `approval` | `$GITLAB_USER_EMAIL != $RELEASE_MANAGER`（发版人不能审批自己） | "Fail: RELEASE_MANAGER should not run this job" |
| `appsec_approval` | `$GITLAB_USER_EMAIL` 在 `$APPSECURITY_APPROVERS` 列表（逗号分隔，小写比对） | "User X is NOT an approver" |

职责分离：`approval` 校验"触发人 ≠ Release Manager"；`appsec_approval` 校验"触发人在安全审批人列表"。两条审批不能兼任。

## 什么算"绕过门禁"（违规行为清单）

| 违规行为 | 怎么做 | 后果 | 适用环境 | 无效怎么办 |
|---|---|---|---|---|
| stage 后移 | 把 `approval` 移到 `deploy-prod` 之后 | 部署先于审批，门禁失效 | 全环境 | 拦截发版，恢复 stage 顺序后重新触发流水线，走安全层复查 |
| 删 approval stage | 从 `stages:` 列表删 `approval` | 审批 Job 无 stage 可落，门禁消失 | 全环境 | 拦截发版，恢复 approval stage 后重新触发，走安全层复查 |
| 删审批 Job | 删 `appsec_approval` 或 `approval` | 安全层/发版层审批缺失 | 全环境 | 拦截发版，恢复审批 Job 后重新触发，走安全层复查 |
| 换条件域 | 把审批 Job 的 extends 从 `.release_rules` 改成 `.default_dev_fix_rules` | 审批 Job 在非发版流程误现或发版时不现 | 全环境 | 拦截发版，恢复 `.release_rules` 条件域后重新触发，走安全层复查 |
| 清空审批人 | `APPSECURITY_APPROVERS` 清空 | 安全审批永远失败（死锁）或被设为空绕过 | 全环境 | 拦截发版，在 CI/CD → Variables 恢复审批人列表后重新触发，走安全层复查 |
| needs 装门禁 | 给 deploy-prod 加 `needs: [appsec_approval]` | **无效**——本仓库门禁靠 stage 顺序，加 needs 不改变 stage 偏序，反而误导 | 全环境 | 删除错误的 needs 声明，门禁机制以 stage 顺序为准，无需修改 |

任一行为成立 = 门禁被绕过，**拦截发版**并走安全层复查。


## 流程要素

- **触发条件**：发版流水线（tag）触发后，流水线到达 `approval` stage 时。
- **输入信息**：`workflows/app-workflow.yml` 的 `stages:` 列表、`stages/approval.yml` 的 Job 定义、`RELEASE_MANAGER` 和 `APPSECURITY_APPROVERS` 变量值。
- **输出结果**：审批通过则流水线进入 `deploy-prod` stage；审批未通过则流水线停在 `approval` stage（`blocked` 状态）。
- **预估耗时**：审批响应约 1-4 小时（取决于审批人在线时间）。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于发版流水线（tag 触发）的审批门禁。分支/MR 流水线和主干流水线不涉及审批门禁（无 `approval` stage）。

## 操作步骤

### 1. 人工核查门禁（发版前）

检查目标仓库 `workflows/app-workflow.yml`：
- `stages:` 列表里 `approval` 在 `deploy-prod` 之前。
- `stages/approval.yml` 里 `approval` 和 `appsec_approval` 两个 Job 存在、`when: manual`、`extends: [.approval|.appsec_approval, .release_rules]`。
- GitLab CI/CD Variables 里 `RELEASE_MANAGER`、`APPSECURITY_APPROVERS` 非空且有效。

### 2. 核查"绕过门禁"违规行为

对照上节"违规行为清单"逐条查：
- `approval` stage 有没有被后移到 `deploy-prod` 之后？
- 审批 Job 有没有被删、extends 有没有被换成非 `.release_rules`？
- 审批人变量有没有被清空？

任一命中 = 门禁被破坏，拦截发版走安全层复查。

## 代码示例

```yaml
# 正确的审批 Job 装配（stages/approval.yml，不要破坏）
approval:
  stage: approval              # 须在 deploy-prod 之前
  when: manual
  allow_failure: false
  dependencies:
    - set-release-manager       # 接收 .pre 阶段记录的触发人邮箱
  extends:
    - .approval
    - .release_rules            # 仅 tag 流水线出现，不要换成 dev_fix

appsec_approval:
  stage: approval
  when: manual
  allow_failure: false
  extends:
    - .appsec_approval
    - .release_rules
```

## 注意事项

- **门禁靠 stage 顺序，不是 needs**：这是全库最易误解的一条。靠 needs 判门禁会漏判（deploy-prod 无 needs 审批）。
- **`set-release-manager` 的作用**：`preparations.yml` 的 `.pre` 阶段 `set-release-manager` Job（`when: always`）记录触发人邮箱到 artifact，供 `approval` 校验职责分离。删它会导致职责分离失效。
- **审批人变量必填**：`APPSECURITY_APPROVERS` 清空 = 安全审批死锁；`RELEASE_MANAGER` 为空 = 发版审批失能。换人先加后删。
- **BPM Pro 暂未实现**：会议提到的 BPM Pro 是"待定，暂不用"，代码无实现，别当已生效。
- **门禁是合规底线**：绕过门禁 = 违规，不只是配置错误。发版前务必按本篇步骤人工核查。
