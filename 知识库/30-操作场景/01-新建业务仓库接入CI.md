# 场景 01：新建业务仓库并接入 CI

## 目标

从 0 到 1：建一个 GitLab 项目 → 写 `.gitlab-ci.yml` include Common 层 → 配变量 → 触发首条分支流水线验证接入成功。

## 流程要素

- **触发条件**：新业务仓库需接入 CI/CD，从零创建 GitLab 项目并触发首条流水线时。
- **输入信息**：GitLab Group（团队 namespace）ID、团队级变量（TEAM/SERVICE_REPOSITORY/BUILD_TOOL）、gitlab-management 服务地址、业务仓库 Git 远程地址。
- **输出结果**：业务仓库 .gitlab-ci.yml 接入 Common 层，首条分支流水线状态变 running，接入成功。
- **预估耗时**：建项目+写 .gitlab-ci.yml 约 10-20 分钟，首条流水线执行约 3-15 分钟（取决于构建工具和镜像大小）。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于新业务仓库首次接入 CI/CD。已接入仓库的配置修改见「场景 02」，流水线触发与查看见「场景 03」。

## 前置条件

- 平台管理员已部署 gitlab-management 服务（地址 `<gitlab-mgmt>`，见「平台管理员」步骤 0）。
- 团队 Lead 已建好 GitLab Group（团队 namespace），且配好 Group 级变量（`TEAM`、`SERVICE_REPOSITORY`、`BUILD_TOOL`，见「团队 Lead」步骤 1）。
- 你的邮箱在该 Group 有 Developer 以上权限。
- 若要用 AI 辅助生成接入文件：已在 `aisix-mgmt` 注册拿 API Key。

## 操作步骤

### 1. 建项目（或用已有项目）

平台管理员通过 projects 路由建项目并归入团队 namespace：

```bash
curl -X POST http://<gitlab-mgmt>/api/projects/ \
  -H "Content-Type: application/json" \
  -d '{"name": "my-service", "namespace_id": <团队Group的ID>}'
```

- 响应 `{id, name, path, web_url, visibility}`，记下 `id`（后续步骤用）和 `web_url`（Git 远程地址）。
- 详见「平台管理员」步骤 1。

### 2. 克隆仓库并创建 .gitlab-ci.yml

```bash
git clone <web_url>
cd my-service
```

在仓库根目录创建 `.gitlab-ci.yml`，最小内容（三必填变量 + include）：

```yaml
include:
  - project: 'platform/cicd-template'
    ref: master
    file: 'workflows/app-workflow.yml'

variables:
  SERVICE_REPOSITORY: "data-platform"   # 团队 namespace（与 Group 变量一致）
  TEAM: "data-platform"                  # 团队名（ArgoCD app-values 路径用）
  BUILD_TOOL: "mvn"                      # 必填：mvn / gradle / pnpm，决定构建方式
```

- `SERVICE_NAME` 默认取 `${CI_PROJECT_NAME}`（仓库名），**不用填**。
- 若 Group 级已配这三个变量，仓库级可省略（Group 级继承）；仓库级优先于 Group 级。
- `BUILD_TOOL` 不设则 build 阶段不出现（条件 include，见「Common 层」的"条件-include构建工具动态选择"节）。

### 3. 补前置文件（按部署路径）

走 ArgoCD（K8s）：app-values 目录运维维护，你无需提供文件。
走 VM Docker Compose：你须在仓库提供 `Dockerfile` + `docker-compose.yml`（编写见「场景 06」）。



### 4. 提交 MR，触发首条分支流水线

```bash
git checkout -b feature/init-ci
git add .gitlab-ci.yml
git commit -m "init: 接入 CICD 模板"
git push -o merge_request.create origin feature/init-ci
```

推送到 feature 分支即触发**分支/MR 流水线**（build → test → dev 部署 → 集成测试 → MR Review）。

### 5. 验证接入成功

```bash
# 查流水线状态
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=running"
```

- 看到 pipeline 状态变 `running` → 接入成功，CI 开始执行。
- 若 `build` Job 没出现 → 检查 `BUILD_TOOL` 是否设了（最常见坑）。
- 若 include 报"file not found" → 检查 `include` 的 `project` 路径（应是 `platform/cicd-template`）和 `ref`。
- 流水线通过后由团队 Lead Review/Approve MR（见「团队 Lead」步骤 3）。

## 代码示例

见上方各步骤。一次性的脚本化接入：

```bash
# 建项目 + 拿 project_id
PID=$(curl -s -X POST http://<gitlab-mgmt>/api/projects/ \
  -H "Content-Type: application/json" \
  -d '{"name":"my-service","namespace_id":12}' | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

# 通过 files API 创建 .gitlab-ci.yml（替代手工编辑）
curl -X POST "http://<gitlab-mgmt>/api/files/$PID/create" \
  -H "Content-Type: application/json" \
  -d '{
    "file_path": ".gitlab-ci.yml",
    "content": "include:\n  - project: platform/cicd-template\n    ref: master\n    file: workflows/app-workflow.yml\nvariables:\n  SERVICE_REPOSITORY: data-platform\n  TEAM: data-platform\n  BUILD_TOOL: mvn\n",
    "branch": "feature/init-ci",
    "commit_message": "init: 接入 CICD 模板"
  }'

# 触发首条流水线
curl -X POST http://<gitlab-mgmt>/api/pipelines/ \
  -H "Content-Type: application/json" \
  -d "{\"project_id\": $PID, \"ref\": \"feature/init-ci\"}"
```

## 注意事项

- **`BUILD_TOOL` 最易漏**：接入后 build Job 不出现，99% 是没设 `BUILD_TOOL`。
- **include 路径**：`project` 必须是 Common 层仓库的真实路径（`platform/cicd-template`），团队 Lead 可告知准确路径。
- **只改 Repo 层**：本仓库 `.gitlab-ci.yml` 可改，Common 层（cicd-template）由平台团队维护，不要直接改。
- **别动 stages 顺序**：若自定义 Job，不要改 `stages:` 里 `approval` 与 `deploy-prod` 的先后（绕过审批门禁，见「场景 05」）。
- **本地验证**：推 MR 前可用 `gitlab-ci-local` 本地模拟（见「场景 02」）。
