# 场景 02：修改 CI 配置

## 目标

通过 gitlab-management files API 程序化修改业务仓库的 `.gitlab-ci.yml`（或任意配置文件），并在推送前本地验证语法与 include/extends 解析正确。

## 流程要素

- **触发条件**：已接入 CI 的业务仓库需要修改 .gitlab-ci.yml 配置时。
- **输入信息**：目标仓库 project_id、gitlab-management 服务地址、当前 .gitlab-ci.yml 的 last_commit_id。
- **输出结果**：更新后的 .gitlab-ci.yml 已提交到 feature 分支，本地验证通过，MR 已提交等团队 Lead Review。
- **预估耗时**：取文件+改内容+提交约 5-10 分钟，本地验证约 2-5 分钟。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于业务仓库 Repo 层的 CI 配置修改。不要用 files API 改 Common 层仓库——那是平台团队治理范围。

## 前置条件

- 已接入 CI（有 `.gitlab-ci.yml`，见「场景 01」）。
- gitlab-management 服务可用（地址 `<gitlab-mgmt>`）。
- 知道目标仓库 `project_id`。
- 你有本仓库 Developer 权限（能推 feature 分支）。

## 操作步骤

### 1. 取当前文件（拿 last_commit_id）

files API 的 `update` 用 `last_commit_id` 做乐观锁防并发覆盖，改前必须先 `get`：

```bash
curl -X POST "http://<gitlab-mgmt>/api/files/<project_id>/get" \
  -H "Content-Type: application/json" \
  -d '{"file_path": ".gitlab-ci.yml", "ref": "feature/update-ci"}'
```

- 请求 `GetFileRequest`：`file_path`、`ref` 默认 `main`（改 feature 分支则填 feature）。
- 响应 `FileResponse`：`{file_name, file_path, content, last_commit_id}`。**记下 `last_commit_id`**，下一步用。

### 2. 更新文件

把新内容 + 上一步的 `last_commit_id` 提交：

```bash
curl -X POST "http://<gitlab-mgmt>/api/files/<project_id>/update" \
  -H "Content-Type: application/json" \
  -d '{
    "file_path": ".gitlab-ci.yml",
    "content": "<新内容>",
    "branch": "feature/update-ci",
    "commit_message": "Update CI config"
  }'
```

- 请求 `UpdateFileRequest`：`file_path`、`content`、`branch`、`commit_message`。
- 服务端逻辑（`file_service.py`）：先 `get` 取当前 commit_id → 用 HTTP PUT 带 `last_commit_id` 提交 → 若期间文件被他人改过（commit_id 不匹配），GitLab 返回 409 冲突。
- 响应 `FileOperationResponse`：`{file_name, file_path, last_commit_id, message}`。更新后 `last_commit_id` 变化，下次改要用新值。

> **乐观锁冲突**：若返回 409/冲突，说明并发有人改了同一文件。重取最新 `get` 拿新 `last_commit_id`，合并后重试 `update`。

### 3. 本地验证（推荐，推 MR 前）

```bash
# 用 gitlab-ci-local 本地模拟执行（开源工具，需自行安装；它直接跑，会展开 include/extends 并报告错误，无单独 lint 子命令）
gitlab-ci-local

# 或调 GitLab CI Lint API 校验语法（只校验 YAML 语法，不展开 include）
curl -X POST "https://<gitlab>/api/v4/ci/lint" \
  -H "PRIVATE-TOKEN: <your_token>" \
  --data-urlencode "content@.gitlab-ci.yml"
```

### 4. 提 MR

本地验证通过后提 MR 走分支/MR 流水线，团队 Lead Review（见「团队 Lead」步骤 3）。

## 代码示例

见上方各步骤。Python 封装（取-改-更新）：

```python
import requests, json
BASE = "http://<gitlab-mgmt>/api"
PID = "<project_id>"
BRANCH = "feature/update-ci"

# 1. 取当前内容 + last_commit_id
cur = requests.post(f"{BASE}/files/{PID}/get",
    json={"file_path": ".gitlab-ci.yml", "ref": BRANCH}).json()
old_commit = cur["last_commit_id"]
content = cur["content"]

# 2. 改内容（示例：加一个变量）
if "BUILD_TOOL" not in content:
    content = content.replace("variables:\n", "variables:\n  BUILD_TOOL: \"mvn\"\n", 1)

# 3. 更新
requests.post(f"{BASE}/files/{PID}/update", json={
    "file_path": ".gitlab-ci.yml",
    "content": content,
    "branch": BRANCH,
    "commit_message": "add BUILD_TOOL"
})
```

files API 还有 `create`（新建文件）、`delete`（删文件）、`list`（列目录）三个端点，用法同 `get`/`update`，都走 `POST /api/files/<project_id>/<op>`。

## 注意事项

- **乐观锁必带 `last_commit_id`**：`update` 前务必先 `get`。不带或带旧值会冲突失败。这是设计行为，防并发覆盖。
- **只改 Repo 层**：不要用 files API 改 Common 层（cicd-template）仓库——那是平台团队治理范围。
- **别动 stages 顺序**：若改 `.gitlab-ci.yml` 时动了 `stages:` 列表，确认 `approval` 仍在 `deploy-prod` 之前。自定义部署 Job 的 `needs` 只填构建依赖（如 `build-container`），审批靠 stage 顺序不靠 needs。完整门禁机制见「场景 05」。
- **本地 lint 子命令不存在**：`gitlab-ci-local` 直接运行即模拟，不需也不支持 `lint` 子命令。
- **API 无鉴权**：files API 可改任意文件，务必确保 gitlab-management 只内网可访问。
