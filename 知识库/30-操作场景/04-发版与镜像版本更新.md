# 场景 04：发版与镜像版本更新

## 目标

完整走一次发版：主干 UAT 验证通过 → 打 tag → 审批 stage → 改 ArgoCD 镜像版本 → 生产部署，并守好审批门禁。


## 流程要素

- **触发条件**：主干流水线 UAT 验证通过，需将已验证镜像发布到生产环境时。
- **输入信息**：目标业务仓库 `project_id`、ArgoCD 部署文件路径 `app-values/<env>/<team>/<service>/<env>-<region>.yaml`、主干流水线镜像 tag（`$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`）、`RELEASE_MANAGER` 和 `APPSECURITY_APPROVERS` 变量已配置。
- **输出结果**：生产环境部署成功（ArgoCD 滚动更新或 VM Docker Compose 重启），发版流水线 `deploy-prod` 状态为 `success`。
- **预估耗时**：镜像版本更新约 1-3 分钟（单次 API 调用），审批响应约 1-4 小时（取决于审批人在线时间）。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本场景适用于走 ArgoCD（K8s）部署路径的发版。若业务走 VM Docker Compose 部署路径（`deploy-container-prod`），不走 argocd API——tag pipeline 的 deploy Job 会 SSH 上目标机直接 `docker compose down/up`，见「场景 06」。

## 前置条件

- 主干流水线已合主干，UAT 部署且集成测试通过（不能发未经验证的版本）。
- gitlab-management 服务可用（地址 `<gitlab-mgmt>`）。
- 知道目标业务仓库 `project_id` 和 ArgoCD 部署文件路径 `app-values/<env>/<team>/<service>/<env>-<region>.yaml`。
- 审批人在线：`RELEASE_MANAGER`（发版审批人）+ `APPSECURITY_APPROVERS`（安全审批人列表）已配好（见「安全团队 AppSec」步骤 1）。
- 你有运维权限（能改 app-values、点 manual job）。

## 操作步骤

### 1. 确认 UAT 通过

发版前确认主干流水线（UAT）已 success——这是 Build Once Promote Many 原则的起点：发版复用主干已构建并经 UAT 验证的镜像，不重新构建。

### 2. 打 tag，触发发版流水线

```bash
git tag v1.2.3
git push origin v1.2.3
```

推 tag 触发**发版流水线**（tag，`CI_COMMIT_TAG`）：
```text
tagging → approval stage（等审批）→ deploy-prod stage（生产部署）→ finalize-release
```

镜像 tag 格式（由 `docker.yml` 定义）：`$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`，如 `v1-2-3-134361`。

### 3. 确认审批门禁未被动（发版前）

检查目标仓库 `workflows/app-workflow.yml` 的 `stages:` 列表（门禁机制与违规行为清单见「场景 05」）：
- `approval` stage 排在 `deploy-prod` 之前。
- `approval` / `appsec_approval` 两个 Job 存在且 `when: manual`、`extends ... .release_rules`。

若门禁被破坏（stage 被后移、Job 被删、条件域被换），**拦截发版**，走安全层复查。

### 4. 审批（approval stage）

流水线跑到 `approval` stage 会 `blocked`，等两个 manual job 被点：
- `approval`：由 Release Manager 之外的人点（校验 `$GITLAB_USER_EMAIL != $RELEASE_MANAGER`，职责分离）。
- `appsec_approval`：由安全团队（邮箱在 `$APPSECURITY_APPROVERS` 列表）点。

两个都点过 → `approval` stage 完成 → 进入 `deploy-prod` stage。

> PM 可查进度（见「产品经理」步骤 2），催审批人。

### 5. 更新 ArgoCD 镜像版本（deploy-prod 触发前或后，按团队约定）

**单个环境**：

```bash
curl -X POST "http://<gitlab-mgmt>/api/argocd/<project_id>/update-version" \
  -H "Content-Type: application/json" \
  -d '{
    "file_path": "app-values/prod/data-platform/my-service/prod-sh.yaml",
    "new_version": "v1-2-3-134361",
    "branch": "master",
    "commit_message": "[Release]: update my-service for prod-sh"
  }'
```

- 服务端逻辑（`version_service.py`）：取文件 → base64 解码 → `yaml.safe_load` → 改 `image.tag` → `yaml.dump` → HTTP PUT（带 `last_commit_id` 乐观锁）回 GitLab。
- 响应：`{file_path, old_version, new_version, last_commit_id, message}`。
- ⚠️ 要求文件含 `image.tag` 字段，否则报 `image.tag field not found`。

**批量多环境**（如 uat + prod 同时发版）：

```bash
curl -X POST "http://<gitlab-mgmt>/api/argocd/<project_id>/batch-update" \
  -H "Content-Type: application/json" \
  -d '{
    "updates": [
      {"file_path": "app-values/uat/data-platform/my-service/uat-sh.yaml", "new_version": "v1-2-3-134361"},
      {"file_path": "app-values/prod/data-platform/my-service/prod-sh.yaml", "new_version": "v1-2-3-134361"}
    ],
    "branch": "master",
    "commit_message": "[Release]: promote my-service uat+prod"
  }'
```

- 逐个调 `update_image_version`，返回 `{total, successful, failed, results}`。

### 6. 确认部署成功

```bash
# 查发版流水线状态
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=running"
```

`deploy-prod` 变 `success` → 部署完成，通知 PM 验证环境（见「产品经理」步骤 4）。

## 注意事项

- **Build Once Promote Many**：发版镜像必须是主干已构建且过 UAT 的那个，不重新构建。`new_version` 要与主干镜像 tag 对齐，别发未验证版本。
- **审批门禁靠 stages 顺序**：`deploy-prod` 的 `needs` 不含审批 Job，门禁靠 `approval` stage 排在 `deploy-prod` 之前实现时序门禁。改 stage 顺序或删除 approval stage = 绕过门禁。完整门禁机制见「场景 05」。
- **职责分离**：`approval` 校验发版人 ≠ Release Manager；`appsec_approval` 校验触发人在安全审批人列表。两条审批不能兼任。
- **`last_commit_id` 乐观锁**：update-version 改同一文件并发会冲突，重取 commit_id 再试。
- **VM 部署路径**：若业务用 `deploy-container-prod`（VM Docker Compose）而非 ArgoCD，不走 argocd API——tag pipeline 的 deploy Job 会 SSH 上目标机 `docker compose down/up`（见「场景 06」、`docker-deploy.yml`）。
- **`new_version` 来源**：取主干流水线的 `IMAGE_TAG`（`$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`），不要手编。
