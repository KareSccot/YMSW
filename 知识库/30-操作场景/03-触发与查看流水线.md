# 场景 03：触发与查看流水线

## 目标

说清四种流水线各自怎么触发、怎么用 API 查状态、流水线失败怎么看日志排障。

## 流程要素

- **触发条件**：已接入 CI 的业务仓库需要触发流水线或查看流水线状态、排查失败时。
- **输入信息**：目标仓库 project_id、gitlab-management 服务地址、触发分支名或 tag 名。
- **输出结果**：流水线触发成功或获取状态列表；失败 Job 的日志定位与修复。
- **预估耗时**：触发流水线约 1 秒（API 调用），流水线执行约 3-15 分钟。以上为估算量级，非实测 SLA。
- **适用范围与不适用场景**：本篇适用于分支/MR/主干流水线。发版流水线由运维触发，见「运维发版」。

## 前置条件

- 已接入 CI（见「场景 01」）。
- gitlab-management 服务可用（地址 `<gitlab-mgmt>`）。
- 知道目标仓库 `project_id`。
- 你有本仓库推分支权限；发版流水线（tag）由运维触发（见「运维发版」）。

## 操作步骤

### 1. 自然触发（推荐，按流程走）

| 流水线 | 触发动作 | 触发源 | 主要内容 |
|---|---|---|---|---|---|
| 分支流水线 | 推 feature/fix 分支 | `CI_COMMIT_BRANCH` | build → test → dev 部署 → 集成测试 |
| MR 流水线 | 提 MR | `merge_request_event` | 同分支流水线 + MR Review |
| 主干流水线 | 合到 master | `CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH` | UAT 部署 → 集成测试 |
| 发版流水线 | 打 tag | `CI_COMMIT_TAG` | tagging → approval → deploy-prod |

对应 `workflows/app-workflow.yml` 的 `workflow.rules`（见「总体架构」）。

### 2. API 手动触发（调试/重跑用）

```bash
curl -X POST "http://<gitlab-mgmt>/api/pipelines/" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "<project_id>",
    "ref": "feature/my-branch",
    "variables": {"BUILD_CONTAINER": "true"}
  }'
```

- 请求 `RunPipelineRequest`：`project_id`（必填）、`ref` 默认 `main`、`variables` 可选（传流水线变量）。
- 服务端逻辑（`pipeline_service.py`）：`project.pipelines.create({'ref': ref, 'variables': variables})`。
- 响应 `PipelineResponse`：`{id, project_id, status, ref, sha, web_url}`，点 `web_url` 进 GitLab 页面。

### 3. 查看流水线状态

```bash
# 列某项目流水线（可按 status 过滤：running/pending/success/failed/canceled/blocked）
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=failed"

# 查单条流水线详情
curl "http://<gitlab-mgmt>/api/pipelines/<project_id>/<pipeline_id>"
```

- 状态含义速查：
  - `running`：执行中
  - `pending`：排队等 runner
  - `blocked`：卡在 manual job（如 approval stage，等审批人点，见「场景 05」）
  - `success`/`failed`：结束
  - `canceled`：被取消

### 4. 流水线失败排障

1. 从 `web_url` 进 GitLab 流水线页面，找到 `failed` 的 Job。
2. 点 Job 看日志。常见失败与定位：

| 失败 Job | 常见根因 | 定位 | 适用环境 | 无效怎么办 |
|---|---|---|---|---|
| build-app | 代码编译错误 / 依赖缺失 / 单元测试失败（mvn/gradle/pnpm） | 看日志报错行；确认 `BUILD_TOOL` 变量已设 | 全环境 | 修复代码/依赖后 Retry |
| build-container | Dockerfile 错 / 依赖拉取超时 / registry 登录失败 | 看日志 `docker build` 报错行；检查 `REGISTRY_USER`/`REGISTRY_PASSWORD` 变量 | 全环境 | 修复 Dockerfile 或确认 registry 凭证后 Retry |
| security-scan | 扫描工具挂 / 发现高危被策略阻断 / 镜像拉取失败 | 看 `security-scan-results` 制品（见「CICD 总体架构」的"安全扫描（质量轴）"节） | 分支/MR + 合主干 | 确认扫描工具可用或修复高危漏洞后 Retry |
| approval | 审批人没点（blocked）或触发人不在审批列表 | 见「场景 05」 / 「安全团队 AppSec」 | 发版流程 | 催审批人点 manual job，或确认审批人变量配置正确 |
| deploy-prod / deploy-container-prod | SSH 凭证 / 目标机磁盘 / 镜像 pull 失败 | 见「运维发版」的"常见排障"节 | 仅发版流程 | 检查 SSH 凭证/目标机状态后 Retry，或升级 GitLab Issue @平台管理员 |

3. 修好后重跑：GitLab 页面点 "Retry"，或用 API 重新触发（步骤 2）。

## 代码示例

见上方各步骤。一条命令看最近失败：

```bash
# 看最近失败的流水线
curl -s "http://<gitlab-mgmt>/api/pipelines/<project_id>/?status=failed" | python -m json.tool
```

## 注意事项

- **发版流水线不归业务线触发**：tag → 生产部署由运维走审批后触发，业务线开发者一般到 MR 合主干为止（见「运维发版」）。
- **blocked ≠ failed**：状态 `blocked` 是卡在 manual job（审批），不是出错——催审批人即可，别误以为流水线挂了。
- **API 无鉴权**：触发/查流水线 API 任何能访问服务的人都能调，确保内网部署。
- **variables 传参**：API 触发时的 `variables` 覆盖仓库/Group 级同名变量，调试时可用（如临时设 `BUILD_CONTAINER=true`）。
