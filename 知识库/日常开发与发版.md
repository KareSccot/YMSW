# 日常开发与发版

## 目标

本篇面向业务线开发者、产品经理、业务方，覆盖从日常提交代码到发版上线的完整流程。阅读后可了解：提交后流水线如何运行、如何查询发版进度、业务方在发版中的配合动作、上线后如何验收、以及 MR 合入常见问题。本篇为只读视角，不涉及 CI 配置变更（配置变更见「新手接入指南」）。

## 适用角色

- 业务线开发者：提交代码、触发流水线、合 MR
- 产品经理 / 业务方：查询发版进度、催审批、验收上线、发版配合

## 提交代码后会发生什么

开发者提交至 feature/fix 分支后，自动触发**分支流水线**：build → test → dev 部署 → 发起 MR 代码评审。提交至 MR 触发 MR 流水线；合入 master 触发主干流水线（UAT 部署与集成测试）；打 tag 触发发版流水线（含审批门禁与生产部署）。push 即触发，无需手动操作。

## 查询发版进度

### 网页查询

进入 GitLab → 项目 → Build → Pipelines → 找到 tag 对应流水线，查看状态：
- `running`：流水线执行中，可查看具体卡在哪个 stage
- `blocked` / `manual`：卡在 approval 阶段，等待审批——此为需催办环节
- `passed` → 进入 deploy-prod：部署中或部署完成
- `failed`：某步失败，需判断是构建、扫描还是部署阶段

### 命令行查询（可选）

需一条命令查询进度时，可使用 GitLab 只读 API。需向运维申请只读 Personal Access Token 或项目 Token（scope `read_api`）。实例地址使用占位符 `<gitlab-instance>`，实际值向运维获取：

```bash
curl --header "PRIVATE-TOKEN: <your-read-token>" \
     "https://<gitlab-instance>/api/v4/projects/<project-id>/pipelines?per_page=5"
# 返回每条含：id / status / ref / sha / web_url
# status 取值：pending / running / success / failed / manual（manual=卡审批）
# 仅查某 tag：加 &ref=<tag-name> 过滤
```

`<project-id>` 为项目数字 ID，可在 GitLab 项目首页查看。Token 需妥善保管，不得写入仓库或贴入聊天群，失效后向运维重新申请。

此 GET 接口仅读取流水线状态，不会触发或修改任何内容。不得使用 POST 触发接口——该操作属平台管理员/运维职责，业务方使用将构成越界（详见「合规须知」）。

## 发版卡住时的处理

发版流水线进入 `approval` stage 后会停止，等待审批人手动点"Run"。审批含两个 manual job：
- `approval` 未点：催发版审批人（单人）
- `appsec_approval` 未点：催安全团队 AppSec

催办方式：请运维在发版通知中抄送审批人邮箱，或通过公司 IM 按审批人姓名搜索并 @ 对应人员。审批人邮箱列表由安全团队维护，业务方不直接查询。催办后仍未审批，联系团队 Lead 协调。

## 发版耗时

顺利情况下约半天，主要取决于审批人响应速度：
- approval 等审批：约 1-4 小时（取决于审批人在线与响应速度）——此为最常卡顿环节，提前协调审批人可显著加快
- deploy-prod 部署：约 3-15 分钟（取决于镜像大小与部署路径）

以上为估算量级，非实测 SLA。加速建议：发版前预先通知发版审批人与安全团队 AppSec。等待超过 4 小时未动，联系团队 Lead 协调催办。

## 业务方在发版中的配合动作

打 tag 触发发版、修改生产部署配置、执行生产部署均属运维（发版人）职责，非业务方/开发者职责。业务方需完成的配合动作分三段：

**发版前**：
1. 确认待发代码已合主干，且主干 UAT 流水线验证通过——不得发布未经验证的版本
2. 提前通知运维发版计划：仓库、计划时间、版本号（tag 名）
3. 提前与发版审批人和安全团队 AppSec 沟通，使其知晓有发版待批
4. 如有需业务方准备的外部依赖（数据库变更、配置开关等），发版前就绪

**发版中**：运维操作，业务方按上述方法查询进度并观察，不进行操作。

**发版后**：业务方按业务功能验证新版，发现异常按回滚流程处理。

业务方不得自行打 tag 触发发版（tag 触发生产部署流水线，误触发将直接影响生产环境），不得试图跳过审批门禁。发版相关变量（审批人列表、部署文件路径等）由运维/平台管理员维护。

## 上线验收与回滚

流水线 `deploy-prod` 变为 `passed` 即表示部署成功。环境访问地址向运维或发版通知 IM 群中本次 tag 的触发人索取；版本号向运维确认本次的 `new_version`。

### 功能异常的回滚

发现功能异常时，按以下 5 步处理：
1. 立即通知运维，说明问题与版本号
2. 运维回滚到上一个稳定版本（ArgoCD 几分钟；VM 稍慢）
3. 回滚期间业务方协调暂时使用旧版本或公告维护
4. 回滚后确认旧版本正常
5. 问题修复后走新的发版流程（不得跳过审批直接重发）

回滚指"部署上一个稳定镜像版本"，非"撤销发版"。审批门禁在回滚时加速但不跳过。

## MR 合入

MR 合入通常需满足：至少 1 个 Approve（团队 Lead 或指定 Reviewer）；若触及安全相关文件，可能还需安全团队审批。在 MR 页面右侧"Approvals"区可查看是否达标。

- Approve 不足：联系团队 Lead 或 Reviewer 审查
- 显示需安全审批：联系安全团队 AppSec
- 条件达标仍无法合入：检查 MR 是否有冲突，先 rebase 解决冲突

## 联系人

| 事项 | 联系人 |
|---|---|
| CI 配置 / GitLab 权限 / 团队 Variables | 团队 Lead |
| 部署 / 发版状态 / 回滚 | 运维（发版人） |
| 审批 / 合规 / 安全 | 安全团队 AppSec |
| 服务地址 / API Key / 镜像仓库凭证 | 平台管理员 |
