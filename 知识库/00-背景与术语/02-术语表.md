# 术语表

## 目标

统一全库术语。按"GitLab CI 核心 / Trunk Flow / 审批与治理"三类列出中英对照与在本项目里的具体含义。看不懂某篇里的词，来这里查。

> **类型与适用范围**：本篇为参考类（reference，规范外补充分类，仅作术语速查，免套四类必含项）。适用范围为全库术语统一参考；本篇不涉及具体操作步骤。

## GitLab CI 核心术语

| 术语 | 英文 | 本项目里的含义 |
|---|---|---|
| 流水线 | Pipeline | 一次 CI/CD 执行。由 ref（分支/tag/MR）触发，含多个 stage |
| 阶段 | Stage | 流水线的执行段，按 `stages:` 列表顺序串行。同 stage 内 Job 全完成才进下一 stage（门禁靠这机制） |
| 作业 | Job | 流水线里的一个执行单元，跑一段 script。如 `deploy-prod`、`appsec_approval` |
| 规则 | rules | 决定 Job 在哪个流程出现的条件。本项目三件套：dev-fix-rules（分支/MR）、uat-rules（主干）、release-rules（发版 tag） |
| 条件域 | rules 域 | 一个 Job 用哪条 rules，决定它在哪些流程出现。`approval`/`deploy-prod` 都用 `.release_rules`（仅 tag） |
| 依赖 | needs | Job 间的数据依赖与执行序。**注意**：本项目生产部署 Job 的 needs 不含审批 Job，门禁靠 stage 顺序不靠 needs |
| 继承 | extends | Job 复用隐藏模板（`.xxx`）的字段。如 `deploy-prod extends: [.deploy, .release_rules]` |
| 包含 | include | 引入外部 YAML 文件。业务仓库 `include` Common 层 `app-workflow.yml`；`include` 可带 `rules` 做条件 include（如按 `BUILD_TOOL` 选 mvn/gradle/pnpm） |
| 引用 | !reference | 跨文件引用某段配置。`.release_rules` 用 `!reference [.conditions_for_tags, rules]` 引用基础条件 |
| 手动触发 | when: manual | Job 需人手点才跑。审批 Job（`approval`/`appsec_approval`）都是 manual，构成审批门禁 |
| 失败不阻断 | allow_failure | `true` 时 Job 失败不阻断流水线。审批 Job 是 `allow_failure: false`（失败则停）；安全扫描默认 `true` |
| 制品 | artifacts | Job 产物，传给下游 Job 或存档。如 `security-scan` 产 `./security-scan-results`；`set-release-manager` 产触发人邮箱供 `approval` 校验 |
| Runner | GitLab Runner | 跑 Job 的执行器。本项目 `default.tags: [platform, tencent, devops]`（见 app-workflow.yml） |
| 变量 | variables | 流水线变量。可在 `.gitlab-ci.yml`、Group 级、Project 级 CI/CD Variables 配。如 `TEAM`、`BUILD_TOOL`、`APPSECURITY_APPROVERS` |

## Trunk Flow 术语

| 术语 | 英文 | 本项目里的含义 |
|---|---|---|
| 主干 | Trunk / master | 主分支。所有 MR 合到主干，主干流水线做 UAT |
| 特性分支 | feature/fix 分支 | 开发用的短分支。推分支触发分支流水线 |
| 合并请求 | Merge Request (MR) | 把特性分支合并到主干的请求。MR 流水线在 MR 时触发，含 Review/Approve |
| 标签 | tag | 标记版本的 ref。打 tag 触发发版流水线（生产部署） |
| 制品晋级 | Build Once Promote Many | 一次构建，多环境复用。发版复用主干已构建并过 UAT 的镜像，不重新构建 |

## 审批与治理术语

| 术语 | 英文 | 本项目里的含义 |
|---|---|---|
| 审批门禁 | approval gate | 发版前必须完成的审批。本项目靠 `approval` stage（排在 deploy-prod 前）+ `when: manual` 实现，**不靠 needs** |
| MR Approve | MR Approve | 团队层的代码审查通过。GitLab MR 功能，开发者互相审核后点 Approve |
| 发版 Approve | release approval | 发版层的审批。`approval` Job，校验触发人 ≠ `RELEASE_MANAGER`（职责分离） |
| 安全层 Approve | appsec approval | 安全层（SDLC）审批。`appsec_approval` Job，校验触发人在 `APPSECURITY_APPROVERS` 列表 |
| Team 层 Pro | Team approval | 团队内部审批。会议口径，**代码无统一实现**，各团队自定义或用 MR Approve |
| BPM Pro | BPM approval | 业务流程管理审批。会议口径"待定，暂不用"，**代码未实现** |
| 职责分离 | segregation of duties | 发版人不能审批自己。`set-release-manager` 记触发人邮箱，`approval` 校验邮箱 ≠ Release Manager |
| 条件 include | conditional include | 按 variable 动态 include 文件。`stages/build.yml` 按 `BUILD_TOOL` 选构建流程 |
| 三层模板 | Common/Team/Repo | 配置复用三层：Common（全公司底座 cicd-template）→ Team（团队 namespace）→ Repo（业务仓库 .gitlab-ci.yml） |
| 条件域一致 | rules 域一致 | 审批 Job 与部署 Job 用同一条件域。本项目审批和 deploy-prod 都用 `.release_rules`（仅 tag），天然一致 |
| CUSTOM_ 前缀 | CUSTOM_ prefix | 应用自定义环境变量约定。`vm-deploy.yml` 收集所有 `CUSTOM_` 变量 base64 注入到目标机容器 |

## 注意事项

- **术语以代码实现为准**：会议口语（如"Prover""BPM Pro"）与代码实现（如 `appsec_approval` 脚本）有落差时，以代码为准。如"安全层 Pro"在代码里是 `appsec_approval` 的内联 shell 比对 email，无独立"Prover"组件。
- **needs 与 stage 的区别**：needs 是 Job 间数据依赖，stage 是执行段顺序。本项目门禁靠 stage 偏序，不是 needs——这是最易混淆的一条。
- **"Pro" 是会议简称**：会议里"Team 层 Pro""安全层 Pro""BPM Pro"的"Pro"是 Approval 的口语简称，不是代码标识符。代码里用 `approval`/`appsec_approval` 等命名。
