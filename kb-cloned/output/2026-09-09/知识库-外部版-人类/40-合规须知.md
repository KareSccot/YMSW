# 合规须知

## 目标

读完本文件，开发者能够：说清四类安全扫描的开启要求与合规责任；理解生产发版两道审批门禁的机制与不可跳过性；遵守镜像合规要求；牢记合规红线清单；明确外包与内部信息的边界。

## 前置条件

- 项目经公司 GitLab 流水线发布（无论走标准模板还是自建 CI）
- 掌握 [20-日常开发与发版](20-日常开发与发版.md) 中的发版流程与安全扫描使用

## 安全扫描合规

公司要求项目按 App Security 团队规定开启对应安全扫描。扫描 job 默认 `allow_failure: true`（失败不阻断部署），`SECURITY_ENABLE_BLOCK` 可设为阻断模式。

四类扫描及开关：

| 扫描类型 | 开关变量 | 依赖 |
|----------|----------|------|
| SAST（静态应用安全测试） | `SAST_PROJECT_ID` + `SAST_APP_ID` + `Has_SAST: "1"` | — |
| SCA（软件成分分析） | `SCA_PROJECT_TOKEN` + `Has_SCA: "1"` | — |
| DockerScan（镜像扫描） | `TENABLE_SCANTARGET_DOCKER_REPOSITORY_URL` | `build-container` 成功 |
| ThreatModeling（威胁建模） | `Has_ThreatModel: "1"` | — |

扫描结果输出到 `./security-scan-results/`，`GenSecurityReport` 生成 HTML 报告并发送至 `$GITLAB_USER_EMAIL`。

部分团队将 ThreatModeling 限定在 main 分支与 MR 触发（如 axiom），在合并前拦截威胁。自建 CI 项目（如 dvcopilot）可只叠加安全扫描段，但须用共享 dind runner，不能用自建 VM 的 shell runner。

**违反后果**：未开启规定扫描项的项目不予发版；App Security 团队有权阻断不合规部署。

## 审批门禁合规

生产发版须经两道审批门禁，均为 `allow_failure: false`（失败即阻断发版，不可跳过）。

- **release-approval**：Release Manager 之外的第二人手动确认。Release Manager 由 `.pre` 阶段 `set-release-manager` 自动记录（打 tag 的用户）。机制上 script 检查操作人邮箱是否等于 `release_variables.txt` 中的 `$RELEASE_MANAGER`，相等则失败
- **appsec-approval**：`APPSECURITY_APPROVERS` 变量列表中的 AppSec 人员手动确认。操作人不在列表则失败

两道门禁均仅 tag 发版流水线触发（release-rules）。门禁 job 为 manual + `allow_failure: false`：必须人工触发且必须通过，否则 `deploy-prod` 不执行。

**违反后果**：跳过或禁用审批门禁属严重违规。dvcopilot 团队红线注释明确：**不得给 `approval` / `appsec_approval` / `set-release-manager` 写 `rules: when: never`**。

## 镜像合规

所有部署镜像须来自公司镜像仓库，镜像 tag 须可追溯至具体流水线或 commit。

合规要求：

- 镜像推送地址：`${DOCKER_REGISTRY}/${SERVICE_REPOSITORY}/${IMAGE_NAME}:${IMAGE_TAG}`
- 默认 tag：`$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`（可追溯流水线）
- 按需 tag：`$CI_COMMIT_SHA`（dvcopilot 团队做法，按 commit 追溯）
- `SERVICE_REPOSITORY` 不得保留默认值 `change_me`，须为本团队实际命名空间

自建 CI 不推 registry 的项目（如 dvcopilot VM 本地构建）不适用镜像 tag 规则，但仍须可追溯 commit。

**违反后果**：使用非公司镜像仓库或不可追溯 tag 的镜像不予部署；环境负责人有权拒绝。

## 红线清单

以下行为属合规红线，任何项目不得违反：

1. 给 `DockerScan` / `SCA` / `GenSecurityReport` / `approval` / `appsec_approval` / `set-release-manager` 写 `rules: when: never`——禁用即绕过安全门禁
2. 在 `.gitlab-ci.yml` 或 CI 变量中硬编码 Token / 密码 / Access Key——须用 GitLab CI/CD Variables（masked）
3. 暴露内网地址、registry 凭证、内部 API 路径到外部可见文档或日志
4. 生产部署跳过审批门禁直接 `deploy-prod`

dvcopilot 团队虽自建 CI，但明确保留安全扫描段并遵守红线，可作为自建 CI 叠加扫描的合规范例。

**违反后果**：App Security 团队 + DevOps 团队联合处置，严重者撤销项目发版权限。

## 外包与敏感信息边界

外部用户与外包人员只走 GitLab UI 操作，不接触内部 API、Token、服务源码。

允许与禁止：

- ✅ 允许：在 GitLab UI 配置 CI/CD Variables、查看 Pipeline、手动触发 deploy / approval job
- ✅ 允许：编写自己的 `.gitlab-ci.yml`、`Dockerfile`、`docker-compose.yml`
- ❌ 禁止：用 curl / API 调用内部 `gitlab-management` 服务、使用 PRIVATE-TOKEN 操作 GitLab API
- ❌ 禁止：获取内部脚本源码（如安全扫描镜像内逻辑）、内网服务地址、registry 凭证明文

内部 API 操作（如 ArgoCD 版本更新、GitLab 文件更新）由 CI Job 内部完成，外部用户无需也不应直接调用。

**违反后果**：违规获取或泄露内部凭证 / 地址属安全事件，按公司安全规范处置。

## 注意事项

- **门禁 job 看似可手动触发，但不可跳过**：`allow_failure: false` 意味着不通过就发不了版
- **扫描默认不阻断但有合规要求**：`allow_failure: true` 是为不阻塞日常开发，不等于可以不开
- **变量值用 UI 配置不硬编码**：所有凭证类变量走 GitLab CI/CD Variables 并勾选 masked
- **自建 CI 也要守红线**：不引用标准模板不等于不受合规约束

## 升级路径

- 不确定要开哪些扫描 → App Security 团队
- AppSec 审批人列表需更新 → App Security 团队
- 发版被审批门禁挡住 → 先确认操作人是否符合门禁要求（非 Release Manager / 在审批人列表），符合仍被挡 → App Security 团队
- 镜像合规疑问 → DevOps 团队 + App Security 团队
