# 新手接入指南

## 目标

读完本文件，开发者能够：把一个新项目接入公司 CI/CD 流水线；正确填写 `.gitlab-ci.yml` 与 CI 变量；跑通首次构建与部署；知道各步出错该找谁。

## 前置条件

- GitLab 账号且有项目仓库 Developer 及以上权限
- 已确认项目所属业务团队
- 已确定构建工具（gradle / mvn / pnpm）与部署模式（ArgoCD / VM Docker Compose）
- 团队已在 `team-cicd` 仓库有对应分支（分支名 = 团队名）。无则先联系 DevOps 团队建团队工作流

## 操作步骤

### 1. 确认团队工作流

检查 `team-cicd` 仓库是否存在本团队分支及 `<team>/backend-workflow.yml`（或 `frontend-workflow.yml`）。team-cicd 按分支组织，每个 feat/* 分支对应一个业务团队。分支不存在则联系 DevOps 团队先创建。

### 2. 创建 .gitlab-ci.yml

在项目根目录创建 `.gitlab-ci.yml`，include 所属团队的工作流文件。最小模板如下，复制后按注释填值：

```yaml
include:
  - project: 'devops/team-cicd'
    ref: <team-branch>           # 替换为所属团队分支名
    file: '/<team>/backend-workflow.yml'

variables:
  BUILD_CONTAINER: "true"        # true=容器构建+VM部署；false=ArgoCD GitOps部署
  BUILD_TOOL: "gradle"           # gradle / mvn / pnpm
  BUILD_FOLDER: "."
  ARTIFACT_FOLDER: "build/libs"
  SERVICE_PORT: 8080
  PACKAGE_NAME: ${IMAGE_NAME}
  DOCKER_BUILD_ARGS: "--build-arg BUILD_FOLDER=${BUILD_FOLDER} --build-arg ARTIFACT_FOLDER=${ARTIFACT_FOLDER} --build-arg PACKAGE_NAME=${PACKAGE_NAME} --build-arg SERVICE_PORT=${SERVICE_PORT}"
```

参数说明：

- `ref`：team-cicd 仓库中本团队的分支名
- `file`：团队目录下的工作流文件（backend / frontend）
- `BUILD_CONTAINER`：决定部署链路。`true` 走容器构建 + VM Docker Compose；`false` 走 ArgoCD GitOps
- `BUILD_TOOL`：构建工具，Common 层 `stages/build.yml` 按此 include 分发

### 3. 配置 CI 变量

在 GitLab UI 进入项目 Settings → CI/CD → Variables，按下方清单填入。带 `<占位>` 的实际值由对应团队提供，不在本指南写出。

| 变量 | 用途 | 提供方 |
|------|------|--------|
| `DOCKER_REGISTRY` | 镜像仓库地址 | DevOps 团队（实例级默认） |
| `REGISTRY_USER` / `REGISTRY_PASSWORD` | 镜像仓库登录凭证 | DevOps 团队（实例级默认） |
| `SERVICE_REPOSITORY` | 镜像命名空间 | DevOps 团队 |
| `SECURITY_SCAN_IMAGE_NAME` / `SECURITY_SCAN_IMAGE_VERSION` | 安全扫描镜像 | App Security 团队 |
| `WUXI_DNS` | 构建容器 DNS | DevOps 团队 |
| `UAT_SSH_TARGET` / `UAT_SSH_USER` / `UAT_SSH_PORT` / `UAT_SSH_PRIVATE_KEY` | UAT VM SSH 凭证 | UAT 环境负责人 |
| `UAT_SSL_CERT` / `UAT_SSL_KEY` / `UAT_DEPLOY_PATH` | UAT 证书与部署路径 | UAT 环境负责人 |
| `PROD_*`（同上 prod 前缀） | 生产 VM 凭证与路径 | 生产环境负责人 |
| `APPSECURITY_APPROVERS` | AppSec 审批人邮箱列表（逗号分隔） | App Security 团队 |

### 4. 提供构建与部署文件

- 容器部署：提供 `Dockerfile`（置于 `DOCKER_BUILD_PATH`，默认 `.`）与 `docker-compose.yml`；设 `SERVICE_PORT`、`IMAGE_NAME`
- ArgoCD 部署：确认目标环境在 GitOps 仓库有 `app-values/<env>/<team>/<service>/<env>-<region>.yaml`

### 5. 选择构建工具

在 `.gitlab-ci.yml` 设 `BUILD_TOOL` 为 `gradle` / `mvn` / `pnpm` 之一。对应行为：

- gradle：执行 `./gradlew clean build`，产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`
- mvn：执行 `mvn package -P<env> -Dmaven.test.skip=true`，产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`
- pnpm：执行 `npm build`，产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/`

只需打镜像不需源码构建时，设 `build-app` 为 `when: never`，仅保留 `build-container`。

### 6. 提交验证

提交代码到 dev 分支，触发 MR 流水线。确认 `build-app` 与 `build-container` 跑通。跑通后按 dev → uat → prod 推进。

## 注意事项

- **`SERVICE_REPOSITORY` 必改**：默认值 `change_me` 会导致镜像 push 失败，须改为本团队命名空间
- **MR 与分支流水线互斥**：分支有打开的 MR 时，分支 push 流水线不跑，只跑 MR 流水线——属预期行为
- **构建镜像由 DevOps 维护**：项目层不修改构建镜像，缺工具/版本不符报 DevOps 团队
- **生产部署不可跳过审批**：`deploy-prod` 依赖 `approval` + `appsec_approval` 通过，详见 [40-合规须知](40-合规须知.md)
- **自建 CI 项目**：不引用 app-workflow 的项目，参考 [20-日常开发与发版](20-日常开发与发版.md) "自建 CI 叠加安全扫描" 单独 include 安全扫描段

### ariba 前端

部署模式为 ArgoCD（K8s GitOps），构建工具 Node18 + npm + vite（产物 `dist/`）。关键配置：`SERVICE_REPOSITORY` 设为本团队镜像命名空间；`TEAM: "ariba"`；按分支选择构建环境（dev→`build:test`、UAT→`build:uat`、Master→`build:prod`、tag→`build:prod`）；`SERVICE_PORT: 80`（nginx 容器）；dev 部署关闭；UAT 部署限定 UAT 分支手动触发。

### isrm-appsec

## 常见接入问题

### UAT 分支名大小写
安全扫描（DockerScan/SCA/ThreatModeling）只在分支名为 `UAT`（大写）时触发。若分支名用小写 `uat`，构建部署正常但安全扫描跳过。建议新建预发布分支时直接使用大写 `UAT`。

### 前端产物路径
vite 构建产物默认输出到 `dist/` 目录而非 `build/`。前端项目接入时须在 `.gitlab-ci.yml` 中设 `ARTIFACT_FOLDER: "dist"`，否则镜像构建会因找不到产物而失败。

### 前端构建环境选择
ariba 前端按分支名自动选择构建 profile：dev 分支跑 `build:test`，UAT 分支跑 `build:uat`，Master 分支或 tag 跑 `build:prod`。分支命名需与 `npm run build:<env>` 对应，否则构建报错。

### 前端 nginx 端口
ariba 前端 nginx 容器监听 80 端口，SSL 终止在 K8s Ingress 层。若自建 nginx 配置，注意 `listen` 写死的端口（默认 80），且容器内非 root 用户无法绑定 <1024 端口。修改端口需同时改 `nginx.conf` 的 `listen` 和 `SERVICE_PORT` 变量。

### 安全扫描与分支名
当前模板安全扫描只对 `UAT` 分支触发。若团队使用其他分支名（如 `release`、`main`）做预发布验证，需在团队工作流中覆盖对应 job 的 rules，或统一使用 `UAT` 分支名。

## 升级路径

- 步骤 1 团队工作流不存在 → DevOps 团队
- 步骤 3 变量值不确定 → 对应环境负责人或 DevOps 团队
- 构建或部署报错 → [30-故障排查](30-故障排查.md)
- 安全扫描配置疑问 → App Security 团队
