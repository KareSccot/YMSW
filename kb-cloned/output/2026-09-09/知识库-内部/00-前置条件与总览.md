# 前置条件与总览

## CI/CD 三层架构

**架构层级**：应用层 → Team 层 → Common 层，通过 GitLab CI 的 `include` 机制层层组合。

**Common 层（cicd-template 仓库，`git@gitspace.wuxibiologics.com:devops/cicd-template.git`）**：提供通用流水线模板，核心设计是"Workflows 组合 Stages，Stages 引用 Jobs 实现，Rules 控制 Job 何时出现"。

- **Workflows**（`workflows/`）：完整流水线骨架。`app-workflow.yml` 是应用基础流水线，`iac-workflow.yml` 是基础设施流水线
- **Stages**（`stages/`）：阶段定义，每个 stage 文件组合对应 job + rules（`build.yml`、`container-build.yml`、`argo-deploy.yml`、`docker-deploy.yml`、`approval.yml`、`security-scan.yml`）
- **Jobs**（`jobs/`）：具体实现脚本，按类别组织（build/deploy/iac/quality/security/release/approval）
- **Rules**（`rules/`）：可复用的触发条件，控制 job 在哪些场景出现

**Team 层（team-cicd 仓库，`git@gitspace.wuxibiologics.com:devops/team-cicd.git`，按分支组织）**：每个业务团队一个分支，通过 `include` 引用 Common 层 `app-workflow.yml`，再用变量开关和规则覆盖定制自己的工作流。当前 16 个分支：Master、docker-test、feat/ariba、feat/atlas-team、feat/axiom、feat/demojava-enable-sast、feat/dfs-sciwriter-team、feat/dpdo-dev-team、feat/dvcopilot、feat/init_sci_writer_team、feat/isrm-appsec、feat/official-website、feat/pipeline-pms、feat/pipeline-tag-test、feat/python、pipeline-pms。

**应用层**：项目根目录 `.gitlab-ci.yml`，`include` 所属团队的工作流文件（如 `devops/team-cicd` 的 `<team>/backend-workflow.yml`）。

## 跨仓 include 关联

Team 层的工作流通过 `include: project:` 引用 Common 层模板，形成跨仓依赖。以下是关键关联：

| 团队分支 | 引用的 Common 层 ref | 引用的文件 | 底层能力 |
|---------|---------------------|-----------|---------|
| feat/ariba（后端） | feat/build_prod_image | workflows/app-workflow.yml | 13 stages 含 build-app/build-container/deploy-uat/deploy-prod/approval/security-scan。**ref 不可达**（浅克隆未含该分支），以 Master 默认分支内容为准 |
| feat/ariba（前端） | feat/enhance_gradle | workflows/app-workflow.yml | 同上，**ref 不可达**，以 Master 默认分支内容为准 |
| feat/isrm-appsec | feat/deploy-docker | workflows/app-workflow.yml | 同上，**ref 不可达**，以 Master 默认分支内容为准 |

**组级 override**：各团队在 include 后通过 variables 和 job 级 rules 覆盖默认参数。例如 ariba 后端设 `DEPLOY_CONTAINER: "false"` 走 ArgoCD，ariba 前端设 `SERVICE_REPOSITORY: "ariba-mw-srmp"` 指定镜像仓库命名空间。

## app-workflow 流水线阶段

**阶段顺序**：

1. `.pre` — 预备（set-release-manager，仅在 tag 流水线触发）
2. `build` — 构建（源码编译 build-app + 镜像构建 build-container）
3. `test` — 测试
4. `quality` — 质量与安全扫描（SAST/SCA/DockerScan/ThreatModeling/Sonar）
5. `security-report` — 生成安全扫描报告（GenSecurityReport）
6. `deploy-dev` — 开发环境部署（手动）
7. `deploy-uat` — UAT 环境部署（手动，部分团队改为自动）
8. `create-release` — 创建发布
9. `approval` — 审批门禁（release-approval + appsec-approval，手动，allow_failure: false）
10. `deploy-prod` — 生产部署（手动，allow_failure: false）
11. `finalize-release` — 发布收尾
12. `.post` — 后置

**关键开关变量**：

- `BUILD_CONTAINER`：`true` 时启用镜像构建与容器部署链路；非 `true` 则走 ArgoCD GitOps 部署
- `DEPLOY_CONTAINER`：`false` 时用 ArgoCD 部署而非容器部署
- `BUILD_TOOL`：`gradle` / `mvn` / `pnpm` 决定用哪个构建 Job
- `BUILD_FOLDER` / `ARTIFACT_FOLDER`：构建源目录与产物目录
- `SERVICE_PORT` / `PACKAGE_NAME` / `IMAGE_NAME`：镜像构建参数
- `SERVICE_REPOSITORY`：镜像仓库命名空间（如 `ariba-mw-srmp`）
- `TEAM`：团队名，ArgoCD deploy job 用它拼 `app-values/<env>/<TEAM>/<service>/` 路径

## 构建工具矩阵

- **gradle**：`./gradlew $GRADLE_BUILD_OPTS`（默认 `clean build`），产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`
- **mvn**：`mvn package -P${BUILD_ENV} -Dmaven.test.skip=true`，产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`
- **pnpm**：`npm build`（pnpm 镜像内），产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/`
- **docker**：`docker build` + `docker push`，镜像 tag 默认 `$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`
- **npm/vite**：ariba 前端用 node18 + npm + vite，产物 `dist/`

## 部署路径

**ArgoCD GitOps 部署**（`DEPLOY_CONTAINER: "false"` 或 `BUILD_CONTAINER` 非 `true`）：Job 调用 `aisix-mgmt` 部署服务（`https://aisix-mgmt.wuxibiologics.com`）更新 GitOps 仓库中应用版本文件，由 ArgoCD 滚动部署。适用于 dev/uat/prod。GitOps 仓库路径：`app-values/<env>/<TEAM>/<service>/<env>-<region>.yaml`

**VM Docker Compose 部署**（`BUILD_CONTAINER: "true"`）：Job 通过 SSH 上传 docker-compose.yml + SSL 证书到目标 VM，远程执行 `docker compose up`。适用于 uat/prod。UAT VM 通过 `UAT_SSH_TARGET` 等变量配置。

## 前置条件

**接入 CI/CD 前需具备**：

- GitLab 账号（`gitspace.wuxibiologics.com`）且有项目仓库的 Developer 及以上权限
- 项目所属团队已在 `team-cicd` 仓库有对应分支和工作流文件
- 确定构建工具（gradle/mvn/pnpm/npm）或仅需容器构建
- 确定部署模式（ArgoCD GitOps 或 VM Docker Compose）
- CI 变量已配置（见 [10-新手接入指南](10-新手接入指南.md) "必配变量"）

## 角色与联系人

- **DevOps 团队**：CI/CD 模板维护、Team 工作流配置、Runner 管理、接入支持。联系：`devops/cicd-template` 或 `devops/team-cicd` 仓库提 issue
- **App Security 团队**：安全扫描配置、AppSec 审批、合规红线裁定。联系：`APPSECURITY_APPROVERS` 变量中的审批人列表
- **环境负责人**：dev/uat/prod 环境的部署目标、SSH 凭证、域名/证书
- **Release Manager**：由发起 tag 流水线的用户自动担任，负责走完发版审批

## 升级路径

- 流水线配置类问题 DevOps 团队未能解决 → 提交 issue 到 `git@gitspace.wuxibiologics.com:devops/cicd-template.git` 或 `devops/team-cicd.git`
- 安全审批被拒或合规疑问 → App Security 团队
- 发版卡在 approval 阶段 → 确认 release-approval 需非 Release Manager 本人操作，appsec-approval 需 AppSec 审批人操作
