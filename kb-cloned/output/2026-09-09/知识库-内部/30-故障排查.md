# 故障排查

## 构建失败：gradle/mvn/pnpm/npm 构建报错

**错误现象**：`build-app` job 失败，日志显示构建命令报错。

**适用环境**：dev/fix 分支或 MR 流水线。

**诊断步骤**：

1. 打开 GitLab UI（`gitspace.wuxibiologics.com`）该 Pipeline 的 `build-app` job 日志
2. 区分错误类型：
   - 依赖解析失败（网络/镜像源）→ 步骤 A
   - 编译错误（代码问题）→ 步骤 B
   - 产物路径不对（`BUILD_FOLDER`/`ARTIFACT_FOLDER` 配错）→ 步骤 C
   - 构建镜像缺工具/版本不符 → 步骤 D

**解决步骤**：

- **步骤 A**：检查 `BUILD_FOLDER` 是否指向含 `build.gradle`/`pom.xml`/`package.json` 的目录；JVM 项目确认 `BUILD_ENV` profile 存在。构建镜像源由 DevOps 统一配置（TCR `cld93-ld-tcr-premium-sh-001.tencentcloudcr.com`），无法访问则报 DevOps 团队
- **步骤 B**：修正代码，本地用相同命令复现后再 push
- **步骤 C**：修正 `BUILD_FOLDER` 与 `ARTIFACT_FOLDER` 变量。JVM 产物须匹配 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`；前端产物匹配 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/`（vite 默认 `dist/`）
- **步骤 D**：构建镜像版本/工具缺包 → DevOps 团队。当前构建镜像：JDK/Maven `jdk21.0.11_10-jdk-ubi9-minimal_mvn3.9.6:feat-ariba-144059`，Node18/npm `node18_npm9.8.1:1.0.0`

**如果无效怎么办**：把 `build-app` job 完整日志贴给 DevOps 团队，注明团队分支与 `BUILD_TOOL` 值。

## 镜像构建/推送失败

**错误现象**：`build-container` job 失败，日志含 `docker login` 失败、`docker push` 权限拒绝、或 `docker build` 报错。

**适用环境**：开启了 `BUILD_CONTAINER: "true"` 的项目，dev/uat/prod 流水线。

**诊断步骤**：

1. 检查日志中 `docker login` 是否成功——失败多为 `REGISTRY_USER`/`REGISTRY_PASSWORD` 凭证问题
2. 检查 `docker push` 目标地址 `cld93-ld-tcr-premium-sh-001.tencentcloudcr.com/<SERVICE_REPOSITORY>/<IMAGE_NAME>:<IMAGE_TAG>` 中各段是否正确
3. 检查 `SERVICE_REPOSITORY` 是否仍是默认值 `change_me`（未配置）
4. 检查 `Dockerfile` 是否存在于 `DOCKER_BUILD_PATH`

**解决步骤**：

- 凭证问题：`REGISTRY_USER`/`REGISTRY_PASSWORD` 缺失或失效 → DevOps 团队（实例级变量，在 `gitspace.wuxibiologics.com` Admin → CI/CD → Variables 配置）
- `SERVICE_REPOSITORY: change_me`：改为本团队在 TCR 的实际命名空间（如 `ariba-mw-srmp`），由 DevOps 团队提供
- `Dockerfile` 不存在：在 `DOCKER_BUILD_PATH`（默认 `.`）根目录放置 `Dockerfile`
- `IMAGE_NAME` 未设：默认取 `$SERVICE_NAME`（= `$CI_PROJECT_NAME`），确认项目名即期望镜像名

**如果无效怎么办**：贴 `build-container` 日志（含 `docker build` 命令行）给 DevOps 团队。

## SSH 部署失败（VM Docker Compose 模式）

**错误现象**：`deploy-container-uat`/`deploy-container-prod` job 失败，日志含 `ssh: connect to host` 失败、`Permission denied (publickey)`、或 `docker compose up` 报错。

**适用环境**：VM Docker Compose 部署模式（`BUILD_CONTAINER: "true"`），uat/prod。

**诊断步骤**：

1. 区分阶段：SSH 连接失败（`connect to host` / `port`）→ 网络或端口；认证失败（`Permission denied`）→ SSH key；远程命令失败（`docker compose` 报错）→ VM 环境或 compose 文件
2. 检查变量：`UAT_SSH_TARGET`/`UAT_SSH_USER`/`UAT_SSH_PORT`/`UAT_SSH_PRIVATE_KEY`（UAT）或 `PROD_*`（PROD）是否配置
3. 检查 `DOCKER_COMPOSE_FILE`（默认 `./docker-compose.yml`）是否存在且格式正确
4. 检查 `UAT_SSL_CERT`/`UAT_SSL_KEY` 是否已配

**解决步骤**：

- SSH 连接/认证失败：`SSH_PRIVATE_KEY`/`SSH_USER`/`SSH_PORT`/`SSH_TARGET` 配错或失效 → 对应环境负责人重新提供
- `docker compose up` 失败：检查 `docker-compose.yml` 中镜像引用、端口、卷配置；VM 上 docker 不可用 → 环境负责人
- 证书问题：`SSL_CERT`/`SSL_KEY` 未配或过期 → 环境负责人

**如果无效怎么办**：把 deploy job 日志给环境负责人 + DevOps 团队。生产部署失败因 `allow_failure: false` 会阻断发版，需优先处理。

## ArgoCD 部署未生效

**错误现象**：`deploy-dev`/`deploy-uat`/`deploy-prod` job 成功但应用版本未更新。

**适用环境**：ArgoCD GitOps 部署模式（`DEPLOY_CONTAINER: "false"`）。

**诊断步骤**：

1. 检查 deploy job 日志中是否有调用 `aisix-mgmt`（`https://aisix-mgmt.wuxibiologics.com`）更新版本文件的记录
2. 确认 GitOps 仓库中 `app-values/<env>/<TEAM>/<service>/<env>-<region>.yaml` 存在
3. 确认 `TEAM`、`SERVICE_NAME`、`ENV`、`REGION` 变量正确
4. 检查 ArgoCD 控制台（`https://argocd.uat-halo-01.tencent.wuxibiologics.com`）同步状态

**解决步骤**：

- 版本文件路径不存在：GitOps 仓库缺配置 → DevOps 团队补 `app-values/<env>/<TEAM>/<service>/` 目录与文件
- `TEAM` 变量未设（默认 `change_me`）：设为本团队名
- ArgoCD 未同步：DevOps 团队检查 ArgoCD 应用状态与同步策略

**如果无效怎么办**：联系 DevOps 团队排查 GitOps 仓库与 ArgoCD 同步链路。

## 安全扫描失败或无结果

**错误现象**：`SAST`/`SCA`/`DockerScan`/`ThreatModeling` job 失败，或 `GenSecurityReport` 提示"No JSON files found"。

**适用环境**：开启了对应扫描开关的项目。

**诊断步骤**：

1. 确认扫描开关变量已正确设置（`Has_SAST`/`Has_SCA`/`Has_ThreatModel` 为 `"1"`，`SAST_PROJECT_ID`+`SAST_APP_ID`、`SCA_PROJECT_TOKEN`、`TENABLE_SCANTARGET_DOCKER_REPOSITORY_URL` 非空）
2. DockerScan 依赖 `build-container` 成功——镜像未构建则 DockerScan 不触发
3. `GenSecurityReport` 提示无 JSON：上游扫描 job 未产出结果文件到 `./security-scan-results/`
4. 扫描镜像 `SECURITY_SCAN_IMAGE_NAME`/`SECURITY_SCAN_IMAGE_VERSION` 是否可从 TCR 拉取

**解决步骤**：

- 变量未配：按 [10-新手接入指南](10-新手接入指南.md) "必配变量" 配齐，SAST/SCA 的项目 ID/Token 向 App Security 团队申请
- DockerScan 无镜像：先确保 `build-container` 成功
- 扫描镜像拉取失败：App Security 团队确认镜像名与版本
- ariba 后端限定安全扫描仅在 UAT 分支触发——非 UAT 分支不跑扫描是预期行为

**如果无效怎么办**：贴扫描 job 日志给 App Security 团队。安全扫描默认 `allow_failure: true`，失败不阻断部署，但合规上应修复。

## 审批门禁失败

**错误现象**：`approval` 或 `appsec_approval` job 失败。

**适用环境**：tag 发版流水线。

**诊断步骤**：

1. `release-approval` 失败：检查日志是否输出 "RELEASE_MANAGER should not run this job"——即 Release Manager 本人点了批准
2. `appsec_approval` 失败：检查日志是否输出 "is NOT an approver"——操作人不在 `APPSECURITY_APPROVERS` 列表

**解决步骤**：

- release-approval：由 Release Manager 之外的第二人重新手动触发该 approval job
- appsec-approval：由 `APPSECURITY_APPROVERS` 变量列表中的 AppSec 人员触发；列表不全或人员变动 → App Security 团队更新变量

**如果无效怎么办**：联系 App Security 团队确认审批人列表与发版策略。审批 job 为 `allow_failure: false`，失败会阻断生产部署，不可跳过。

## 流水线根本没触发

**错误现象**：push 代码或打 tag 后 GitLab（`gitspace.wuxibiologics.com`）没有产生 Pipeline。

**适用环境**：所有项目。

**诊断步骤**：

1. 确认 `.gitlab-ci.yml` 存在于根目录且 include 路径正确（`project: devops/team-cicd`、`ref`、`file` 三段）
2. 确认 team-cicd 仓库（`git@gitspace.wuxibiologics.com:devops/team-cicd.git`）对应分支存在该工作流文件
3. 分支 push 不触发且有打开的 MR：预期行为，MR 流水线代替分支流水线
4. tag 不触发：确认 `release-rules` 要求的 `CI_COMMIT_TAG` 条件
5. Runner 不可用：流水线 stuck 在 pending，无 runner tag 匹配

**解决步骤**：

- include 路径错：修正 `ref`（团队分支名）和 `file`（团队目录下文件名）
- Runner pending：确认项目 `default.tags` 与可用 runner tag 匹配（`tencent`/`platform`/`devops`/`atlas`/`mno`/`security`/`shared`），缺 runner → DevOps 团队

**如果无效怎么办**：贴 `.gitlab-ci.yml` 与 Pipeline pending 截图给 DevOps 团队。

## 构建镜像拉取失败：TCR 权限或名称不匹配

**错误现象**：build-app job 在 docker pull 构建镜像时报 pull access denied 或 image not found，但 docker login 成功。

**适用环境**：所有使用共享 TCR 镜像的构建 job。

**诊断步骤**：

1. 确认 docker login 成功（REGISTRY_USER/REGISTRY_PASSWORD 有效）但 docker pull 被拒——这是 TCR 命名空间权限问题，不是凭证问题
2. 检查构建镜像名称是否与 TCR 实际存在的镜像匹配——base-image-catalog 中记录的名称可能与 TCR 实际不一致（已发现 catalog 记录的 devops/jdk21_with_gradle_mvn 在 TCR 不存在）
3. 确认项目所在 GitLab group 是否有目标 TCR 命名空间的拉取权限——TCR 权限按 GitLab group 级别配置（DOCKER_AUTH_CONFIG），不同 group 权限不互通（如 ariba group id=2310 有 devops 命名空间权限，sf-btp-development group id=1161 没有）

**解决步骤**：

- TCR 权限问题：同一 REGISTRY_USER/REGISTRY_PASSWORD 能 login 但不能 pull 其他 group 的命名空间镜像 → 找 IT/运维为目标 GitLab group 配置目标 TCR 命名空间的拉取权限
- 镜像名不匹配：核对 TCR 实际镜像名（在 TCR 控制台 cld93-ld-tcr-premium-sh-001.tencentcloudcr.com 或用 docker pull 验证），不要轻信 base-image-catalog 中的名称——目录需要定期与 TCR 实际内容同步
- 镜像不存在：使用已验证存在的替代镜像（如 devops/jdk21.0.11_10-jdk-ubi9-minimal_mvn3.9.6:feat-ariba-144059 替代 JDK17 镜像，JDK21 向后兼容）

**如果无效怎么办**：贴 docker login + docker pull 完整日志给 DevOps 团队 + IT/运维。

## ArgoCD Pod CrashLoopBackOff：容器端口/权限问题

**错误现象**：ArgoCD 应用 Pod 处于 CrashLoopBackOff 状态，容器日志显示 ind() failed (13: Permission denied)。

**适用环境**：ArgoCD GitOps 部署模式（rgocd.uat-halo-01.tencent.wuxibiologics.com），容器以非 root 用户运行。

**诊断步骤**：

1. 查看 Pod 日志（kubectl logs 或 ArgoCD 控制台 Logs 标签），确认是否为端口绑定权限错误（
ginx: [emerg] bind() to 0.0.0.0:80 failed (13: Permission denied)）
2. 检查容器 
unAsUser 是否为非 root（如 1000）——非 root 用户无法绑定 1024 以下端口
3. 检查 containerPort 与应用实际监听端口是否一致——环境变量改了（如 IPMS_SERVER_PORT=8080）但应用配置模板（如 nginx.conf.template）中 listen 仍写死为 80，改动无效
4. 检查是否已挂载必要的 emptyDir 卷（如 /var/cache/nginx、/var/run、/var/log/nginx、/tmp）——缺少可写卷会导致非 root 容器启动失败

**解决步骤**：

- 端口绑定权限：将 containerPort 和应用监听端口统一改为 1024 以上（如 8080），同时修改应用配置模板使 listen 读取环境变量而非写死
- nginx 特例：如果镜像是 nginx 基础镜像，default.conf.template 中的 listen 默认写死为 80——需要用 ConfigMap 覆盖模板（listen 8080），或重建镜像修改默认配置
- emptyDir 缺失：在 Deployment 中补充 /var/cache/nginx、/var/run、/var/log/nginx、/tmp 的 emptyDir 挂载

**如果无效怎么办**：贴 Pod 日志 + Deployment manifest 给应用负责人 + DevOps 团队。

## 镜像 tag 不匹配导致部署失败

**错误现象**：deploy-container 或 ArgoCD 同步时找不到目标镜像 tag，或部署了错误的镜像版本。

**适用环境**：UAT/PROD 部署。

**诊断步骤**：

1. 检查部署引用的镜像 tag 格式——CI 自动生成的 tag 格式为 $CI_COMMIT_REF_SLUG-（如 eat-ariba-150946），仅适合 UAT 测试
2. 生产部署要求正式版本号 tag（如 1.2.0），如果 GitOps 仓库或部署变量引用的是分支构建 tag，生产环境不会接受
3. 确认 tag 发版流水线中 build-app 是否切换了构建 profile（如 Maven 的 uild:prod vs uild:test）

**解决步骤**：

- UAT 部署：使用 CI 自动生成的分支 tag 即可（$CI_COMMIT_REF_SLUG-）
- 生产部署：打 annotated tag 触发发版流水线，使用正式版本号作为镜像 tag；不要拿分支构建的镜像直接上生产
- 构建 profile 不匹配：确认 tag 流水线的 build-app 使用 production profile（如 Maven -Pbuild:prod），非 tag 流水线使用 test profile

**如果无效怎么办**：确认镜像 tag 策略与 DevOps 团队对齐，确保 UAT 和生产使用不同规则。
