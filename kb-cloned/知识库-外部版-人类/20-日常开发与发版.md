# 日常开发与发版

## 目标

读完本文件，开发者能够：判断流水线何时触发；查看流水线状态与进度；完成 dev/uat/prod 各环境部署；走完 tag 发版流程；正确开启与使用安全扫描；为自建 CI 项目叠加公司安全扫描。

## 前置条件

- 项目已完成 CI/CD 接入（见 [10-新手接入指南](10-新手接入指南.md)）
- 已掌握分支与 MR 的关系
- 有 GitLab UI 访问权限

## 流水线触发场景

Common 层 `app-workflow.yml` 默认在以下场景触发：merge_request 事件、web 手动触发、分支 push、tag push。**当前分支已有打开的 MR 时，分支 push 流水线不跑**（避免与 MR 流水线重复），只跑 MR 流水线。

各 job 的具体触发由 `rules/` 控制：

| 规则 | 触发场景 | 典型 job |
|------|----------|----------|
| `default_dev_fix_rules` | 分支 push 或 MR | 构建、部署 dev、安全扫描 |
| `merge_request_rules` | 仅 MR | Sonar 质量门禁 |
| `default_uat_rules` | 默认分支（master/main） | UAT 部署 |
| `release_rules` | tag | 生产部署、审批、release manager |

## 查看流水线状态

在 GitLab UI 进入项目 → Build → Pipelines（或 CI/CD → Pipelines），查看流水线状态。点开单条 Pipeline 可看各阶段 job 状态、日志、产物。流水线地址形如 `<gitlab-instance>/<project>/-/pipelines/<pipeline-id>`。

镜像 tag 格式默认 `$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`（如 `main-12345`），在构建日志和镜像仓库中可用此 tag 查找对应产物。部分团队（如 dvcopilot）用 `$CI_COMMIT_SHA` 作为 tag，便于按 commit 精确定位。

## 部署到各环境

### dev 环境

`deploy-dev` job，手动触发，dev/fix 分支或 MR 可见。

### uat 环境

`deploy-uat` job，手动触发。部分团队（如 axiom）已改为 main 分支 push 或目标为 main 的 MR 时自动触发。ArgoCD 模式通过更新 GitOps 仓库版本文件部署；VM 模式通过 SSH 执行 `docker compose up`。部署 job 依赖 `build-container` 成功。

### prod 环境

`deploy-prod` job，仅 tag 触发，手动确认，`allow_failure: false`（失败阻断发版）。详见下方"发版流程"。

## 发版流程（打 tag 发生产）

打 git tag 触发 release 流水线，流程如下：

1. 在默认分支（master/main）打 tag，触发 tag 流水线
2. `.pre` 阶段 `set-release-manager` 自动记录打 tag 的用户为 Release Manager
3. 流水线跑构建、镜像、安全扫描
4. `create-release` 阶段创建发布
5. `approval` 阶段两道审批：
   - **release-approval**：需 Release Manager 之外的第二人手动确认。script 会检查操作人邮箱是否等于 `release_variables.txt` 中的 `$RELEASE_MANAGER`，相等则失败
   - **appsec-approval**：需 `APPSECURITY_APPROVERS` 列表中的 AppSec 人员手动确认。操作人不在列表则失败
6. 审批通过后 `deploy-prod` 手动部署生产（`allow_failure: false`）
7. `finalize-release` 收尾

**关键设计**：release-approval 的机制是 Release Manager 不能批准自己的发布——必须第二人操作。

## MR 与分支流水线差异

Common 层用 `!reference` 复用规则片段。`default_dev_fix_rules` 同时匹配分支 push 和 MR，但部分 job 用 `merge_request_rules` 仅 MR 触发（如 Sonar 质量门禁，在合并前拦截）。

team-cicd 团队可覆盖 job 的 rules 实现定制策略。如 axiom 团队让 `deploy-container-uat` 在 main 分支 push 或目标为 main 的 MR 时自动部署 UAT，`ThreatModeling` 限定 main 分支 + MR 触发以在合并前拦截威胁。

## 安全扫描使用

Common 层 `stages/security-scan.yml` 提供 4 类扫描，默认 `allow_failure: true`（不阻断部署），通过变量开关：

| 扫描类型 | 开关变量 | 依赖 |
|----------|----------|------|
| SAST | `SAST_PROJECT_ID` + `SAST_APP_ID` + `Has_SAST: "1"` | — |
| SCA | `SCA_PROJECT_TOKEN` + `Has_SCA: "1"` | — |
| DockerScan | `TENABLE_SCANTARGET_DOCKER_REPOSITORY_URL` | `build-container` 成功 |
| ThreatModeling | `Has_ThreatModel: "1"` | — |

扫描结果输出到 `./security-scan-results/`，`GenSecurityReport` 生成 HTML 报告并发送至 `$GITLAB_USER_EMAIL`。`SECURITY_ENABLE_BLOCK` 控制是否阻断（默认 `"0"` 不阻断）。

## 自建 CI 项目叠加安全扫描

不引用 `app-workflow` 的自建 CI 项目，参考 team-cicd 的 dvcopilot 团队做法：单独 include Common 层 `stages/security-scan.yml`，只裁剪安全扫描段，用 rules 限定在特定分支（如 `PRD` 或 `feat/securityscan`）触发，并指定共享 dind runner（不能用自建 VM 的 shell runner）。

dvcopilot 团队本轮接 SCA + ThreatModeling；DockerScan 因未开 `BUILD_CONTAINER` 按模板 docker rule 自然不触发（非手动禁用，不触红线）。

## 注意事项

- **审批门禁不可跳过**：`approval` 与 `appsec_approval` 为 `allow_failure: false`，失败阻断发版，详见 [40-合规须知](40-合规须知.md)
- **红线**：不得给 `DockerScan` / `SCA` / `GenSecurityReport` / `approval` / `appsec_approval` / `set-release-manager` 写 `rules: when: never`
- **镜像 tag 可追溯**：默认 `$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID` 或 `$CI_COMMIT_SHA`，发布时给同一 SHA 打 git tag 直接 pull 同一镜像，不重建
- **变量继承**：Team 层覆盖 job 时仅写需覆盖属性，其余继承不变

## 升级路径

- 流水线不触发且不符合规则 → DevOps 团队检查 rules 配置
- MR 与分支行为差异不符预期 → 检查团队工作流是否覆盖 job rules → DevOps 团队
- 扫描配置或结果疑问 → App Security 团队
- 发版审批被卡 → 确认操作人是否符合门禁要求（非 Release Manager / 在审批人列表），符合仍被挡 → App Security 团队
