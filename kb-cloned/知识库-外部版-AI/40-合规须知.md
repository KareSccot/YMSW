# 合规须知

## 适用范围

**适用对象**：所有使用公司 CI/CD 体系的应用项目，无论走 Common 层标准模板还是自建 CI 叠加安全扫描。

**不适用场景**：无——只要代码经公司 GitLab 流水线发布，即受本须知约束。

## 安全扫描合规

**政策结论**：项目须按 App Security 团队要求开启对应安全扫描；扫描 job 默认 `allow_failure: true`（失败不阻断部署），但 `SECURITY_ENABLE_BLOCK` 可设为阻断模式。

**四类扫描**：

- **SAST**（静态应用安全测试）：配 `SAST_PROJECT_ID`+`SAST_APP_ID`+`Has_SAST: "1"`
- **SCA**（软件成分分析）：配 `SCA_PROJECT_TOKEN`+`Has_SCA: "1"`
- **DockerScan**（镜像扫描）：配 `TENABLE_SCANTARGET_DOCKER_REPOSITORY_URL`，依赖 `build-container` 成功
- **ThreatModeling**（威胁建模）：配 `Has_ThreatModel: "1"`

**条件与例外**：

- 扫描结果输出到 `./security-scan-results/`，`GenSecurityReport` 生成 HTML 报告并发送至 `$GITLAB_USER_EMAIL`
- 部分团队（如 axiom）将 ThreatModeling 限定在 main 分支与 MR 触发，合并前拦截威胁
- 自建 CI 项目（如 dvcopilot）可只叠加安全扫描段，但须用共享 dind runner，不能用自建 VM 的 shell runner

**违反后果**：未开启规定扫描项的项目不予发版；App Security 团队有权阻断不合规部署。

**负责人及更新日期**：App Security 团队；2026-08-17。

## 审批门禁合规

**政策结论**：生产发版须经两道审批门禁，均为 `allow_failure: false`（失败即阻断发版，不可跳过）。

**两道门禁**：

- **release-approval**：Release Manager 之外的第二人手动确认。Release Manager 由 `.pre` 阶段 `set-release-manager` 自动记录（打 tag 的用户）。机制上 script 检查 `$GITLAB_USER_EMAIL == $RELEASE_MANAGER` 则 `exit 1` 失败
- **appsec-approval**：`APPSECURITY_APPROVERS` 变量列表中的 AppSec 人员手动确认。操作人不在列表则 `exit 1` 失败

**条件与例外**：

- 两道门禁均仅 tag 发版流水线触发（release-rules）
- 门禁 job 为 manual + `allow_failure: false`：必须人工触发且必须通过，否则 `deploy-prod` 不执行

**违反后果**：跳过或禁用审批门禁属严重违规。dvcopilot 团队的红线注释明确：**不得给 `approval` / `appsec_approval` / `set-release-manager` 写 `rules: when: never`**。

**负责人及更新日期**：App Security 团队；2026-08-17。

## 镜像合规

**政策结论**：所有部署镜像须来自公司镜像仓库，镜像 tag 须可追溯至具体流水线或 commit。

**合规要求**：

- 镜像推送地址：`${DOCKER_REGISTRY}/${SERVICE_REPOSITORY}/${IMAGE_NAME}:${IMAGE_TAG}`
- 默认 tag：`$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`（可追溯流水线）
- 按需 tag：`$CI_COMMIT_SHA`（dvcopilot 团队做法，按 commit 追溯）
- `SERVICE_REPOSITORY` 不得保留默认值 `change_me`，须为本团队实际命名空间

**条件与例外**：无例外。自建 CI 不推 registry 的项目（如 dvcopilot VM 本地构建）不适用镜像 tag 规则，但仍须可追溯 commit。

**违反后果**：使用非公司镜像仓库或不可追溯 tag 的镜像不予部署；环境负责人有权拒绝。

**负责人及更新日期**：DevOps 团队 + App Security 团队；2026-08-17。

## 红线清单（禁止行为）

**政策结论**：以下行为属合规红线，任何项目不得违反。

**禁止行为**：

1. 给 `DockerScan` / `SCA` / `GenSecurityReport` / `approval` / `appsec_approval` / `set-release-manager` 写 `rules: when: never`——禁用即绕过安全门禁
2. 在 `.gitlab-ci.yml` 或 CI 变量中硬编码 Token/密码/Access Key——须用 GitLab CI/CD Variables（masked）
3. 暴露内网地址、registry 凭证、内部 API 路径到外部可见文档或日志
4. 生产部署跳过审批门禁直接 `deploy-prod`

**条件与例外**：无例外。dvcopilot 团队虽自建 CI，但明确保留安全扫描段并遵守红线，可作为自建 CI 叠加扫描的合规范例。

**违反后果**：App Security 团队 + DevOps 团队联合处置，可能撤销项目发版权限。

**负责人及更新日期**：App Security 团队；2026-08-17。

## 外包与敏感信息边界

**政策结论**：外部用户/外包人员只走 GitLab UI 操作，不接触内部 API、Token、服务源码。

**边界**：

- ✅ 允许：在 GitLab UI 配置 CI/CD Variables、查看 Pipeline、手动触发 deploy/approval job
- ✅ 允许：编写自己的 `.gitlab-ci.yml`、`Dockerfile`、`docker-compose.yml`
- ❌ 禁止：用 curl/API 调用内部 `gitlab-management` 服务、使用 PRIVATE-TOKEN 操作 GitLab API
- ❌ 禁止：获取内部脚本源码（如安全扫描镜像内逻辑）、内网服务地址、registry 凭证明文

**条件与例外**：内部 API 操作（如 ArgoCD 版本更新、GitLab 文件更新）由 CI Job 内部完成，外部用户无需也不应直接调用。

**违反后果**：违规获取或泄露内部凭证/地址属安全事件，按公司安全规范处置。

**负责人及更新日期**：App Security 团队；2026-08-17。

## 升级路径

**政策结论**：合规疑问与审批被阻时，按场景找人。

**找人规则**：

- 不确定要开哪些扫描 → App Security 团队
- AppSec 审批人列表需更新 → App Security 团队
- 发版被审批门禁挡住 → 先确认操作人是否符合门禁要求（非 Release Manager / 在审批人列表），符合仍被挡 → App Security 团队
- 镜像合规疑问 → DevOps 团队 + App Security 团队
