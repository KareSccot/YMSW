# 前置条件与总览

## CI/CD 三层架构

**架构层级**：应用层 → Team 层 → Common 层，通过 GitLab CI 的 `include` 机制层层组合。

**Common 层（cicd-template 仓库）**：提供通用流水线模板，核心设计是"Workflows 组合 Stages，Stages 引用 Jobs 实现，Rules 控制 Job 何时出现"。

- **Workflows**（`workflows/`）：完整流水线骨架。`app-workflow.yml` 是应用基础流水线，`iac-workflow.yml` 是基础设施流水线
- **Stages**（`stages/`）：阶段定义，每个 stage 文件组合对应 job + rules
- **Jobs**（`jobs/`）：具体实现脚本，按类别组织（build/deploy/iac/quality/security/release/approval）
- **Rules**（`rules/`）：可复用的触发条件，控制 job 在哪些场景出现

**Team 层（team-cicd 仓库，按分支组织）**：每个业务团队一个分支，通过 `include` 引用 Common 层 `app-workflow.yml`，再用变量开关和规则覆盖定制自己的工作流。团队分支示例：smart-esg、ariba、atlas-team、axiom、official-website 等。

**应用层**：项目根目录 `.gitlab-ci.yml`，`include` 所属团队的工作流文件（如 `team-cicd` 的 `<team>/backend-workflow.yml`）。

## app-workflow 流水线阶段

**阶段顺序**：流水线按以下阶段顺序执行。

**阶段列表**：

1. `.pre` — 预备（如设置 release manager，仅在 tag 流水线触发）
2. `build` — 构建（源码编译 + 镜像构建）
3. `test` — 测试
4. `quality` — 质量与安全扫描（SAST/SCA/DockerScan/ThreatModeling/Sonar）
5. `security-report` — 生成安全扫描报告
6. `deploy-dev` — 开发环境部署（手动）
7. `deploy-uat` — UAT 环境部署（手动）
8. `create-release` — 创建发布
9. `approval` — 审批门禁（release approval + appsec approval，手动，失败即阻断）
10. `deploy-prod` — 生产部署（手动，失败即阻断）
11. `finalize-release` — 发布收尾
12. `.post` — 后置

**关键开关变量**：

- `BUILD_CONTAINER`：`true` 时启用镜像构建与容器部署链路；非 `true` 则走 ArgoCD GitOps 部署
- `DEPLOY_CONTAINER`：`false` 时用 ArgoCD 部署而非容器部署
- `BUILD_TOOL`：`gradle` / `mvn` / `pnpm` 决定用哪个构建 Job
- `BUILD_FOLDER` / `ARTIFACT_FOLDER`：构建源目录与产物目录
- `SERVICE_PORT` / `PACKAGE_NAME` / `IMAGE_NAME`：镜像构建参数

## 构建工具矩阵

**可选招建模工具**：

- **gradle**：`./gradlew $GRADLE_BUILD_OPTS`（默认 `clean build`），产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`
- **mvn**：`mvn package -P${BUILD_ENV} -Dmaven.test.skip=true`，产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`
- **pnpm**：`npm build`（pnpm 镜像内），产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/`
- **docker**：`docker build` + `docker push`，镜像 tag 默认 `$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`

**选择方式**：应用在 `.gitlab-ci.yml` 设 `BUILD_TOOL` 变量，stages/build.yml 按该变量 include 对应构建 stage。

## 部署路径

**两种部署模式**：

- **ArgoCD GitOps 部署**（`DEPLOY_CONTAINER: "false"` 或未开容器）：Job 调用部署服务更新 GitOps 仓库中应用版本文件，由 ArgoCD 滚动部署。适用于 dev/uat/prod
- **VM Docker Compose 部署**（`BUILD_CONTAINER: "true"`）：Job 通过 SSH 上传 docker-compose.yml + 证书到目标 VM，远程执行 `docker compose up`。适用于 uat/prod

## 前置条件

**接入 CI/CD 前需具备**：

- GitLab 账号且有项目仓库的 Developer 及以上权限
- 项目所属团队已在 `team-cicd` 仓库有对应分支和工作流文件
- 确定构建工具（gradle/mvn/pnpm）或仅需容器构建
- 确定部署模式（ArgoCD GitOps 或 VM Docker Compose）
- CI 变量已配置（见 [10-新手接入指南](10-新手接入指南.md) "必配变量"）

## 角色与联系人

**角色职责对照**：

- **DevOps 团队**：CI/CD 模板维护、Team 工作流配置、Runner 管理、接入支持
- **App Security 团队**：安全扫描配置、AppSec 审批、合规红线裁定
- **环境负责人**：dev/uat/prod 环境的部署目标、SSH 凭证、域名/证书
- **Release Manager**：由发起 tag 流水线的用户自动担任，负责走完发版审批

**找人规则**：接入与流水线配置 → DevOps；安全与合规 → App Security；部署环境问题 → 环境负责人；发版审批卡住 → 确认 Release Manager 是否为当前操作人之外的第二人。

## 升级路径

**找不到对应角色时**：

- 流水线配置类问题 DevOps 团队未能解决 → 提交 issue 到 `devops/cicd-template` 或 `devops/team-cicd` 仓库
- 安全审批被拒或合规疑问 → App Security 团队（通过 `APPSECURITY_APPROVERS` 变量中的审批人列表联系）
- 发版卡在 approval 阶段 → 确认 release-approval 需非 Release Manager 本人操作，appsec-approval 需 AppSec 审批人操作
