# 新手接入指南

## 接入 CI/CD 的触发条件

**触发条件**：新项目需要接入公司 CI/CD 流水线，实现自动构建、镜像打包、多环境部署、安全扫描。

**输入信息**：项目 GitLab 仓库地址、所属业务团队名、构建工具（gradle/mvn/pnpm）、部署模式（ArgoCD 或 VM Docker Compose）、服务端口。

**步骤清单**：

1. 确认项目所属团队在 `team-cicd` 仓库存在对应分支（分支名 = 团队名，如 smart-esg、ariba、atlas-team）。不存在则联系 DevOps 团队先建团队工作流
2. 在项目根目录创建 `.gitlab-ci.yml`，include 所属团队的工作流文件。最小模板见下方"接入模板"
3. 在 `.gitlab-ci.yml` 中设置团队定制变量（`BUILD_CONTAINER`、`BUILD_TOOL`、`BUILD_FOLDER`、`ARTIFACT_FOLDER` 等）
4. 在 GitLab UI 配置 CI/CD 变量（路径：项目 Settings → CI/CD → Variables），填入必配变量
5. 若需容器部署，提供 `Dockerfile` 和 `docker-compose.yml`，并设置 `SERVICE_PORT`、`IMAGE_NAME` 等构建参数
6. 提交代码到 dev 分支，触发 MR 流水线验证构建链路通顺
7. 跑通后，按 dev → uat → prod 推进

**输出结果**：项目拥有可运行的 CI/CD Pipeline，含构建、镜像、安全扫描、多环境部署。

**预估耗时**：30-60 分钟（变量与 Dockerfile 已备齐）；含环境凭证协调则 1-2 天。

**升级路径**：步骤 1 团队工作流不存在 → DevOps 团队；步骤 4 变量值不确定 → 对应环境负责人；构建/部署报错 → [30-故障排查](30-故障排查.md)。

## 接入模板（最小 .gitlab-ci.yml）

**模板用途**：新项目引用团队工作流的最小配置，复制后按注释填值。

**最小模板**：

```yaml
include:
  - project: 'devops/team-cicd'
    ref: <team-branch>           # 替换为所属团队分支名
    file: '/<team>/backend-workflow.yml'

variables:
  BUILD_CONTAINER: "true"        # true=容器构建+VM部署；false=ArgoCD GitOps部署
  BUILD_TOOL: "gradle"           # gradle / mvn / pnpm
  BUILD_FOLDER: "."
  ARTIFACT_FOLDER: "build/libs"
  SERVICE_PORT: 8080
  PACKAGE_NAME: ${IMAGE_NAME}
  DOCKER_BUILD_ARGS: "--build-arg BUILD_FOLDER=${BUILD_FOLDER} --build-arg ARTIFACT_FOLDER=${ARTIFACT_FOLDER} --build-arg PACKAGE_NAME=${PACKAGE_NAME} --build-arg SERVICE_PORT=${SERVICE_PORT}"
```

**参数说明**：

- `ref`：team-cicd 仓库中本团队的分支名
- `file`：团队目录下的工作流文件（backend / frontend）
- `BUILD_CONTAINER`：决定部署链路。`true` 走容器构建 + VM Docker Compose；`false` 走 ArgoCD GitOps
- `BUILD_TOOL`：构建工具，对应 Common 层 `stages/build.yml` 按 include 分发

## 必配变量

**变量清单**（在 GitLab UI Settings → CI/CD → Variables 配置）：

| 变量 | 用途 | 由谁提供 |
|------|------|----------|
| `DOCKER_REGISTRY` | 镜像仓库地址 | DevOps 团队（实例级默认） |
| `REGISTRY_USER` / `REGISTRY_PASSWORD` | 镜像仓库登录凭证 | DevOps 团队（实例级默认） |
| `SERVICE_REPOSITORY` | 镜像命名空间 | DevOps 团队 |
| `SECURITY_SCAN_IMAGE_NAME` / `SECURITY_SCAN_IMAGE_VERSION` | 安全扫描镜像 | App Security 团队 |
| `WUXI_DNS` | 构建容器 DNS | DevOps 团队 |
| `UAT_SSH_TARGET` / `UAT_SSH_USER` / `UAT_SSH_PORT` / `UAT_SSH_PRIVATE_KEY` | UAT VM SSH 凭证 | UAT 环境负责人 |
| `UAT_SSL_CERT` / `UAT_SSL_KEY` / `UAT_DEPLOY_PATH` | UAT 证书与部署路径 | UAT 环境负责人 |
| `PROD_*`（同上 prod 前缀） | 生产 VM 凭证与路径 | 生产环境负责人 |
| `APPSECURITY_APPROVERS` | AppSec 审批人邮箱列表（逗号分隔） | App Security 团队 |

**占位说明**：上表中 `DOCKER_REGISTRY` 等实际值用 `<registry>` `<service-name>` 占位，不在本知识库暴露内网地址。具体值由对应团队提供。

## 选择构建工具

**触发条件**：确定项目用什么工具编译源码产出制品。

**输入信息**：项目技术栈（JVM 用 gradle/mvn，前端用 pnpm）。

**步骤清单**：

1. 在 `.gitlab-ci.yml` 设 `BUILD_TOOL` 变量为 `gradle` / `mvn` / `pnpm` 之一
2. `stages/build.yml` 会按 `BUILD_TOOL` 条件 include 对应构建 stage（gradle-build / mvn-build / pnpm-build）
3. 对应 Job 执行：gradle 跑 `./gradlew clean build`；mvn 跑 `mvn package -P<env> -Dmaven.test.skip=true`；pnpm 跑 `npm build`
4. 产物路径：JVM 产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/*.jar`；前端产物 `${BUILD_FOLDER}/${ARTIFACT_FOLDER}/`
5. 若不需源码构建只打镜像，设 `build-app` job 为 `when: never`，仅保留 `build-container`

**输出结果**：构建产出制品，作为镜像构建的输入。

**预估耗时**：首次构建 5-15 分钟（拉镜像 + 依赖）。

**升级路径**：构建工具镜像缺包或缺版本 → DevOps 团队（构建镜像由其维护）。

## 选择部署模式

**触发条件**：确定应用部署到 K8s（ArgoCD）还是 VM（Docker Compose）。

**两种模式**：

- **ArgoCD GitOps**：设 `BUILD_CONTAINER: "false"` 或 `DEPLOY_CONTAINER: "false"`。部署 Job 调用部署服务更新 GitOps 仓库版本文件，ArgoCD 自动滚动。dev/uat/prod 各有 deploy job
- **VM Docker Compose**：设 `BUILD_CONTAINER: "true"`。部署 Job 通过 SSH 上传 compose 文件 + 证书到 VM，远程 `docker compose up`。仅 uat/prod

**输入信息**：目标环境类型（K8s 集群或 VM）、是否已有 docker-compose.yml。

**步骤清单**：

1. ArgoCD 模式：确认目标环境在 GitOps 仓库有对应 `app-values/<env>/<team>/<service>/<env>-<region>.yaml`
2. VM 模式：提供 `docker-compose.yml`，配置 `DOCKER_COMPOSE_FILE`、`SSH_TARGET` 等变量
3. 在团队工作流中覆盖对应 deploy job 的 rules 以匹配分支策略（如 feat/axiom 团队让 main 分支自动部署 UAT）

**输出结果**：应用部署到目标环境。

**升级路径**：ArgoCD 部署不生效 → DevOps 团队（GitOps 仓库配置）；VM SSH 失败 → [30-故障排查](30-故障排查.md) "SSH 部署失败"。
