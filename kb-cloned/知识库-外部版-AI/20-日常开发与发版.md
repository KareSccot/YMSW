# 日常开发与发版

## 我的流水线在什么场景会触发

**典型问法**：我 push 了代码，流水线怎么没跑？什么时候跑？

**标准答案**：Common 层 `app-workflow.yml` 默认在以下场景触发：merge_request 事件、web 手动触发、分支 push、tag push。**若当前分支已有打开的 MR，则分支 push 流水线不跑**（避免与 MR 流水线重复），只跑 MR 流水线。

**补充说明**：各 job 的具体触发由 `rules/` 控制：

- **dev-fix-rules**：分支 push 或 MR 触发。dev/fix 分支与 MR 的构建、部署 dev、安全扫描走此规则
- **merge-request-rules**：仅 MR 触发。如 Sonar 质量门禁
- **uat-rules**：默认分支（master/main）触发。UAT 部署走此规则
- **release-rules**：tag 触发。生产部署、审批、release manager 设置走此规则

**升级路径**：流水线不触发且不符合上述规则 → DevOps 团队检查 rules 配置。

## 如何查看流水线状态与进度

**典型问法**：我的构建到哪了？怎么看进度？

**标准答案**：在 GitLab UI 进入项目 → Build → Pipelines（或 CI/CD → Pipelines），查看流水线状态。点开单条 Pipeline 可看各阶段 job 状态、日志、产物。流水线地址形如 `<gitlab-instance>/<project>/-/pipelines/<pipeline-id>`。

**补充说明**：镜像 tag 格式为 `$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`，在构建日志和镜像仓库中可用此 tag 查找对应产物。部分团队（如 dvcopilot）用 `$CI_COMMIT_SHA` 作为镜像 tag，便于按 commit 精确定位。

**升级路径**：Pipeline 页面打不开或日志缺失 → DevOps 团队（GitLab 平台问题）。

## 如何部署到 dev / uat / prod

**典型问法**：怎么把代码部署到各环境？

**标准答案**：

- **dev**：`deploy-dev` job，手动触发，dev/fix 分支或 MR 可见
- **uat**：`deploy-uat` job，手动触发（部分团队如 axiom 已改为 main 分支 push 自动触发）
- **prod**：`deploy-prod` job，仅 tag 触发，手动确认，`allow_failure: false`（失败阻断发版）

**补充说明**：ArgoCD 模式下部署通过更新 GitOps 仓库版本文件实现；VM 模式下通过 SSH 执行 `docker compose up`。部署 job 依赖 `build-container` 成功（`needs`）。

**升级路径**：部署 job 不见 → 检查分支是否符合 uat/release rules；部署失败 → [30-故障排查](30-故障排查.md)。

## 如何发版（打 tag 发生产）

**典型问法**：怎么发版？发版流程是什么？

**标准答案**：打 git tag 触发 release 流水线。流程：

1. 在默认分支（master/main）打 tag，触发 tag 流水线
2. `.pre` 阶段 `set-release-manager` 自动记录打 tag 的用户为 Release Manager
3. 流水线跑构建、镜像、安全扫描
4. `create-release` 阶段创建发布
5. `approval` 阶段两道审批：
   - **release-approval**：需非 Release Manager 本人的第二人手动确认
   - **appsec-approval**：需 `APPSECURITY_APPROVERS` 列表中的 AppSec 人员手动确认
6. 审批通过后 `deploy-prod` 手动部署生产（`allow_failure: false`）
7. `finalize-release` 收尾

**补充说明**：`release-approval` 的设计是 Release Manager 不能自己批准自己的发布——script 会检查 `$GITLAB_USER_EMAIL` 是否等于 `release_variables.txt` 中的 `$RELEASE_MANAGER`，相等则 `exit 1` 失败。

**升级路径**：审批被卡 → 确认是否第二人操作（release）/ 是否 AppSec 审批人操作（appsec）；找不到审批人 → App Security 团队。

## 为什么我的 MR 流水线和分支流水线行为不同

**典型问法**：MR 里跑的流水线和直接 push 分支跑的为什么不一样？

**标准答案**：Common 层用 `!reference` 复用规则片段。`default_dev_fix_rules` 同时匹配分支 push 和 MR，但部分 job 用 `merge_request_rules` 仅 MR 触发（如 Sonar 质量门禁，在合并前拦截）。另外当分支有打开的 MR 时，分支 push 流水线被 `when: never` 抑制，只跑 MR 流水线。

**补充说明**：team-cicd 团队可覆盖 job 的 rules 实现定制策略，如 axiom 团队让 `deploy-container-uat` 在 main 分支 push 或目标为 main 的 MR 时自动部署 UAT。

**升级路径**：MR 与分支行为差异不符合预期 → 检查团队工作流是否覆盖了 job rules → DevOps 团队。

## 镜像 tag 怎么命名，怎么查镜像

**典型问法**：构建出的镜像 tag 是什么？去哪查？

**标准答案**：默认镜像 tag 为 `$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID`（如 `main-12345`），推送地址 `${DOCKER_REGISTRY}/${SERVICE_REPOSITORY}/${IMAGE_NAME}:${IMAGE_TAG}`。dvcopilot 团队用 `$CI_COMMIT_SHA` 作为 tag，便于按 commit 拉取。

**补充说明**：tag 的好处是可追溯——`$CI_COMMIT_REF_SLUG-$CI_PIPELINE_ID` 能定位到具体流水线，`$CI_COMMIT_SHA` 能定位到具体 commit。发布时给同一个 SHA 打 git tag，直接 pull 同一个镜像，无需重建。

**升级路径**：镜像 push 失败 → [30-故障排查](30-故障排查.md) "镜像构建/推送失败"。

## 如何用安全扫描

**典型问法**：怎么开启 SAST / SCA / DockerScan / ThreatModeling？

**标准答案**：Common 层 `stages/security-scan.yml` 提供 4 类扫描，默认 `allow_failure: true`（不阻断部署），通过变量开关：

- **SAST**：设 `SAST_PROJECT_ID` + `SAST_APP_ID` + `Has_SAST: "1"`
- **SCA**：设 `SCA_PROJECT_TOKEN` + `Has_SCA: "1"`
- **DockerScan**：设 `TENABLE_SCANTARGET_DOCKER_REPOSITORY_URL`（依赖 `build-container`）
- **ThreatModeling**：设 `Has_ThreatModel: "1"`

**补充说明**：扫描结果输出到 `./security-scan-results/`，`GenSecurityReport` job 生成 HTML 报告并发送至 `$GITLAB_USER_EMAIL`。`SECURITY_ENABLE_BLOCK` 控制是否阻断（默认 `"0"` 不阻断）。

**升级路径**：扫描配置或结果疑问 → App Security 团队；合规要求详见 [40-合规须知](40-合规须知.md)。

## 自建 CI 的项目怎么叠加安全扫描

**典型问法**：我的项目有自己的一套 build/deploy，怎么接入公司安全扫描？

**标准答案**：参考 team-cicd 的 dvcopilot 团队做法——单独 include Common 层 `stages/security-scan.yml`，只裁剪安全扫描这一段，用 rules 限定在特定分支（如 `PRD` 或 `feat/securityscan`）触发，并指定共享 dind runner（不能用自建 VM 的 shell runner）。

**补充说明**：dvcopilot 团队的红线注释明确：**不得给 DockerScan / SCA / GenSecurityReport / approval / appsec_approval / set-release-manager 写 `rules: when: never`**——这些是合规门禁，禁用即违反红线。

**升级路径**：自建 CI 叠加扫描的配置 → DevOps 团队 + App Security 团队。
