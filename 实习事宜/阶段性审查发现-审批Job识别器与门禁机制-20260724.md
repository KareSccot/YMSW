## 二、我得到了什么结论

### 结论 A：第二位专家的质疑**成立，且比他说的更严重**

专家说"靠命名约定识别审批 Job 不可靠"——这点对。但根因比命名更深：

- **命名三套分隔符混用**：文件 `appsec-approval.yml`（连字符）↔ 模板 `.appsec_approval`（下划线）↔ Job A 干脆叫泛词 `approval`（无前缀，跟文件名都不对应）。
- **没有共同模板父**：`.approval` 和 `.appsec_approval` 互不继承、无共同 base，extends 链只有一层。专家设想的"extends 自某个审批基类"在仓库里根本不存在。
- **`when:manual`+`allow_failure:false` 不区分审批与部署**：deploy-prod/deploy-container-prod 都有这俩字段。*（订正：初稿曾误把 `set-release-manager` 也列入此组，实际 [preparations.yml:5-8](stages/preparations.yml) 它是 `stage:.pre`+`when:always`+`allow_failure:false`，属 .pre 阶段 always 运行 Job，不在审批/部署 manual 组内。不影响结论——仅说明 manual+allow_failure 组合仍横跨审批与部署。）*
- **没有任何外部审批 API 调用**：专家寄望的"审批 Job 调 GitLab approvals API / 企业 BPM"在全库根本不存在。审批就是十几行内联 shell 比对 `$GITLAB_USER_EMAIL` 与某个变量。
- **补入新发现（grep 核实）**：全库 grep `stage: approval` 仅命中 [approval.yml:7](stages/approval.yml)、[approval.yml:17](stages/approval.yml)，恰为两个审批 Job，**0 假阳性**；`set-release-manager` 用保留字 `stage:.pre`，不落 `approval`。故在**当前 Common 层**，`stage:approval` 单信号即 0 假阳性的审批 Job 识别器，比"目录路径 + stage 值"两信号更干净。**但此 0 假阳性仅 Common 层成立**——业务线层若复用 `stage:approval` 值或在 `stages:` 列表塞别的 stage 名，假阳性仍可能出现。

### 结论 B：专家的解决方案**部分有效，有盲区**

"目录 + extends + 命名"三信号里——extends 项在仓库实际不成立（无共同父），真正起作用的只有"目录路径 + stage 值"两信号，extends 是冗余项。更根本的盲区：专家把"识别单个审批 Job"当目标，但首切片真正目标是"**门禁完整性判定**"，识别只是中间一步。

### 结论 C（最关键、也是要改的核心理由）：**门禁靠 `stages:` 顺序，不靠 needs**——这推翻了计划书现有论述

这是我和 Plan 代理一起查实的**硬事实**（*订正：首条 needs 描述初稿有误，已据第二位专家复核 + 亲自核查订正*）：

- [stages/argo-deploy.yml:29-37](stages/argo-deploy.yml) 的 `deploy-prod`：**根本没有 needs 字段**（初稿误记为"needs 只有 [build-container]"，实际那是同文件 `deploy-dev`(L15-16)/`deploy-uat`(L26-27) 的 needs）。
- [stages/docker-deploy.yml:27-44](stages/docker-deploy.yml) 的 `deploy-container-prod`：`needs` 为 `[build-container]`（[docker-deploy.yml:44-45](stages/docker-deploy.yml)）。
- **两者的 needs 都不含任何审批 Job**（deploy-prod 无 needs；deploy-container-prod 的 needs 不含审批）。审批 Job 从来没被 needs 挂到部署 Job 上。
- 门禁的真正机制是 [workflows/app-workflow.yml:13-23](workflows/app-workflow.yml) 的 `stages:` 列表顺序——`approval`（第 21 行）排在 `deploy-prod`（第 22 行）之前，加上 GitLab"同 stage 内 Job 全完成才进下一 stage"的串行语义。

**由此推出三个必须改的地方**：

1. **第 633 行示例是无中生有**：计划书写"deploy-container-prod 新增 needs: [build-container]，但移除了对 appsec_approval 的 needs"——但代码里 deploy-container-prod **从来没有过**对 appsec_approval 的 needs。示例描述的缺陷构造在代码里不存在。
2. **第 423 行"数学结构未变"不成立**：原文说首切片缺陷"仍是下游出现但上游缺失或条件域不一致"（needs DAG 可达性）。但审批门禁的数学结构是 **stage 偏序覆盖 + 层级集合包含**，不是 needs 可达性。结构变了。
3. **第 389 行"Prover"表述与代码不符**：原文称"Common 层内置 Appsec Security Prover"，实际 [appsec-approval.yml](jobs/approval/appsec-approval.yml) 是 16 行内联 shell 比对 email 列表，无任何 Prover 抽象。

### 结论 D：更优方案（我推荐的识别器设计）

- **识别信号分层**：P0 注册表签名匹配（确定性，Common 层 0 误报）→ P1 业务线声明式注解 → P2 LLM 仅诊断疑似分类 → 未识别一律进 `unresolved` 取保守值（绝不默认当审批或非审批），精准覆盖计划书第 767 行的"把团队内部 Pro 误当作安全层 Approve"失败模式。
- **门禁判定双图叠加**：needs 图（保留，检构建依赖齐全）+ stage 偏序图（新增，检审批有序+层级齐全）。审批门禁完整性由 stage 偏序图判定。
