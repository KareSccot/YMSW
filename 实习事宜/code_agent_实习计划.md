# gitlab_ci_agent_深度分析

# 面向 GitLab CI/CD 三大流程与多层审批的合规守护 Agent

## 定义主次关系

正确的关系应该是：

```text
CI 配置分析器 / 条件依赖检查器
不是最终项目
而是 Agent 可以调用的确定性工具之一
```

真正的项目应该收敛为：

> **面向 GitLab CI/CD 三大流程与多层审批的合规守护 Agent**

守护的不是某一个仓库，而是公司所有业务线接入 CI/CD 时都要遵守的同一套交付与治理契约——
三大流程（分支/MR 流水线、主干流水线、发版流水线）与多层审批（MR Approve / Team 层 / 安全层 / 发版 Approve）。
这套契约目前没有人/工具在系统性地守护，Agent 正好填这个空白。

第一个细分场景则是：

> **针对发版流程审批门禁完整性的合规守护 Agent**

这样，原来的条件依赖检查器只是 Agent 的一个 Tool。

再往上一层，这个合规守护 Agent 本身也不是终点。它属于更大概念的一个垂直子能力：

```text
Coding Agent
├── 业务代码生成与修改
├── 单元测试生成
├── 普通代码审查
├── 安全代码审查
├── 依赖升级
└── CI/CD 流程与审批契约守护
      └── 当前研究重点
```

通常说的 Coding Agent 覆盖完整的软件开发流程：

```text
读取需求或 Issue
→ 分析代码仓库
→ 修改业务代码
→ 编写测试
→ 运行测试
→ 修复失败
→ 创建 Commit 或 Merge Request
→ 参与代码审查
```

而当前规划的合规守护 Agent，只覆盖其中一个边界明确、容易验证的窄区域：

```text
读取业务线仓库变更（MR / 主干推送 / 发版 tag）
→ 理解变更触及哪几段流程、牵动哪些审批门禁
→ 规划跨流程验证场景
→ 调用确定性工具检查门禁与依赖
→ 生成 YAML 修复补丁
→ 自验证
→ 输出 MR 评论 / 发版门禁建议
```

所以本项目是 Coding Agent 中一个边界明确、容易验证的垂直子能力。保持窄边界，但能力沉淀要面向未来可被吸收。

> **变更说明（相对上一版）**：上一版项目题为"面向共享 GitLab CI 模板变更的智能审查与修复 Agent"，
> 守护对象是 `cicd-template-Master` 这一个 Common 层仓库。本版把守护对象从"单仓库的 rules/needs 一致性"
> 提升为"全公司业务线都要遵守的三大流程 + 多层审批契约"，使项目天然覆盖各业务线、回应"宏大"要求。
> 工程骨架（确定性检测、可插拔工件接口、自验证闭环等）不变；首切片由"rules/needs DAG 一致性"
> 调整为"发版审批门禁完整性"，但原 DAG 一致性检测仍是核心确定性工具之一（详见第四章"变更说明"）。

## 一、为什么单纯检测不需要 AI

以模板仓库里的问题为例：

```yaml
deploy-container-prod:
  needs:
    - build-container
  extends:
    - .release_rules
```

而：

```yaml
build-container:
  extends:
    - .default_dev_fix_docker_rules
```

前者出现在 Tag Pipeline，后者主要出现在 Branch/MR Pipeline。

判断两者条件域不一致，用规则引擎完全可以完成：

```text
deploy-container-prod 存在
且 build-container 不存在
→ DAG 无效
```

这类逻辑：

*   可精确计算；
*   可重复验证；
*   不应该交给大模型；
*   用大模型反而可能产生幻觉。

因此，**检测器必须是确定性的**。

## 二、为什么不直接做通用 Code Agent，但又不能只做 CI 检测器

Leader 批评"选题太窄太小，要宏大一点，要能在将来帮助到各个业务线"——这个批评是对的，但需要先想清楚"窄"在哪、"宏大"该怎么实现。

> 以下"窄在六个维度"是对**上一版（v1）锚定 Common 层单仓库**的诊断。本版已把守护对象提升为
> 全公司三大流程 + 多层审批契约，逐一化解了下述六个窄维度（见第四章）。保留这段诊断是为了
> 说清"为什么要演进、演进解决了什么"，而非当前定位。

### 窄在六个维度（对 v1 的诊断）

*   **作用域窄**：只服务 `cicd-template-Master` 一个共享模板仓库，全公司几百个业务开发几乎永远碰不到它。→ 本版化解：守护对象改为全公司业务线都要走的三大流程 + 多层审批契约。
*   **工件类型窄**：Agent 的推理能力（意图理解、影响分析、补丁、自验证）本应是通用能力，却被 GitLab CI YAML 这一工件深度耦合。→ 本版化解：可插拔工件接口（`ArtifactAnalyzer` / `ArtifactVerifier`）保证推理层与工件解耦。
*   **缺陷类型窄**：只处理"下游 Job 出现但上游 needs 不出现"这一种 DAG 不一致，只是变更风险的一个极小子集。→ 本版化解：首切片推广为"发版审批门禁完整性"，并沿演进路径扩到全流程、制品一致性、代码变更驱动。> 注：v4 首切片的缺陷类型是"审批门禁不完整"，含 **needs 缺失**（v3 保留，检构建依赖，如 deploy-container-prod 的 needs=[build-container]）+ **stage 顺序破坏**（审批 stage 不再先于生产部署 stage）+ **审批层级缺失**（required_layers 未被覆盖）三种子型。
*   **数据来源窄**：只读 MR 描述 + Diff。真实影响判断还需要调用图、历史 incident、依赖图、运行时拓扑等富数据。→ 本版化解：后续阶段逐步引入跨流程制品元数据、历史发版记录等富数据。
*   **输出价值窄**：补丁只改 CI YAML。一次变更往往牵动 CI + 部署 + 监控 + 回滚 + 文档，只补 CI 等于修了冰山一角。→ 本版化解：补丁护栏限制只改 rules/needs/extends 与 stages: 列表顺序，但诊断报告覆盖跨流程、跨审批影响，不只盯 CI YAML。
*   **时间维度窄**：只在 MR 时刻介入一次，是点状工具而非伴随式 Agent。→ 本版化解：Agent 可在 MR / 主干推送 / 发版 tag 多时刻介入，覆盖三大流程全段。

症结不是规模小，而是**能力封装的颗粒度小**——把本可做成全公司基建的通用 Agent 能力，绑定到了"单仓库、单工件、单缺陷、单时刻"的极窄场景。本版的全部调整，就是把颗粒度从"单仓库"提升到"公司级流程契约"。

### 但直接跳去做通用 Code Agent 会失败

通用代码审查看起来只是"多看几种文件"，但问题域会突然扩大：

*   业务需求是否实现正确；
*   函数和模块之间的调用关系；
*   数据库事务；
*   并发和线程安全；
*   API 兼容性；
*   安全漏洞；
*   性能退化；
*   单元测试覆盖；
*   不同语言和框架的规范。

如果一开始做通用代码审查，很容易变成：

> 把整个代码 Diff 发给模型，然后让模型输出一些建议。

这种项目与现有代码助手差异不大，效果也难以客观证明。

相比之下，CI 模板审查虽然也复杂，但问题域更有限：

*   Pipeline 是否创建；
*   Job 是否出现；
*   依赖是否存在；
*   部署顺序是否正确；
*   制品是否一致；
*   审批是否被绕过；
*   安全扫描是否被关闭。

这些结果更容易通过 GitLab Lint、Dry-run、图算法和测试场景进行确定性验证。

### 正确的做法：定位宏大，交付窄

宏大不在第一阶段交付什么，而在**能力沉淀是否可被未来复用**。所以正确思路是：

> 第一阶段不开发通用 Coding Agent，而是先实现一个 CI/CD 垂直领域 Agent，解决 GitLab CI 模板变更的审查、测试规划、修复和验证问题。后续再扩展到业务代码变更影响分析、自动测试生成和通用代码审查，最终作为完整 Coding Agent 的交付与验证能力。

这样既保留 Coding Agent 的未来空间，也不会让当前项目失去焦点。

## 三、真正需要 Agent 的地方是什么

关键不是让 Agent 替代规则引擎，而是让它完成规则引擎很难独立完成的四件事。

### 1. 理解修改意图

假设 MR 描述写着：

> 生产发布改为跳过 UAT 直接部署，以加速紧急修复。

Agent 要结合：

*   MR 描述；
*   YAML Diff；
*   三大流程上下文（分支/MR / 主干 / 发版）；
*   多层审批架构（MR Approve / Team 层 / 安全层 / 发版 Approve）；
*   `include` 和 `extends`；
*   部署脚本；

判断实际改动是否实现了这个意图，以及——是否在"加速"的名义下**绕过了安全层 Approve**。

传统检测器只能看到：

```text
Job A 消失
Job B 的 needs 改了
变量 IMAGE_TAG 变了
```

Agent 则需要回答：

> 这次改动意图是紧急修复加速，但删掉了安全层 Approve Job，实际行为违反了多层审批契约——生产部署 Job 仍出现，但所需上游审批门禁已不齐全。

这叫：

> **意图—行为一致性审查**

这里自然语言理解和跨流程、跨审批的推理才真正需要模型。

### 2. 自主生成测试场景

确定性检查器必须有人告诉它测试哪些场景：

```text
push + feature branch
push + main
merge request
tag
schedule
BUILD_CONTAINER=true/false
BUILD_TOOL=mvn/gradle/pnpm
```

变量一多，全量组合会迅速膨胀。

Agent 可以根据本次 Diff 动态决定：

*   哪些 Pipeline Source 受影响；
*   哪些变量需要取边界值；
*   哪些 Job 和环境需要验证；
*   哪些组合没有必要测试。

例如发现 `.release_rules` 被修改后，Agent 可以规划：

```text
本次只重点生成：
1. Tag Pipeline；
2. 非 Tag Pipeline；
3. Tag + BUILD_CONTAINER=true；
4. Tag + BUILD_CONTAINER=false；
5. Tag 下 Argo 与 VM 两种部署路径。
```

这不是让大模型直接判断对错，而是让它：

> **规划该调用哪些确定性测试工具。**

这是典型 Agent 能力。

### 3. 生成多种修复方案并分析取舍

对于：

```text
deploy-container-prod 出现（发版流程）
但所需的安全层 Approve Job 不出现，或条件域与生产部署不一致
```

不是只有一个修复方法。

#### 方案 A：给缺失的 Approve Job 增加 tag 规则，使其在发版流程出现

```yaml
appsec_approval:
  rules:
    - if: $CI_COMMIT_TAG
```

优点：实现简单，恢复门禁。

缺点：若该 Approve 本就不该在发版流程（如团队内部 Pro），可能误加，破坏原治理设计。

#### 方案 B：把生产部署 needs 改为依赖已有的、条件域一致的 Approve

优点：符合原治理设计，不引入不该出现的审批。

缺点：需确认该 Approve 确实覆盖安全要求，可能需人工核实审批范围。

#### 方案 C：把 `needs` 改成 optional

优点：Pipeline 可以创建。

缺点：门禁被绕过，部署一个未审批的状态——不建议。

普通规则引擎能发现冲突，却很难结合仓库目标判断：

> 方案 B 更符合这套模板的长期治理设计，方案 C 不建议采用。

Agent 可以基于：

*   README 中的模板目标；
*   团队发布规范；
*   多层审批架构（MR / Team / 安全 / 发版）；
*   历史 MR；
*   GitLab 变量约定；

生成并排序修复方案。

### 4. 执行"生成—验证—修正"循环

真正的 Agent 不应该只输出一段建议，而应该形成闭环：

```text
读取 MR Diff
→ 分析受影响配置
→ 生成测试计划
→ 调用 GitLab Lint / Dry-run
→ 调用 DAG 检查器
→ 发现失败
→ 生成候选补丁
→ 再次运行验证
→ 补丁失败则修正
→ 最多 N 轮（N ≤ 3）
→ 连续 2 轮失败：回退到"仅报告问题，不生成补丁"
→ 补丁通过后提交给人工审批
```

例如：

```text
第 1 次补丁：
给 build-container 增加 Tag 规则

验证结果：
Pipeline 可以创建，但 Tag 流水线重新构建镜像，
违反制品晋级策略

第 2 次补丁：
生产部署读取 release-manifest.json 中的镜像 Digest

验证结果：
DAG 合法，生产部署引用已有镜像

最终：
生成 MR Suggestion，由开发者确认
```

补丁通过判据：Lint 通过 + DAG Validator 通过 + Dry-run 通过，三者全过。

补丁范围护栏：第一阶段补丁允许修改 `rules` / `needs` / `extends` 与 `workflows/*.yml` 的 `stages:` 列表顺序自身。架构级改造建议（如 release-manifest 制品晋级、重构审批层）放报告"附加观察"，不进入自动补丁循环——避免给开发者一个"改个 stage 顺序却被建议改造整个发布流程"的过重补丁。

这里具备 Agent 的关键特征：

*   有目标；
*   有状态；
*   会规划；
*   会选择工具；
*   会根据反馈修正；
*   最终动作受人工审批控制。

## 四、项目主题与演进路径

### 守护对象：三大流程 + 多层审批

项目锚定的不是某一个仓库，而是公司所有业务线接入 CI/CD 时都要遵守的同一套交付与治理契约。这套契约由两个正交维度构成：

**三大流程（时间轴）**：

```text
① 分支/MR 流水线（feature/fix 分支）
   build → test → dev 部署 → 集成测试 → MR → Review/Approve
   → 合主干时追加：安全扫描 job + Sonar

② 主干流水线（merge 到 master 后）
   → UAT 部署 → 集成测试

③ 发版流水线（tag）
   复用主干已构建 image（无 rebuild）→ tagging
   → 发版前多层 Approve → 生产部署 → 生命周期管理/Release
```

三段各有触发源（分支 push / MR / 主干 push / tag）、各有规则域（dev-fix / uat / release）、各有审批要求。`cicd-template-Master` 的 `rules/` 三件套正是对它们的编码。

**多层审批架构（治理轴）**：

```text
MR Approve     开发者互相审核（内部消化，团队层）
Team 层 Pro    团队内部审批
安全层 Approve     SDLC 安全审批（安全部门，Common 层内置 `appsec_approval` 门禁脚本——内联 shell 比对 `$APPSECURITY_APPROVERS` 与触发者 email，无独立 Prover 组件；Phase-0 Spike 评估是否抽象为可插拔 Verifier）
BPM Pro       待定（pending，暂不用，需时自行集成）
发版 Approve   上述组合后 → 生产部署 Job
```

这套契约目前没有人/工具在系统性地守护。Daryl 的 Skill 做生成，静态检查器做语法，"这次变更是否遵守了跨流程、跨审批的治理契约"这件事是空白。Agent 正好填这个空白，不重叠。

### 当前主题

> **面向 GitLab CI/CD 三大流程与多层审批的合规守护 Agent**
> 形态：MR/发版时的审查者（不与 Daryl 的生成式 Skill 重叠，他生成，Agent 审查）。

第一阶段只支持：

```text
发版流程的审批门禁完整性
```

第一种缺陷只支持：

```text
生产部署 Job 出现，但所需上游 Approve/构建 Job 不齐全或条件域不一致
```

第一种自动修复只支持：

```text
调整 `stages:` 列表顺序 / `rules` / `needs` / `extends`，使审批 stage 先于生产部署 stage 且门禁齐全、条件域一致
```

架构级改造建议（如重构审批层）作为附加观察，不进入自动补丁循环。

**首切片检测规约（needs 图 + stage 偏序图双图叠加）**：

发版流水线（tag 触发）下，生产部署 Job 出现时，须同时满足四条，缺一即判门禁不完整：

```text
(a) 存在：注册表 required_layers 对应的审批 Job 在 tag 条件域被装配；
(b) 有序：审批 stage 在生产部署 stage 之前（按 workflows/app-workflow.yml 的 stages: 列表偏序）；
(c) 层级齐全：required_layers ⊆ present_layers（覆盖 release / security 等必需审批层）；
(d) 无旁路：生产部署 Job 的 needs/extends/stage 改动不得绕过审批 stage。
```

检测由两张图叠加完成，二者是不同的数学结构：

```text
needs 图（v3 保留）：检"构建依赖齐全"——生产部署 Job 的 needs 是否被满足
  （例：deploy-container-prod 的 needs=[build-container]，build-container 须在 tag 条件域出现）。
stage 偏序图（v4 新增）：检"审批门禁有序 + 层级齐全"——审批 stage 是否先于
  生产部署 stage、required_layers 是否被覆盖。
```

> **机制澄清**：本仓库审批门禁靠 `stages:` 列表偏序 + `when: manual` 实现——`approval` stage 排在
> `deploy-prod` stage 之前，GitLab 同 stage 内 Job 全完成才进下一 stage。**不是**靠生产部署 Job 的
> `needs` 指向审批 Job（`deploy-prod` 无 needs，`deploy-container-prod` 的 needs 仅 `[build-container]`）。
> 故审批门禁完整性的判定主体是 stage 偏序图，needs 图只管构建依赖。
>
> 条件域一致（`.release_rules` 被 approval / deploy-prod 共享）在 Common 层是构造性保证、平凡成立，
> 不是首切片检测重点；业务线层若把生产部署 Job 的 extends 从 `.release_rules` 改成非发版条件域
> （如 `.default_dev_fix_rules`），则判违规。

> **变更说明（保留原首切片作为设计参照）**：
> 此前第一阶段首切片为"rules / extends / needs 变更"下的"下游 Job 出现，但必要上游 Job 不出现"
> （即 DAG 条件域不一致）。该缺陷的数学结构**已扩展**：v3 是 **needs DAG 可达性**（下游出现但上游
> 构建 Job 缺失），v4 首切片在此之上新增 **stage 偏序覆盖**（审批 stage 须先于生产部署 stage）与
> **审批层级集合包含**（required_layers ⊆ present_layers）。needs 图仍用于构建依赖齐全性，
> 审批门禁完整性由 stage 偏序图判定，二者叠加为 v4 完整检测。
> 本版把首切片的业务语义从"Job 依赖一致性"推广到"发版审批门禁完整性"，使首切片对齐公司级治理主线、
> 贴合会议所述多层审批、且拥有真实发版数据（发版流水线每条业务线都跑，不像 Common 层 MR 稀缺）。
> 原 DAG 一致性检测仍是 Agent 调用的核心确定性工具之一（needs 图），只是审批门禁判定改由 stage 偏序图承担。

### 演进路径

```text
第一阶段：发版审批门禁完整性守护
  - rules / needs / extends / stages: 列表顺序，聚焦发版流程
  - 意图理解、场景规划、门禁检测、补丁生成、补丁验证、MR 评论
  - 证明 Agent 工作闭环

第二阶段：三大流程全段守护（含 Pipeline 脚本审查）
  - 分支/MR 流程、主干流程、发版流程的阶段齐全与顺序
    如"MR 合主干后才许 UAT 部署""主干未过安全扫描不许 tag"
  - 从 YAML 结构扩展到 Job 中的 Shell 脚本
    Token 泄露、危险命令、缺少 set -e、变量引用错误
    制品一致性破坏、生产阶段重新构建、绕过扫描或审批
  - 仍限定在 CI/CD 领域

第三阶段：跨流程制品一致性
  - 发版 tag 引用的镜像是否真是主干/UAT 验证过的那个
  - Build Once Promote Many 守护

第四阶段：代码变更驱动的流程响应 ← 关键桥梁
  - Agent 读 MR Diff，决定该跑哪些流程测试
  - 改 Dockerfile → 触发容器扫描
  - 改 DB migration → 跑 migration test
  - 改 Helm values → 跑 helm lint
  - 改 Agent Tool Schema → 跑 Tool Calling 回归
  - Agent 始终只懂流程，不懂业务代码，可复制性高

第五阶段：MR 代码审查 + 测试生成
  - 代码风险分析、潜在 Bug 发现、单元测试生成、Pipeline Job 建议补充
  - 仍以"建议"和"候选补丁"为主，不自动合并

第六阶段：完整 Coding Agent
  - 读取 Issue → 修改业务代码 → 修改测试 → 修改 CI 配置
  - 执行 Pipeline → 分析失败 → 自动修复 → 创建 MR
  - 此时合规守护 Agent 成为完整 Coding Agent 的交付与验证子系统
```

> 注：相对原版演进路径，本版用"三大流程 + 多层审批"作为统一主线重排了各阶段顺序
> （脚本审查并入"全段守护"、新增"跨流程制品一致性"为独立阶段、代码变更驱动顺延为第四阶段），
> 各阶段的技术内容与原版一致，只是对齐到公司级治理机制的主线上。工程骨架不变。

### 关键桥梁：代码变更驱动的流程响应

第四阶段是接入全公司业务线的关键。它妙在：

> **让 Agent 的能力自然流到所有业务线，但 Agent 本身仍然只懂 CI/CD 流程，不需要懂业务代码。**

每个业务线都在改代码、都在触发流程，但 Agent 只做"代码 Diff → 流程响应"这一件事。这比让 Agent 学各业务线的 AST 可复制性高一个量级。

它能把 Trunk Flow、GitLab CI、Agent 和公司 AI 基建串起来。这是比普通代码审查更符合主线的连接点，因为它解决的是：

> 代码发生变化以后，流程应该如何动态响应。

## 五、工程机制：让能力可被未来复用

演进路径要成立，不能只靠"未来扩展"四个字。需要工程机制保证扩展时不重写。

### 分层架构

```text
┌─────────────────────────────────────────────────────────┐
│  业务线接入层                                          │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐    │
│  │ 后端服务 │ 前端    │ IaC     │ 数据管道 │ CI 模板 │    │
│  └────┬────┴────┬────┴────┬────┴────┬────┴────┬────┘    │
│       ▼         ▼         ▼         ▼         ▼         │
│  ┌─────────────────────────────────────────────────┐     │
│  │  Agent 推理层（通用，与工件无关）                │     │
│  │  · 变更意图理解                                  │     │
│  │  · 影响范围规划                                  │     │
│  │  · 验证场景生成                                  │     │
│  │  · 补丁候选生成与取舍                            │     │
│  │  · 生成-验证-修正闭环（含终止条件）              │     │
│  └─────────────────┬───────────────────────────┘     │
│                    │ 调用                              │
│       ┌────────────┴───────────────────┐             │
│       ▼   工具插件接口 ArtifactAnalyzer              │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐  │
│  │ Java    │ TS      │ TF      │ SQL     │ CI-YAML │  │
│  │ AST/    │ tsc/    │ plan/   │ lineage │ DAG/    │  │
│  │ callgraph│ eslint │ apply   │ analyzer│ rules   │  │
│  └─────────┴─────────┴─────────┴─────────┴─────────┘  │
│       │                                             │
│       ▼   验证器插件接口 ArtifactVerifier           │
│  ┌─────────┬─────────┬─────────┬─────────┬─────────┐  │
│  │ JUnit   │ vitest  │ TF plan │ SQL dry │ GitLab  │  │
│  │ runner  │ runner  │ /apply  │ run     │ Lint/   │  │
│  │         │         │         │         │ Dry-run │  │
│  └─────────┴─────────┴─────────┴─────────┴─────────┘  │
└─────────────────────────────────────────────────────────┘
```

### 三条设计原则

1.  **推理层与工件解耦**：Agent 主体不关心"YAML"还是"Java"，只面向抽象的工件模型。
2.  **工具接口标准化**：`ArtifactAnalyzer` / `ArtifactVerifier` 两个接口，每种业务线实现一套插件。
3.  **CI-YAML 是首个插件**：第一阶段交付物，验证整个架构跑得通。

### 为什么这样设计让"未来扩展"不变成空话

如果没有可插拔接口，演进路径第三、四阶段每接一个业务线都要重写推理层。有了接口，接入新业务线只需实现新插件，推理层不动。这是"宏大叙事"不沦为口号的工程载体。

### 护栏：第二切片跑不通要回头改抽象

未来扩展到第二业务线时，如果发现"换个工件就要重写推理层"，说明抽象错了。正确动作是回头改抽象，不是硬接业务线。这是验证架构正确性的关键检查点。

### 工程地基的先验 Spike

演进路径要跑起来，第一阶段之前需要一个工程地基 Spike：

*   **验证公司内部模型 API 的函数调用能力、限速、上下文长度**——决定 Agent 自验证闭环能否成立，比 GitLab API 更硬的前置约束（公司不允许公网 Claude/Anthropic API，须用 GLM5.1 / DeepSeek V4 等内部模型）；
*   验证 GitLab CI Lint / Pipeline Dry-run API 真实能力边界（能力、限速、鉴权）；
*   调研 `gitlab-ci-local` 等开源本地模拟器，决定自研 or 复用；
*   写出能解析本仓库 `include` / `extends` / `!reference` 的最小解析器。

`include` / `extends` / `!reference` 的解析器本身就是 2-4 周工作量——GitLab CI 有 `include` 多来源、`extends` 多级链式继承、`!reference` 跨文件引用、`rules` 的 `if` 表达式求值（变量匹配、正则、`~` 正则匹配符）、`needs` 的 `optional: true` 语义。它不能被当背景板一笔带过，是整个项目 70% 工作量的地基。

### 合规与模型边界

*   **公司内部开发允许使用 AI**；"禁止 AI 代码开发"的禁令针对外包，不影响本实习项目（主要面向内部）。
*   **仍必须用公司内部模型**（GLM5.1 / DeepSeek V4 等），不允许公网 Claude/Anthropic API（数据出口合规）。
*   故审查式补丁（改 CI YAML）对内部不再灰色，Agent 可放手做生成补丁、自验证。
*   Common 层是共享底座，Agent 自动改 Common 层模板可能需更高治理审批（治理问题，非合规禁止）；首切片聚焦各业务线仓库的发版流程，规避此问题。

## 六、第一个任务可以怎么做

> **门禁机制澄清**（承接第四章首切片检测规约）：本仓库审批门禁靠 `workflows/app-workflow.yml`
> 的 `stages:` 列表偏序 + `when: manual` 实现——`approval` stage 排在 `deploy-prod` stage 之前，
> GitLab 同 stage 内 Job 全完成才进下一 stage。**不是**靠生产部署 Job 的 `needs` 指向审批 Job
> （`deploy-prod` 无 needs，`deploy-container-prod` 的 needs 仅 `[build-container]`）。故首切片
> 检测核心是 **stage 偏序覆盖 + 审批层级集合包含**，needs 图仅用于构建依赖齐全性。下面示例的缺陷
> 即落在 stage 偏序上，而非 needs 上。

不要一开始让 Agent 审查所有合规问题。第一版只处理一种修改：

> **某个发版流程 Job 的** `rules`、`extends` **或** `needs` **发生变化，牵动审批门禁完整性。**

### Agent 输入

```text
MR 描述：
"紧急修复加速：生产部署改为跳过 UAT，直接从主干 tag 发版。"

MR Diff：
- 将 workflows/app-workflow.yml 的 stages: 列表中 `approval` 移到 `deploy-prod` 之后（审批不再先于生产部署）
- deploy-container-prod 仍 extends .release_rules、needs: [build-container] 未变
```

### Agent 执行过程

#### 第一步：定位影响范围

沿着仓库结构与审批架构追踪：

```text
stages/docker-deploy.yml
→ jobs/deploy/vm-deploy.yml
→ rules/release-rules.yml
→ rules/branch-conditions.yml
→ stages/approval.yml（appsec-approval / release-approval）
→ rules/release-rules.yml（审批门禁的条件域）
```

#### 第二步：生成场景

```text
发版流程（tag）+ 当前审批齐全
发版流程（tag）+ 本次改动后审批缺失
非发版流程是否被误开放了生产部署
tag 下 Argo 与 VM 两种部署路径的门禁
```

#### 第三步：调用工具

工具返回：

```json
{
  "scenario": "tag",
  "present_jobs": ["deploy-container-prod", "build-container", "approval", "appsec_approval"],
  "stage_order_ok": false,
  "missing_gate": [
    {
      "job": "deploy-container-prod",
      "required_approval": "appsec_approval",
      "reason": "approval stage 不再先于 deploy-prod stage（stages: 偏序违规），审批门禁时序被破坏"
    }
  ]
}
```

#### 第四步：Agent 诊断

Agent 结合 MR 描述与多层审批架构进一步发现：

```text
MR 意图是"跳过 UAT 加速"，但实际改动把 approval stage 重排到了 deploy-prod 之后，
属于在加速名义下让审批不再先于生产部署，绕过安全层 Approve，违反多层审批契约。
即使 build-container 仍在、审批 Job 仍存在，审批门禁的时序已被破坏——
生产部署可先于审批触发，门禁形同虚设。
```

#### 第五步：生成修复建议

第一阶段补丁范围允许修改 `rules` / `needs` / `extends` 与 `workflows/*.yml` 的 `stages:` 列表顺序自身。架构级建议放"附加观察"：

```text
[补丁候选 - 范围内]
方案 A：把 stages: 列表中的 approval 恢复到 deploy-prod 之前
  - 简单，直接恢复审批门禁时序
  - 符合原治理设计，不引入不该出现的审批

方案 B：若确实需要加速，给生产部署 Job 的 stage 单独命名并保持其仍位于 approval 之后
  - 保留"加速"意图的空间，但不破坏审批时序
  - 需确认该路径仍经过必需审批层

[附加观察 - 超出第一阶段补丁范围]
方案 C：为"紧急修复"设计一条受控的快速通道（如预先审批 + 事后复审）
  - 符合"加速"意图且不破坏门禁
  - 属于流程级改造，建议单独立项，不在本阶段自动补丁循环内
```

#### 第六步：验证补丁

再次调用：

*   YAML Lint；
*   Dry-run；
*   DAG Validator；
*   审批门禁完整性检查器。

最多 3 轮。连续 2 轮失败 → 降级为仅诊断模式。三者全过 → 生成 MR Suggestion，由开发者确认。

这就比普通静态检查器深了一层。

## 七、哪些部分算 AI，哪些部分算平台

| 模块 | 是否需要 AI | 原因 |
| --- | --- | --- |
| YAML 解析 | 否 | 必须确定性 |
| include/extends 合并 | 否 | GitLab 语义固定 |
| rules 求值 | 否 | 可以精确计算 |
| DAG 检查 | 否 | 图算法即可 |
| 审批门禁完整性检查 | 否 | 图算法 + 条件域规则即可 |
| 修改意图理解 | 是 | 来源是自然语言和上下文 |
| 受影响流程推理 | 部分需要 | 跨流程、跨审批、跨脚本 |
| 测试场景规划 | 是 | 需要控制组合数量和覆盖率 |
| 根因解释 | 是 | 需要组合多种工具结果 |
| 补丁生成 | 是 | 涉及代码生成和设计选择 |
| 补丁验证 | 否 | 必须由确定性工具完成 |
| 修复迭代 | 是 | 根据工具反馈重新规划 |
| 合并/放行 | 不自动 | 必须人工审批 |

比较合理的比例是：

```text
70% 确定性工程工具
30% Agent 推理、规划和生成
```

这不是 AI 含量不足，反而是企业 Agent 正确的实现方式。

一个可靠的 Agent 不应该把所有判断都交给大模型，而应该是：

> **LLM 负责决策和编排，工具负责事实和执行。**

## 八、可能存在的量化指标

| 指标 | 含义 |
| --- | --- |
| 门禁回归检出率 | 注入的审批/流程违规中发现多少 |
| 场景覆盖率 | 是否覆盖真正受影响的流程场景 |
| 场景压缩率 | 相比全量三流程组合减少多少测试 |
| 根因定位准确率 | 是否定位到正确流程段和审批门 |
| 首次补丁通过率 | 第一次生成的修复能否通过验证 |
| 最终补丁通过率 | 多轮修正后是否通过 |
| 补丁采纳率 | 人工是否接受建议 |
| 误报率 | 正常改动是否被错误阻断 |
| 平均工具调用次数 | Agent 完成任务的成本 |
| 每次审查 Token 成本 | 是否可用于生产 |

### 评测集与基线

*   **离线评测集**：真实历史发版 MR 回溯 + 注入违规，目标 30-50 标注样本。发版流水线每条业务线都跑，故可拿到真实数据；评测以发版流程为基线。
*   **基线**：场景压缩率的基线是"全量三流程组合"——全量组合本身需要先实现，才能算压缩率。
*   **通用性**：指标写成通用的（检出率、采纳率、压缩率），不是发版专属指标，便于第二流程段、第二业务线复用。

### 三模式对照实验

还可以对比三种模式：

```text
A. 纯 LLM 直接阅读 YAML
B. 确定性检测器
C. Agent + 确定性工具 + 自验证
```

预期结果应该是：

*   A：解释灵活，但容易漏报和幻觉；
*   B：检测稳定，但不会理解意图、生成完整修复；
*   C：兼顾精确检测与自动修复。

这会形成比较完整的实验价值。

### 已知失败模式

需在评测集专门覆盖：

*   LLM 把 `needs` 误读成 `dependencies`；
*   把不存在的 Job 名当存在的（幻觉 Job）；
*   把 `rules` 的 `if` 表达式写错语法；
*   把 `extends` 的隐藏模板 `.foo` 当成可见 Job；
*   跨 `include` 引用解析错误；
*   跨流程条件域判断错误（如把分支流程的 Approve 误当作发版流程的门禁）；
*   把"团队内部 Pro"误当作"安全层 Approve"，门禁覆盖范围判错。

## 九、总结

单纯做 rules 与 needs 的一致性检测，本质上仍然是普通 CI 平台工具，不能直接作为 AI 或 Agent 课题。它更适合作为 Agent 可以调用的一个确定性分析工具。

更合理的项目边界是：

> **以任意业务线仓库的变更为输入，构建一个能够理解变更触及哪几段流程、牵动哪些审批门禁、调用确定性工具诊断合规回归、生成受限补丁并自验证的合规守护 Agent。** 第一阶段只守发版流程的审批门禁完整性。

第一阶段只支持：

```text
发版流程的审批门禁完整性
```

第一种缺陷只支持：

```text
生产部署 Job 出现，但所需上游 Approve/构建 Job 不齐全或条件域不一致
```

第一种自动修复只支持：

```text
调整 `stages:` 列表顺序 / `rules` / `needs` / `extends`，使审批 stage 先于生产部署 stage 且门禁齐全、条件域一致
```

架构级改造建议（如重构审批层、制品晋级）作为附加观察，不进入自动补丁循环。

定位上，这个合规守护 Agent 是 Coding Agent 的一个垂直子能力，不是平级概念。当前保持窄边界（发版门禁一种缺陷），但锚定的是公司级治理机制（三大流程 + 多层审批），故天然覆盖全公司发版，回应 Leader "宏大"；能力沉淀通过可插拔的工件接口（`ArtifactAnalyzer` / `ArtifactVerifier`）保证可被未来各业务线复用，而非绑死在 CI YAML 这一种工件上。

```text
当前：发版审批门禁完整性守护 Agent
近期：三大流程全段守护 + 跨流程制品一致性
中期：代码变更驱动的流程响应 + MR 代码审查与测试生成
远期：从 Issue 到 MR 的完整 Coding Agent
```

可以给 Leader 的表述：

> 第一阶段不开发通用 Coding Agent，而是做一件目前没人做的事：作为 MR/发版时的审查者，守护公司所有业务线都要遵守的"三大流程 + 多层审批"契约。首期只守发版流程的审批门禁完整性，边界明确、可验证、有真实发版数据。后续沿演进路径扩展到三大流程全段守护、跨流程制品一致性、代码变更驱动的流程响应、MR 代码审查与测试生成，最终作为完整 Coding Agent 的交付与验证子系统。技术栈锁定公司内部模型 + 合规 Claude Code 载体。

这样既足够细分，又真正包含了 Agent 的核心能力；既回应了"宏大"——锚定公司级治理机制，覆盖各业务线发版；又保留了"窄交付"——第一阶段只做发版门禁完整性，边界明确、可验证；且不与已有工作重叠（Daryl 做生成式接入 Skill，Agent 做合规守护审查，分工互补）。
