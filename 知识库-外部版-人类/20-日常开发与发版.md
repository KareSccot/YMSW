# 日常开发与发版

## 目标
读完本章后，开发者能掌握日常开发中的 CI/CD 操作流程、发版流程和常见管理操作。

## 前置条件
- 已完成项目接入（见 10-新手接入指南.md）
- 拥有对应项目的访问权限

## 操作步骤

### 日常开发流程
1. 在功能分支开发完成后，提交并推送至远程仓库
2. 流水线自动触发，执行 build → quality 阶段
3. 在 GitLab → CI/CD → Pipelines 查看流水线状态
4. 创建 Merge Request，触发 MR Pipeline
5. 通过所有检查后合并到主分支

### 发版流程
1. 确保所有功能代码已合并到主分支
2. 创建版本 Tag（如 `v1.2.0`）并推送
3. 自动触发 Release Pipeline：
   - 记录发版人信息
   - 进入 Release Approval 阶段（需第二人审批）
   - 进入 AppSec Approval 阶段（安全团队审批）
4. 审批通过后，手动部署到 UAT 环境验证
5. UAT 验证通过后，手动部署到生产环境
6. 发版完成

### 管理 GitLab 流水线
- 查看流水线状态：GitLab → CI/CD → Pipelines
- 手动触发流水线：Run Pipeline → 选择分支和变量
- 查看失败日志：点击流水线 ID → 点击失败 job
- 取消/重试：在流水线页面点击 Cancel / Retry

### 常见问题
- **流水线未触发**：检查 `.gitlab-ci.yml` 文件是否存在，语法是否正确
- **查看发版进度**：在 Pipelines 页面查看各阶段状态
- **构建失败**：查看详细日志，定位错误原因
- **审批等待**：直接联系审批人处理

## 注意事项
- Release Approval 不能由发版人自己审批
- 生产部署前必须通过所有审批
- 安全扫描允许失败，但结果必须被审阅
- 自定义变量需以 `CUSTOM_` 前缀才能在远程脚本中使用

## 升级路径（搞不定找谁）
- 审批卡住 → 联系 Release Approver 或 AppSec 团队
- 安全扫描问题 → 联系安全团队 `#security-support`
- 部署失败 → 联系 DevOps 团队
- 紧急发版 → 联系 DevOps 主管协调
